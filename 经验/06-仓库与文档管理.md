# 仓库与文档管理

## 远程与分支

- `origin`：`https://github.com/pixian5/SukiSU-Ultra`（可写分叉）；`upstream`：官方仓库（只读）。
- 日常 `git push` 推 `origin`；不要直推 `upstream`（403）。
- 本地 `main` 的提交目前全是文档与 `tools/`，项目本体源码零改动。
- 上游 `main` 是 kprobe 模式，实际设备构建用 `origin/builtin`（手动挂钩），引用分支时要说清。

## 文档规范

- 文件命名：`docs/年月日-时分-标题-模型名.md`，例如 `20261108-0101-当前开发进度-DeepSeek-V4.1-Flash.md`。
- 每新增一份报告，必须在 `docs/README.md` 与 `docs/zh/README.md` 各加一条索引。
- 根 `README.md` 保留【当前开发进度】【下一步待实现】两节，详细内容放在对应的独立文档并互相链接。
- 根 `文档索引.md` 介绍 `docs/` 下每份文档；`经验/` 按类别提炼可复用结论。
- 历史文档结论可能被后续更正；新文档明确写「更正了哪一条」，避免旧说法继续流传。

## 资产与安全

- `backup/` 是大体积设备备份，已被 `.gitignore` 排除，**不入库**。
- 任何含凭据的配置（如 rclone）权限设 600、加入 `.gitignore`，绝不提交。
- 关键产物必须同时记录 MD5、SHA-256、大小与来源；`MANIFEST` 与文档两处都要有。
- 云电脑产物回传本机后要逐份复算校验值，不能只看传输工具提示成功。

## 发布纪律（用户明确要求，长期有效）

- **每个可交付产物都必须发布到 GitHub Releases**，不能只放在本地 `dist/` 或聊天附件里。
- Tag 规则：`<项目>-v<X.Y.Z>`，例如 `camellian-susfs-v0.0.4`；版本号与 `tools/camellian-susfs/VERSION` 同步，每次改动 +0.0.1、满十进一。
- Release 必须附：产物本体 + `SHA256SUMS.txt`；说明里写清适用设备/固件、大小、MD5/SHA256、内核版本、刷机与回退命令、刷后判据、已知限制。
- 未在真机验证的产物一律标 **pre-release**，不能暗示已验证。
- 发布后用 `gh release view <tag> --json assets` 核对附件名与字节数。
- 命令：`gh release create <tag> <产物> <SHA256SUMS.txt> --target main --title ... --notes-file ... --prerelease`

## 工作纪律

- **修改完必须检查再停止**：编译、补丁应用、脚本运行都要有可复现的验证命令与结果。
- 声称「成功」前先确认判据；尤其不要把「编译通过 / 开关打开」当成「功能可用」。
- 长任务先给阶段性结论与进度，避免用户长时间无反馈。
- 每轮把不必要的文件加入 `.gitignore`，提交信息用中文，提交后推送。
- 发现能明显优化、或与已有做法冲突的方向，主动提出让用户拍板。
