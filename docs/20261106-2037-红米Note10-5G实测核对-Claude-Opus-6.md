## 一、结论先行（与纸面评估有重要出入）

1. **这台手机已经有 root 了**：Magisk 的守护进程正在以 root 身份运行，普通调试终端执行 `su` 能拿到 `uid=0(root)`。所以「能不能 root」这个问题，答案已经是「已经完成」。
2. **但仍然不能直接用 SukiSU-Ultra 的现成安装包**。实测内核是 4.14.186，且**没有开启运行时挂钩所需的内核配置**，连「借现有 root 加载一个现成内核模块」这条路也走不通。要换成这个项目，仍然必须自己重编内核。
3. 纸面评估里「第一步必须解锁 Bootloader」这一条**需要修正**：既然 Magisk 已经在运行、能正常提权，说明这台设备的启动链早已被改过，或启动锁其实已解开但状态被伪装。解锁不再是待办事项。
4. 新增一个明确障碍：内核**没开符号全量表**，这会影响另一类「修补 boot 镜像」的替代方案（详见第五节）。

### 2.3 内核编译配置（本次最有价值的新发现）

从设备的 `/proc/config.gz` 读到的原样结果：

```
CONFIG_IKCONFIG=y
CONFIG_IKCONFIG_PROC=y
CONFIG_KALLSYMS=y
# CONFIG_KALLSYMS_ALL is not set
# CONFIG_KALLSYMS_ABSOLUTE_PERCPU is not set
# CONFIG_KALLSYMS_BASE_RELATIVE is not set
# CONFIG_KPROBES is not set
CONFIG_HAVE_KPROBES=y
CONFIG_HAVE_KRETPROBES=y
CONFIG_HAVE_SYSCALL_TRACEPOINTS=y
CONFIG_MODULES=y
CONFIG_EXT4_FS=y
```

翻译成人话：

- `CONFIG_KPROBES` **没有开启**。项目 `main` 分支要求它才能运行时挂钩，因此**自动挂钩路线确定不可用**，只剩 `builtin` 分支的手动改内核源码一条路。
- `CONFIG_KALLSYMS_ALL` **没有开启**。项目文档说明非通用内核规范设备要用可加载内核补丁模块（KPM）需额外开启它；另一类「修补 boot 镜像」方案也依赖它。当前内核不满足。
- `CONFIG_HAVE_KPROBES=y` 这类带 `HAVE_` 前缀的只表示处理器架构支持，**不等于功能已启用**，不要看错。
- `CONFIG_MODULES=y` 虽然允许加载内核模块，但下面第五节会说明为什么这仍然帮不上忙。

### 2.4 已存在的 root 方案

| 检查项 | 实测值 |
| --- | --- |
| 守护进程 | `magiskd`，PID 807，属主 root，父进程 1 —— **正在运行** |
| 二进制 | `/product/bin/magisk`（329320 字节）、`magiskpolicy`；`su` / `resetprop` / `supolicy` 都是指向它们的链接 |
| 版本 | `50af14f2-alpha:MAGISK:R`，版本代码 `28103`（Magisk Alpha） |
| 挂载痕迹 | `/debug_ramdisk` 上是 `magisk` 的 tmpfs，含 `.magisk/pts` |
| 提权验证 | `su -c id` 返回 `uid=0(root) gid=0(root) ... context=u:r:magisk:s0` |
| 本项目的管理器 | 系统中**没有**安装 SukiSU / KernelSU / APatch 相关应用 |
| `/sys/module/kernelsu*` | 不存在（内核里没加载本项目的模块） |

### 2.5 启动锁相关属性（存在一个矛盾，必须说明）

读到的属性是：`ro.boot.flash.locked=1`、`ro.boot.vbmeta.device_state=locked`、`ro.boot.verifiedbootstate=green`、`ro.boot.veritymode=enforcing`、`sys.oem_unlock_allowed=0`。单看这些会以为「完全没解锁、官方原封未动」。

**但 Magisk 正在 root 运行，两者是矛盾的**。最可能的解释是这些属性值被 root 隐藏类模块改写过（这类模块常把启动状态伪装成官方锁定，用来通过应用检测）；也可能是启动锁实际已解开、而属性仍被改成锁定显示。设备上同时存在 `resetprop` 这个改属性工具，进一步支持这个推测。

尝试从更底层的 `/proc/cmdline` 与 `/proc/bootconfig` 找原始启动参数，**没有找到对应条目**，所以本次**无法确定真实的 Bootloader 解锁状态**。想确认必须让手机进入刷机模式后读底层变量（例如 `fastboot getvar unlocked`、`fastboot oem device-info`），那一步会**重启手机**，本次没有擅自执行。`sys.oem_unlock_allowed=0` 只表示开发者选项里的「OEM 解锁」开关当前没打开，不能当成「厂商禁止解锁」的证据。

## 四、为什么「已有 root」也不能一键换成 SukiSU-Ultra

有人会想：既然已经能拿到 root，直接把项目的内核模块加载进去不就行了？实测数据说不行，四个原因：

1. **没有对应的模块文件**：项目的持续集成只产出 5.10 到 6.18 那批通用内核规范版本的内核模块，没有为这台机器 4.14.186 厂商内核编译的版本。
2. **挂钩机制没开**：`main` 分支的模块依赖 `CONFIG_KPROBES`，当前内核没开启；即便硬编出模块，挂钩也注册不上。
3. **模块签名与版本串**：厂商内核加载模块时会核对版本串与签名，跨源码树编译的模块通常直接被拒绝。
4. **两套方案会互相打架**：Magisk 已经改了启动镜像和初始系统，SukiSU 也要改同一处，不先移除 Magisk 就叠加，大概率起不来。

所以路径只有一条：**拿这台机器对应的内核源码，开启所需配置、按 `builtin` 分支手动加入挂钩，编译出完整内核/boot 镜像，处理启动校验后刷入**。而且现在多了一个前置动作：先决定现有 Magisk 怎么处理。

## 五、现在有哪些选择

### 选项 A：什么都不做（如果目的只是「有 root」）

手机已经能提权，Magisk Alpha 28103 正在工作。不改动就没有任何风险，也不用解锁、不用编译、不用清数据。

### 选项 B：继续用 Magisk

维持现状，按需装模块。代价是拿不到 SukiSU-Ultra 的隐藏检测机制、可加载内核补丁模块和主题商店生态；另外系统安全补丁停在 2023-10-01，系统本身较旧。

### 选项 C：换成 SukiSU-Ultra（门槛最高）

具体要做：确认真实解锁状态 → 取对应 `V14.0.4.0.TKSEUXM` 的内核源码（小米开源索引有 `camellian-t-oss` 分支，社区另有 4.14 源码树）→ 先独立编出能开机的内核 → 打开所需内核配置、按 `builtin` 分支手动加挂钩 → 编译 → 处理 `vbmeta`/AVB 校验 → 移除现有 Magisk → 刷入并保留原 boot 镜像以便回退。
代价：需要内核编译与救砖能力；刷错可能开不了机；数据要先备份；这一步不是几分钟能完成的事。

### 选项 D：先把「真实解锁状态」查清楚

需要把手机重启进刷机模式，再读底层变量。**这一步会打断手机使用并重启**，所以本次没有做，需要你明确同意后我再执行。

**推荐顺序**：如果 root 已经满足需求，选 A，不要为了换方案去动一台正常工作的手机；如果确实想体验 SukiSU 的特性，先做 D 把底摸清，再评估 C 值不值得，并强烈建议先用备用机练手。

## 八、术语说明

| 名词 | 含义 |
| --- | --- |
| root / uid=0 | 系统里的超级用户身份；`uid=0` 是拿到这个身份的确证 |
| USB 调试 / adb | 开发者选项里的调试通道，用来在电脑上读手机信息、执行终端命令 |
| Magisk | 一种通过修补启动镜像取得 root 的方案；`magiskd` 是它的后台守护进程 |
| 守护进程 | 开机后一直在后台运行、提供服务的程序 |
| 内核配置 | 编译内核时打开或关闭的功能开关，`CONFIG_XXX=y` 表示启用 |
| kprobe / 手动挂钩 | 在内核函数执行时插入自己代码的两种办法；前者要求内核开启对应配置 |
| 运行时挂钩 | 不用改内核源码、开机后动态注册挂钩的方式 |
| 启动镜像 / boot 分区 | 开机时加载内核和初始系统的那一小块存储区域 |
| 启动校验（AVB / vbmeta） | 开机时检查系统有没有被改动的机制，改动 boot 后要一并处理 |
| 刷机模式（fastboot） | 关机状态下按住组合键进入的、供电脑刷写分区的模式 |
| A/B 双槽位 | 系统存两份、交替升级的设计，`_b` 表示当前从第二份启动 |
| 官改 / 改版固件 | 在原厂系统基础上被人修改后重新分发的系统包 |
