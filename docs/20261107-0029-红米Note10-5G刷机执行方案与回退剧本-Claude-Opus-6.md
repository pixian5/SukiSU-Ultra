## 0. 这份文档是什么、不是什么

**是**：一份可以照着一步步做的操作剧本。每一步都写清「动手前确认什么、具体做什么、看到什么才算通过、不通过往哪里退」。

**不是**：不是授权，也不是执行记录。用户明确说过「在我明确说刷机之前，你不要修改我手机的数据。你可以只读」。所以此刻到用户明确说出「刷机」为止，本方案里的任何一条都不会被执行。

**解除条件**：用户明确说出「刷机」，或明确点名授权某一个具体动作。「继续」「下一步」「方案写好了就照做」这类含糊指令不算授权。

**电脑侧改动的影响面（回答「是不是只改了启动分区镜像」）**：截至本文档更新，手机侧写入为零——没有任何分区、启动槽、校验分区、文件或应用被改过，手机仍是原来的 Magisk Alpha 环境。电脑与云电脑侧做的是内核源码改动、编译、打包、下载官方用户态组件、写文档与脚本，这些全都只是文件。将来真正执行时：第 7 阶段只写当前槽的启动分区，且镜像里只换了内核那一段，原厂内存盘、设备树、校验结构、分区大小都原样保留；第 8 阶段安装管理器安装包会往手机的数据分区放置后台程序（这是 root 环境的一部分，不是系统分区）；默认不动校验分区，也不碰用户数据分区和另一槽。所以「只动一个分区」对试刷那一步成立，对完整流程不成立。

## 1. 先把词讲清楚（后文第一次出现时都用全称或先解释）

| 词 | 用大白话讲是什么 |
| --- | --- |
| 启动分区镜像（`boot.img`） | 手机开机时最先加载的一小段数据，里面装内核、内存盘、设备树和校验信息。刷内核改的就是它。 |
| 系统槽（a 槽 / b 槽） | 这台手机把启动相关的分区做了两份物理拷贝，一份叫 `boot_a`，一份叫 `boot_b`。当前用的是 b 槽。 |
| 虚拟 A/B（VAB） | 一种系统更新方式，影响的是系统、厂商分区这类放在「超级分区」里的逻辑分区和快照合并；**不改变启动分区有两份物理拷贝这个事实**。 |
| 启动校验（AVB）与校验分区（`vbmeta`） | 开机时核对启动分区有没有被改过的一整套机制；记录核对规则的那块数据叫校验分区。 |
| 防回滚（anti-rollback） | 厂商记录的「最低允许安全版本」，防止刷回太老的固件。 |
| `adb` | 手机**正常开机**时，电脑通过 USB 和手机通信的通道，能读属性、装应用、执行命令。 |
| `fastboot` | 手机**停在刷机模式**时，电脑通过 USB 直接写分区的通道。 |
| 内存盘（ramdisk） | 开机最早加载的一个小型文件系统，里面放启动脚本。 |
| 设备树 | 一张「这块板子上有哪些硬件、各接在哪里」的说明书，内核靠它认硬件。 |
| 用户态后台程序（`ksud`） | 开机后以最高权限常驻的普通程序，负责模块、授权、策略。 |
| 管理器安装包（APK） | 手机上的那个管理界面应用，负责授权、装模块、看状态。 |
| 线刷包 | 电脑用 `fastboot` 写各分区的完整固件包（`.tgz`），里面有原厂 `boot.img` 和全部救砖材料。 |
| 载荷新鲜度 | 「这次要刷的文件，确实是最后一次编译/打包出来的那份」，判据是文件时间不早于最后一次构建时间，光看版本号不算。 |

## 2. 目标与「成功」的判据

**目标**：把自编的 SukiSU 内核只写进当前槽的启动分区，另一槽原封不动留着当后路；装好用户态组件；让手机开机后 SukiSU 可用。

**全部满足才算成功**：

1. 能正常进系统，`sys.boot_completed` 变成 `1`，不是卡在开机动画或反复重启。
2. 当前槽仍是 b，`boot_a` 从未被写过。
3. 手机读出来的内核版本串是自编内核（不再是原厂那串 `4.14.186-perf-gf8d872e9279c`）。
4. 管理器能识别到内核，显示已安装，接口版本为 6。
5. `su -c id` 返回 `uid=0(root)`。
6. 原厂启动镜像、**手机原本那份被 Magisk 改过的启动分区备份**、以及本轮回退所需文件都在电脑上手边且校验值对得上。

**判定失败**：卡开机动画超过 10 分钟、连续自动重启、进 Recovery 而不是系统、管理器提示未安装/内核不支持、root 不可用、出现启动校验红屏且无法继续。

## 3. 红线：绝对不做的事

- **不执行 `flash_all_lock.sh`**：这个官方脚本会重新锁上启动锁，自编内核必然起不来，属于必砖操作。
- **不执行 `flash_all.sh`** 作为试刷手段：它会刷两个槽、刷超级分区、擦启动分区和元数据分区、刷用户数据分区（清数据）、刷一系列校验分区、读取防回滚计数、最后把活动槽切到 a。这是「整包恢复/救砖」，不是试刷。
- **不用不带槽后缀的 `fastboot flash boot ...`**：试刷必须点名 `boot_b`，避免写到含糊的默认目标。
- **不刷 `boot_a`**：另一槽是后路。
- **不动用户数据分区、元数据分区、超级分区**：不清除数据、不恢复出厂。
- **不刷 `vbmeta_a`**：连另一槽的校验分区都不碰。
- **不把「切到另一个槽」当第一回退手段**：顺序见第 10 节。
- **不在电量低、线缆不可靠、电脑可能断电时刷**。
- **不在载荷新鲜度没核对完之前刷**。

### 6.2 把手机当前那一槽的启动分区整块读回电脑（最重要的回退资产）

**为什么**：手机现在的启动分区是被 Magisk Alpha 改过的，而线刷包里的原厂启动镜像是没改过的。如果只靠线刷包回退，刷回去会是一个**没有 root** 的原厂状态，Magisk 的启动层补丁就丢了。把当前分区原样读回来，才能精确复原到刷机前的样子。

> **2026-11-07 08:52 重要更正：本节原先那条「直接把读出的内容重定向到文件」的命令已作废，不要再用。** 实测发现这台设备的 USB 调试原始输出通道**不是二进制干净的**：数据里每一个换行字节都会被写成「回车 + 换行」。直接重定向得到的备份会被撑大、中间被插入字节——当前槽启动分区实测多出 105,890 字节，连末尾的校验尾都被推后了。这种文件刷回去是危险的。早期按「尾部多几个 0 字节、截掉即可」处理同样错误，那只是小分区的假象。
>
> 正确做法已固化在 `tools/camellian/scripts/backup_partitions_readonly.py`：把每个「回车 + 换行」还原成单个换行（这是该转换的精确逆变换），强制要求还原后长度**精确等于**内核报告的分区大小；每个分区读两遍比对；最关键的启动分区再用手机自带的文本编码走一条完全不碰二进制的通道做第三方比对。

```bash
# 只读备份：不重启、不切槽、不写任何分区、不往手机推文件
python3 /Users/x/code/SukiSU-Ultra/tools/camellian/scripts/backup_partitions_readonly.py
```

复核：脚本会输出每份文件的字节数、MD5、SHA256，并生成 `/Users/x/camellian-flash/BACKUP-MANIFEST.txt` 与 `device-state-before.txt`。启动分区必须是 67,108,864 字节、开头 8 字节 `ANDROID!`、末尾 64 字节是校验尾。**「长度精确相等 + 两次读取一致 + 文本编码交叉比对一致」三条同时成立才算可用回退件。** 这份备份比线刷包里的原厂启动镜像更贴近「刷机前的手机」。

> 说明：`su -c` 靠的是手机上现有的 Magisk Alpha root，只读分区、不写手机；「原始输出通道能原样传二进制」这个假设在这台设备上不成立，所以必须走上面的修正脚本。

**执行状态**：2026-11-07 08:52 已在用户单独点名授权下完成，12 个分区全部通过校验。详见 [手机分区只读备份与传输污染排查](./20261107-0852-手机分区只读备份与传输污染排查-Claude-Opus-6.md)。

## 7. 第 2 阶段：只写当前槽的启动分区

**为什么只写一个槽**：这台手机的启动分区是两份物理拷贝；虚拟 A/B 影响的是系统分区的快照合并，不改变这一点。试刷时只写当前在用的 `boot_b`，`boot_a` 一个字节都不动，留着当后路。官方全量恢复脚本会刷两个槽，那是「整包升级/救砖」场景，和试刷是两回事，别混。

```bash
# 只把当前槽 b 的启动分区换成自编内核镜像
/Users/x/Library/Android/sdk/platform-tools/fastboot flash boot_b ~/camellian-flash/boot-sukisu-lto-stockdtb.img
```

**判据**：命令返回 `OKAY`，写入字节数与文件大小一致；写之前再确认一次 `current-slot` 仍是 b。写完之后 `boot_a` 必须从未被写入过。

**这一步不要顺手做的事**：不要刷校验分区、不要切槽、不要 `fastboot erase`、不要刷任何别的分区。

### 7.1 校验分区策略（需要你拍板，见第 13 节）

- **方案 A（推荐，默认）**：**不动校验分区**。理由：启动锁已解锁，校验错误按理不致命；现在手机上的 Magisk Alpha 本身就把启动分区改过且能开机，这是最强旁证；少改一个分区就少一条回退链。自编启动镜像里保留的校验哈希仍是原厂内容，没有厂商私钥无法重签，这一点要在心里有数。
- **方案 B（兜底，仅在 A 起不来且确认是校验问题时）**：把 `vbmeta-verification-disabled.img` 写到 `vbmeta_b`，等价于临时关闭校验。代价：多改一个分区；之后**必须**用第 6.2 节读回来的 `vbmeta_b-before.img` 对称刷回，否则以后的官方更新或整包恢复可能出问题。
- **两种方案都绝对不碰 `vbmeta_a`，也绝对不用 `flash_all_lock.sh`。**

## 8. 第 3 阶段：开机与用户态接入

```bash

/Users/x/Library/Android/sdk/platform-tools/fastboot reboot
```

### 8.1 装管理器安装包

```bash
/Users/x/Library/Android/sdk/platform-tools/adb install -r ~/camellian-flash/SukiSU_v4.3.0-r2_41150-release.apk
```

### 8.2 为什么不需要手工往手机推后台程序

**先用大白话讲机制**：官方管理器安装包里**已经打包了一份后台程序**（安装包里那个 `libksud.so` 就是它）。内核在开机时会核对管理器的签名，认出来之后给这个应用最高权限；管理器随后自己把后台程序放进手机数据分区的 `/data/adb/ksud`，并在开机脚本里注册好。所以「装用户态」这一步，真正要做的只是**把管理器安装包装上**，不是手工传文件。

代码里的依据（括号附定位，看不懂可跳过）：管理器里取后台程序路径的 `getKsuDaemonPath()` 与执行安装的 `install()`，位于 `manager/app/src/main/java/com/sukisu/ultra/ui/util/KsuCli.kt`；内核里写死目标路径的 `KSUD_PATH` 与开机脚本注入逻辑，位于 `kernel/runtime/ksud.h` 和 `kernel/runtime/ksud_integration.c`。

补充核对过的两件事：官方安装包 v2 签名的第一张证书长度 860 字节、SHA256 `947ae944f3de4ed4c21a7e4f7953ecf351bfa2b36239da37a34111ad29993eef`，与内核白名单第一条完全一致；内核与安装包的接口版本都是 6。我们另外下载的独立后台程序只是备用件，不必推到手机。

打开管理器，确认它识别到内核；若提示需要完成安装或重启一次，按界面提示做一次。

### 8.3 一个必须提前说明的预期变化

我们打包时用的是**原厂线刷包里的内存盘**，不是手机当前被 Magisk 改过的那份内存盘。所以刷入之后，Magisk 的启动层补丁会消失，**SukiSU 会成为唯一的 root 方案**；手机数据分区里 Magisk 的模块和配置还在，但不会生效。这是预期，不是故障。

精确回到刷机前的 Magisk 状态，靠的是第 6.2 节读回来的那份备份；只刷线刷包里的原厂启动镜像，回到的会是「无 root 的原厂状态」。

## 10. 第 5 阶段：回退剧本（按顺序，不要跳级）

**先停下来**：出现第 2 节的失败判据，立刻停止重试，别反复开机把问题搅复杂。

### 10.0 回退前先解决一个实操前提：系统起不来时怎么进刷机模式

第 6.4 节进刷机模式用的是 `adb reboot bootloader`，它依赖安卓系统已经正常起来。而回退场景恰恰是「新内核没能开机」——这时 `adb` 根本连不上，那条命令用不了。**刷回原启动分区这件事本身没问题，但前提是手机能停在刷机模式，让电脑有通道写分区。**

好消息：试刷只写了启动分区，没有碰引导加载程序（开机第一段、负责提供刷机模式的程序），所以内核起不来时刷机模式通常依然进得去。执行前必须落实的是：

- **先查清这台机型进刷机模式的硬件按键组合**（联发科平台常见是关机状态下按住音量键再接 USB，但音量上还是音量下、要不要同时按电源键，因机型而异）。本轮没有实机验证过具体组合，不能凭印象写死；应在手机还正常时查证并实际演练一次。
- 如果手机卡在重启循环，先长按电源键强制关机，再按组合键进入。
- 进刷机模式后用 `fastboot devices` 确认电脑看得见设备，再执行下面的刷回命令。
- 刷回前读一次 `fastboot getvar current-slot`，确认仍是 b；不要在没确认槽位的情况下写入。
- 命令必须点名 `boot_b`，不要写不带槽后缀的 `boot`。

如果连刷机模式都进不去，那就不是刷回启动分区能解决的了，属于第 6 优先的联发科预加载器级救砖，先停下来单独评估。

**第 1 优先 — 精确复原（如果第 6.2 节的备份做成了）**

> **最容易踩的坑**：线刷包里的原厂启动镜像**不是**「原来的面具 boot」。它是没打过 Magisk 补丁的干净版本，刷回去通常能开机，但会失去 root。要「刷回原来的面具 boot 且仍保留 root」，手里必须是从手机当前槽整块读回来的 `boot_b-before.img`。这份备份**目前还没有做**，它是执行前第一件要补的事，而且只是把手机上的分区读回电脑，不写手机。

```bash
# 在当前槽 b 刷回「刷机前那份」启动分区，精确回到 Magisk Alpha 状态
fastboot flash boot_b ~/camellian-flash/boot_b-before.img
fastboot reboot
```

这是最干净的一条：刷完就是原来的系统、原来的 root。

**第 2 优先 — 同槽刷回原厂启动镜像（没有备份或备份不可用时）**

```bash
# 只刷当前槽 b，换回线刷包里的原厂启动分区镜像
fastboot flash boot_b ~/camellian-flash/boot-stock.img
fastboot reboot
```

**后果要讲清**：Magisk 的启动层补丁会消失，手机回到无 root 的原厂状态。之后若要恢复 Magisk，需要用管理器重新修补启动镜像再从电脑刷入；数据分区里的模块和配置还在，不会丢。

**第 3 优先 — 对称刷回校验分区（仅在确实动过它时）**

```bash
# 只有用了方案 B 才需要这一步：把读回来的原厂校验分区刷回同一槽
fastboot flash vbmeta_b ~/camellian-flash/vbmeta_b-before.img
```

**第 4 优先 — 切到另一个槽**

```bash
fastboot --set-active=a
fastboot reboot
```

**三个前提必须同时成立**：a 槽本来就是可启动状态；两个槽的系统版本与用户数据兼容；当前没有进行中的系统更新快照合并。而且**用户数据分区是两个槽共用的**，切槽不会把数据「换回旧的那份」，所以切槽不能当作数据恢复手段。

**第 5 优先 — 官方全量线刷（最后手段）**

用线刷包里的 `flash_all.sh`。执行前必须再确认一次数据已备份，并再次确认**不是** `flash_all_lock.sh`。它会刷两个槽、刷校验分区、清用户数据、读防回滚计数、最后把活动槽切到 a。这一步之后手机接近出厂状态。

**第 6 优先 — 完全进不了刷机模式**

这属于联发科预加载器级别的救砖，需要专用工具和额外授权，风险等级完全不同，本方案不展开；真到这一步应停下来单独评估。

**回退后复核**：能开机、当前槽、root 方案是哪一套、数据是否还在、校验值是否对得上，并写进结果记录。

## 13. 需要你拍板的三件事

### 13.1 到底要不要真的试刷

- **现在是什么情况**：镜像、内核、管理器安装包、回退剧本都已在电脑侧准备并核对完；手机一点没动，仍是稳定跑着的 Magisk Alpha；自编内核从未开机验证过。
- **不改会怎样**：最安全，但永远不知道这颗自编内核能不能开机、能不能提权。这两件事只能靠真机验证，电脑上再怎么查都推不出来。
- **有哪些选项、各做什么、代价是什么**：① 停在准备阶段，只做只读核对或文档整理，代价是结论永远悬着；② 先把关闭的可选隐藏特性恢复后重编、重新打包，代价是再过一遍编译关、再核一轮载荷，仍然不碰手机；③ 明确说「刷机」，按本方案一次性做完「刷当前槽 + 装管理器 + 验证 + 必要时回退」，代价是会写手机数据、有起不来的风险。
- **我的建议**：先停在 ①。拿一套稳定跑着的 root 方案去换一个还没验证能开机、隐藏能力还更弱的自编内核，收益不明显。若确实想试，先做 ②，再考虑 ③，且 ③ 一定要你单独明说。

### 13.2 校验分区用哪个策略

- **现在是什么情况**：自编镜像里保留的是原厂校验数据，换了内核之后哈希必然对不上；启动锁已解锁，正常情况下这个错误不致命。
- **不改会怎样**：默认方案 A 就是不改，最可能的结果是开机时闪一下校验提示然后正常进系统；小概率是卡在校验错误。
- **有哪些选项、各做什么、代价是什么**：方案 A 不动校验分区，少改一处、回退链最短，代价是要容忍可能的校验提示；方案 B 额外把「关闭校验」的镜像写进当前槽的校验分区，能压掉校验问题，代价是多改一个分区、之后必须对称刷回原厂那份，且不能碰另一槽。
- **我的建议**：用方案 A。只有在 A 明确因为校验起不来时，才升级到方案 B，并且同步安排对称刷回。

### 13.3 什么时候算授权

- **现在是什么情况**：用户已确立「明确说刷机之前手机只读」的最高优先边界，本方案只是纸面剧本。
- **不改会怎样**：一切照旧，手机不会被写。
- **有哪些选项、各做什么、代价是什么**：① 什么也不说，我继续只做电脑侧工作；② 只授权某一个具体动作（例如「允许把启动分区读回电脑」，这仍是从手机读、往电脑写），我可以只做那一件；③ 明确说「刷机」，我才按本方案从第 6 节往下走。
- **我的建议**：如果你只是想先把「精确复原备份」做出来（这件事不写手机、只是把手机上的分区读回电脑），可以单独点名授权 ②；这一步风险极低，却能把回退能力从「刷回无 root 原厂」提升到「精确回到现在的 Magisk 状态」。我不会把 ② 理解成 ③。
