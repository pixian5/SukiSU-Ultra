## 2. 环境要求（为什么非要这台云电脑）

| 条件 | 原因 |
|------|------|
| Linux x86_64 | 小米官方构建配置要求 Linux x86_64 的预编译编译器；本机 Mac 是 arm64 且 Docker 守护进程没开 |
| **区分大小写**的文件系统 | 内核源码里存在只差大小写的不同文件；本机 macOS 默认不区分，浅克隆后 12 个文件被标成「已修改」，那种检出只能读，不能编 |
| 约 40 GiB 可用空间 | 5.4 GB 线刷包 + 源码 + 编译输出；实测云电脑 40 GiB 够用 |
| 4 核 / 7.7 GiB 内存 | 实测 `-j4` 可以跑完，不会因内存不足被杀 |

云电脑实测：Ubuntu 24.04.5 LTS，Linux x86_64，`/workspace` 区分大小写。

## 3. 从零复跑（阶段 A → H）

以下命令按当时实操整理，全部在云电脑上执行，工作根目录统一为 `/workspace`。

### 阶段 A：装基础编译工具

```sh
sudo apt update
sudo apt install -y build-essential bc bison flex libssl-dev \
  device-tree-compiler ccache clang lld llvm \
  gcc-aarch64-linux-gnu python3 git wget ca-certificates cpio gzip
```

其中 `device-tree-compiler` 提供设备树编译器，`bison`/`flex` 供内核配置解析，`gcc-aarch64-linux-gnu` 提供交叉编译用的二进制工具，`lld` / `llvm` 提供链接器和 `llvm-nm` / `llvm-objcopy`。

### 阶段 B：取小米这颗量产内核用的官方编译器

`clang-r383902` **不是 Git 分支名**，是 AOSP 预编译编译器仓库里 `android11-release` 分支下的一个目录名。从归档接口下载：

```sh
mkdir -p /workspace/aosp/clang-r383902
cd /workspace/aosp
wget -O clang-r383902.tar.gz \
  'https://android.googlesource.com/platform/prebuilts/clang/host/linux-x86/+archive/refs/heads/android11-release/clang-r383902.tar.gz'
tar xzf clang-r383902.tar.gz -C clang-r383902
/workspace/aosp/clang-r383902/bin/clang --version
# Android (6443078 based on r383902) clang version 11.0.1
```

原厂 `boot.img` 里解出的内核版本串带的编译器信息，和这个是同一套，说明选对了。

### 阶段 C：检出源码（必须在区分大小写的目录里）

```sh
git clone --depth 1 --single-branch -b camellian-t-oss \
  https://github.com/MiCode/Xiaomi_Kernel_OpenSource.git \
  /workspace/camellian-kernel

git clone --depth 1 --single-branch -b builtin \
  https://github.com/SukiSU-Ultra/SukiSU-Ultra.git \
  /workspace/SukiSU-Ultra

cd /workspace/camellian-kernel && git rev-parse HEAD
# f4e416aea06c81f1e661d0524c0554f0538d11cb
```

> 小米按「机型 + 安卓大版本 + 区域」发布开源内核快照，**不提供某个 MIUI 小版本专属的源码**。`V14.0.4.0.TKSEUXM` 里的 `T` 是 Android 13、`EU` 是欧洲经济区，所以对应分支是 `camellian-t-oss`；`camellia-r-oss` 是 4G 版 / Android 11 的分支，别拿错。

### 阶段 D：展开配置并做 5 处必要适配

```sh
cd /workspace/camellian-kernel
make O=/workspace/out ARCH=arm64 CC=clang camellian_defconfig
# 再按 tools/camellian/config/key-config-options.txt 调整 .config 后执行
make O=/workspace/out ARCH=arm64 CC=clang olddefconfig
```

基础配置来自 `camellian_defconfig`（内部还会合并 `k6833v1_64_defconfig` 与区域差异片段 `camellian_in_eea_defconfig`）。**官方开源快照本身不自洽**，不改这 5 处编不过：

| # | 问题 | 处理 |
|---|------|------|
| 1 | 编译参数只放在环境变量时，被内核 Makefile 覆盖，出现 `WARNING: Disabling clang-specific options with gcc` | 把 `CC=clang`、`CLANG_TRIPLE`、`CROSS_COMPILE`、`LD=ld.lld`、`NM=llvm-nm`、`OBJCOPY=llvm-objcopy` **全部写在 `make` 命令行上** |
| 2 | `vendor/xiaomi/kernel_modules/mihw/millet/Makefile: No such file or directory` | 关掉 `CONFIG_MILLET`（私有模块目录不在开源快照里） |
| 3 | `camellian/cust.dtsi file not found` | 新增 `arch/arm64/boot/dts/camellian/cust.dtsi` 空占位文件（内容见 `tools/camellian/patches/cust.dtsi`）。这是原厂构建阶段生成的私有板级配置 |
| 4 | `stack frame size of 4176 bytes ... [-Werror,-Wframe-larger-than=]` | `CONFIG_FRAME_WARN=0` |
| 5 | 链接期三个未定义符号：`hq_regiser_hw_info`、`get_huaqin_pcba_config`、`get_audio_pa_vendor` | 这些实现本来就在 `drivers/misc/hqsysfs/`，只是开关被关了，改为 `CONFIG_HQ_SYSFS_SUPPORT=y` |

编译命令（已固化为 `tools/camellian/scripts/build.sh`）：

```sh
cd /workspace/camellian-kernel
export PATH=/workspace/aosp/clang-r383902/bin:$PATH
export LD_LIBRARY_PATH=/workspace/aosp/clang-r383902/lib64:${LD_LIBRARY_PATH:-}
make O=/workspace/out -j4 \
  ARCH=arm64 CC=clang CLANG_TRIPLE=aarch64-linux-gnu- CROSS_COMPILE=aarch64-linux-gnu- \
  LD=ld.lld NM=llvm-nm OBJCOPY=llvm-objcopy
```

原版试编成功的产物：`Image.gz-dtb` 11,573,496 字节，MD5 `a31bc208dc788336714202f78bed1174`。

### 阶段 E：集成 SukiSU-Ultra 的 `builtin` 分支

`builtin` 分支是给 5.10 以前的内核用的**手动挂钩**方案：项目自带的集成脚本只做软链接和构建系统两行引用，四处挂钩点要自己改内核源码。已固化为幂等脚本 `tools/camellian/scripts/integrate.py`（重复执行会打印 `[skip]` 而不是重复插入），完整改动也在 `tools/camellian/patches/kernel-tree.patch` 里。

```sh
python3 /workspace/integrate.py
# 等价的手工内容：
#   drivers/kernelsu -> /workspace/SukiSU-Ultra/kernel   （软链接）
#   drivers/Makefile 末行追加 obj-$(CONFIG_KSU) += kernelsu/
#   drivers/Kconfig  最后一个 endmenu 之前插入 source "drivers/kernelsu/Kconfig"
#   fs/exec.c        do_execveat_common 里调用 ksu_handle_execveat
#   fs/open.c        faccessat 里调用 ksu_handle_faccessat
#   fs/stat.c        vfs_statx 里调用 ksu_handle_stat
#   fs/read_write.c  vfs_read 里调用 ksu_handle_vfs_read
```

**不需要改** `kernel/sys.c` 的 `setresuid`（`builtin` 分支走 `security_add_hooks` / `task_fix_setuid`），也**不需要改** `init/main.c`（内核侧代码自带 `device_initcall(kernelsu_init)` 自动注册初始化）。

单编译单元提示：内核侧 `kernel/Makefile` 只编译 `ksu_main.c`，其它 `.c` 都是被它用 `#include "xxx.c"` 直接包进来的。所以单独编某个目标文件时会报 `No rule to make target ... ksu.o`，要编目录目标 `make ... drivers/kernelsu/`。

### 阶段 F：4.14 上的 5 类兼容补丁

完整改动见 `tools/camellian/patches/sukisu-kernel.patch`：

| # | 报错 | 处理 |
|---|------|------|
| 1 | 缺 `linux/static_call.h` | 这个机制 5.10 才引入；在 `kernel/kernel_includes.h` 里按 `LINUX_VERSION_CODE >= 5.10` 条件包含 |
| 2 | 缺 `vdso/datapage.h`、`vdso/clocksource.h` | 4.14 没有整套 vDSO 时钟类型；在 `kernel/extension/cpu_spoof.c` 里对 < 5.4 内核整体禁用该扩展，保留函数符号返回 `-EOPNOTSUPP` |
| 3 | `access_ok` 宏参数太少 | `kernel/extension/kpm/kpm.c` 里改用项目已有的兼容宏 `ksu_access_ok` |
| 4 | `implicit declaration of function 'kvcalloc'` | 4.14 有 `kvzalloc` 没有 `kvcalloc`；在 `kernel/kernel_compat.h` 补一个等价宏 |
| 5 | `implicit declaration of function 'susfs_parse_priority_app_strings'` | 全仓库没有这个符号的定义；`kernel/manager/pkg_observer.c` 里两处调用用 `#ifdef CONFIG_KSU_SUSFS` 包住 |

> 头文件静态扫描还报过 `crypto/sha2.h`、`linux/hex.h`、`uapi/linux/mount.h` 缺失，核对后确认项目本来就有版本分支（4.14 走 `crypto/sha.h` / 不引入 / `uapi/linux/fs.h`），**属于误报，不需要改**。

### 阶段 G：编译并做符号级核验

```sh
bash /workspace/build-ksu.sh      # 参数与 build.sh 相同，日志写到 /workspace/build-ksu.log
nm /workspace/out/vmlinux | grep -E ' (T|t) (kernelsu_init|ksu_handle_execveat|ksu_supercall_handle_ioctl)$'
```

集成版产物：`Image.gz` 11,495,575 字节 / MD5 `a9eb569a1780236e3ec0272b2d4b9fcb`；`Image.gz-dtb` 11,627,361 字节 / MD5 `a1b39daa9f7257e2d1b2f46ff37f6824`；`vmlinux` 298,014,656 字节 / MD5 `139759124dc8874658b314c9e796173e`。符号表里能读到 `kernelsu_init`、`ksu_handle_execveat`、`ksu_handle_faccessat`、`ksu_handle_stat`、`ksu_handle_vfs_read`、`ksu_supercall_handle_ioctl` 等，确认内核侧确实编进去了。

### 阶段 H：拿原厂基线，打包可刷镜像

```sh
bash /workspace/download-rom.sh           # 阿里云新加坡 OSS 的官方线刷包
md5sum /workspace/rom.tgz                 # af69a61f516331e275f8580ea53d662f
# 解出 images/boot.img 后：
python3 /workspace/pack_boot.py           # 产出 dist/boot-sukisu-stockdtb.img，自带 12 项结构校验
python3 /workspace/make_vbmeta_disabled.py   # 产出可选兜底件
```

官方线刷包（`.tgz`）而不是卡刷包（`.zip`）：线刷包直接含 `images/boot.img` 和全部分区镜像，是打包和救砖的基线；卡刷包通常是 `payload.bin`，还要额外解包。

打包原理、原厂启动镜像的精确布局、12 项校验结果见 [可刷启动镜像打包与结构校验](./20261106-2314-可刷启动镜像打包与结构校验-Claude-Opus-6.md)。

`tools/camellian/config/key-config-options.txt` 是最终 `.config` 里关键开关的摘录：

```

CONFIG_KSU_FEATURE_ADBROOT=y
# CONFIG_KSU_DEBUG is not set
# CONFIG_KPM is not set
# CONFIG_KSU_SUSFS is not set
CONFIG_HQ_SYSFS_SUPPORT=y
CONFIG_FRAME_WARN=0
# CONFIG_MILLET is not set
CONFIG_KPROBES=y
CONFIG_KALLSYMS_ALL=y
CONFIG_IKCONFIG_PROC=y
CONFIG_LTO_NONE=y
# CONFIG_LTO is not set
# CONFIG_LTO_CLANG is not set
```

对照从原厂 `boot.img` 里解出的量产配置：

## 6. 已知偏差与还没做完的事

5. **没有开机验证**：本轮不碰手机，「能开机 / 能提权 / 隐藏是否生效」全部未验证。
6. **校验哈希过期**：自编启动镜像里的 AVB 哈希对不上，依赖已解锁的启动锁容忍验证错误，没有实机验证。
7. **手机侧一切写操作都还没授权**：刷 `boot_b`、刷 `vbmeta_b`、切槽、全量恢复，都要单独明确授权。

## 7. 云电脑被回收之后怎么恢复

- 小文件（脚本、补丁、配置、校验值）**已经全部在本仓库 `tools/camellian/`**，跟着 git 走，不会丢。
- 大文件（5.4 GB 线刷包、源码树、编译输出、两个镜像产物）没有回传本机，也不适合进 git。它们可以**按本手册第 3 节从零重新生成**：线刷包用 `download-rom.sh` 里的链接重下（实测约 9.5 MB/s 起步，实际约 40 MB/s），源码按固定分支与提交重新浅克隆，编译器按阶段 B 重下，编译与打包按阶段 D–H 跑。
- 所有产物都有 MD5，重跑完逐项对一遍就能确认结果一致。
- 若要在本机重建，必须先解决「区分大小写文件系统」和「Linux x86_64 工具链」两个前提；本机 macOS 直接检出源码会导致只差大小写的文件互相覆盖。
