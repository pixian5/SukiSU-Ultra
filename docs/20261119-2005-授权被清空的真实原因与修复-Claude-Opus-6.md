# 授权过一会自己变回关闭：授权记录的包名是空的

- 时间：2026-11-19 20:05（GMT+8）
- 设备：Redmi Note 10 5G（M2103K19C / camellia），Android 13，自编内核 `#11`，管理器 `v4.3.0-r2`
- 用户现象：**「超级用户」列表里应用右侧的开关，「没重启、过一会就变回去」**
- 取证方式：用户临时给 Shell 授予 root 后，只读读取授权文件、租约目录与内核日志；**没有修改手机上的任何文件**

---

## 一、结论

不是临时租约，也不是写盘失败。**授权记录里的包名字段是空的**，而内核在清理授权时要求「uid 与包名同时匹配已安装应用清单」，空包名永远匹配不上，于是这条授权被当成「应用已不存在」删掉。

触发时机：**每次安装 / 更新 / 卸载应用**，系统都会重写 `/data/system/packages.list`，内核监听这个文件的变化并执行清理。你授权的 `com.rosan.installer.x`（InstallerX）本身就是安装器——用它装一个应用，它自己的 root 授权就被清掉了。

---

## 二、实测证据

### 授权文件里两条记录的包名都是空的

`/data/adb/ksu/.allowlist`，1576 字节，文件头 `55 53 4b 7f`（magic）、版本 4，后面是两条 784 字节的授权记录：

| 记录 | curr_uid | key（包名） | allow_su |
| --- | --- | --- | --- |
| 第 1 条 | 10800 | **全零（空字符串）** | 1 |
| 第 2 条 | 2000（Shell） | **全零（空字符串）** | 1 |

`/data/system/packages.list` 里：`com.rosan.installer.x 10800 ...` —— 也就是说，uid 10800 的应用包名是 `com.rosan.installer.x`，但授权记录里是空的。

### 内核清理要求包名逐字符匹配

`ksu_prune_allowlist()` → `is_uid_exist()`：

```c
if (np->uid == uid % PER_USER_RANGE &&
    strncmp(np->package, package, KSU_MAX_PACKAGE_NAME) == 0)
```

`package` 就是授权记录里的 `key`。空字符串与 `com.rosan.installer.x` 比较必然不等 → 判定「应用不存在」→ 删除授权，并立即写盘（`modified = true` → `ksu_persistent_allow_list()`）。

### 触发点：监听 packages.list

`kernel/manager/pkg_observer.c` 用文件系统通知监听 `packages.list` 的创建/重命名事件，一旦变化就 `track_throne(false)` → `prune`。这解释了「没重启、过一会就变回去」：只要装/更新/卸载应用就会触发。

---

## 三、空包名是怎么来的（这是 11 月 7 日修复引入的回归）

链路：

1. 管理器打开某个**从未授权过**的应用详情页，调用 `Natives.getAppProfile(packageName, uid)`；
2. JNI 层先用自己的包名填好 `profile.key`，再调内核读配置；
3. 内核对「没有配置的 uid」返回一份默认配置（这是 11 月 7 日修的「默认 app profile」，避免管理器报「更新 app profile 失败」）；
4. **那份默认配置是 `memset(0)` 出来的，只有 version / curr_uid / allow_su / nrp_config，没有包名**；
5. JNI 把内核返回的结构整体拷回，`profile.key` 被覆盖成空字符串，管理器拿到的 `name` 就是空的；
6. 用户打开开关保存，管理器把空包名原样写回内核 → `.allowlist` 里就是空 key。

11 月 7 日验证时只确认了「授权成功、管理器显示工作中」，**没有验证清理发生之后授权是否还在**，所以这个回归一直没暴露。

## 四、修复（已改代码）

### 1. 管理器 JNI 补回包名

`manager/app/src/main/cpp/jni.cc`：

```cpp
bool useDefaultProfile = get_app_profile(&profile) != 0;

// 内核返回的默认配置不带包名，用调用者传入的包名补回去，
// 否则管理器会把空包名写回内核，后续按包名清理时被误删。
if (profile.key[0] == '\0' && key[0] != '\0') {
    strcpy(profile.key, key);
}
```

### 2. 内核清理时跳过空包名（防御旧数据）

`kernel/policy/allowlist.c` 的 `ksu_prune_allowlist()`：

```c
// 空包名记录无法与已安装应用清单匹配，跳过而不是删除，
// 避免旧版管理器写入的空包名授权被误删。
if (np->profile.key[0] == '\0') {
    continue;
}
```

### 3. 版本号

按「每轮改源码 +0.0.1」规则，`tools/camellian-susfs/VERSION` 由 `0.0.7` 升到 **`0.0.8`**。

## 五、生效条件与验证

- **管理器 JNI 的修改**需要重新构建管理器 APK 才生效；
- **内核的修改**需要重新编译内核并刷入才生效；
- 两者只要有一个生效，就不会再出现「授权被清」。最稳的是两个都上。

验证（不用你反复开关）：

1. 重编管理器后，在应用详情页重新开关一次授权；
2. 读 `.allowlist`，该 uid 的 `key` 应该变成 `com.rosan.installer.x` 而不是全零；
3. 用 InstallerX 安装任意一个应用，再看授权是否还在。

## 六、实际修复执行（2026-11-19 20:25，已生效，未刷机）

用户说「刷机」后，先确认了一件事：**这个修复不需要刷内核，也不需要重启**。

1. 备份原文件：`/data/adb/ksu/.allowlist` → `.allowlist.bak-20261119`（1576 字节，root:root 644）。
2. 读回本机确认两条记录的 `key` 都是空的。
3. 用 `ksud` 的配置接口一次性修正「内核内存 + 磁盘文件」：

```sh
/data/adb/ksud temporary-root apply 10509 permanent false '<json>'
```

`json` 的字段名必须是 camelCase（`currentUid` / `allowSu` / `rootUseDefault` / `nonRootUseDefault` / `umountModules`），否则会报 `missing field currentUid`。`permanent` 同时会清掉该 uid 的旧租约。

4. 验证结果：

- `od` 读 `.allowlist`：offset 12 起为 `com.rosan.installer.x`，文件仍是 1576 字节；
- `/data/adb/ksud temporary-root status 10800` 返回 **`permanent`**（不是 timed/boot）；
- 临时脚本已从 `/data/local/tmp` 删除。

**效果**：内核内存与磁盘上的这条授权都带上了正确包名，之后任何一次 `packages.list` 变化触发的清理都能匹配上，不会再被删掉。

**附带说明**：Shell（uid 2000）那条记录仍然是空包名，重启后会被清理掉——Shell 本来就没有包名，属于正常现象，不影响应用授权。

**代码层面的修复仍然保留**（JNI 补包名 + 内核跳过空包名，版本 0.0.8），等下次重编管理器或内核时一并生效，用来防止「首次授权又写出空包名」再次发生。
