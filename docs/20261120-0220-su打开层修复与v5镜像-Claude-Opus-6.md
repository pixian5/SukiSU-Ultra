# su 打开层修复与 v5 镜像（含对 v4 两处结论的更正）

时间：2026-11-20 02:20
设备：红米 Note 10 5G / POCO M3 Pro 5G（camellian，MT6833），Android 13，
      MIUI EEA V14.0.4.0.TKSEUXM，内核 4.14.186 非 GKI，当前槽 b
产物：`boot-sukisu-susfs-allowlist-fix-v5.img`（未刷机、未连手机、未发布 Release）

---

## 1. 结论先行

v4 之后用户提出两个质疑，逐条核实结果：

| 质疑 | 结论 |
|---|---|
| ① `ksu_ksud_binary_exists()` 可能在 shell/APP creds 下拿到 `-EACCES` | **不成立**。探测在 `escape_with_root_profile()` → `commit_creds()` 之后执行，且显式带 `CAP_DAC_READ_SEARCH` |
| ② v4 是否处理了 `/system/bin/su` 的 open 层 ENOENT | **没有处理**。4.14 的 `do_sys_open()` 之前没有任何 KSU 钩子，v4 与 v3 完全相同 |

另外**更正 v3 文档中的一个错误判断**：当时写「sus_path 只影响 readdir，不会让 open 返回 ENOENT」是错的。
本移植在 `fs/namei.c` 里挂了 17 处 `SUS_PATH → -ENOENT`，确实会拦 lookup。

---

## 2. 质疑①：探测的 creds 足够

`kernel/feature/sucompat.c` 两处调用都是**先提权、再探测**：

```c
/* ksu_sucompat_user_common()，约 287 行 */
ret = escape_with_root_profile();
if (!!ret)
    return ret;

// NOTE: we only check file existence, not exec success!
if (!ksu_ksud_binary_exists())
    goto no_ksud;
```

```c
/* ksu_handle_execveat_sucompat()，约 362 行 */
ret = escape_with_root_profile();
ksu_sulog_emit_pending(pending_root_execve, ret, GFP_KERNEL);
if (!!ret)
    return 0;

if (!ksu_ksud_binary_exists())
    goto no_ksud;
```

`kernel/policy/app_profile.c:107-206` 的 `escape_with_root_profile()`：

```c
cred->uid.val = profile->uid;   /* suid/euid/fsuid 同样置 0 */
cred->fsuid.val = profile->uid;
...
/* we need CAP_DAC_READ_SEARCH becuase `/data/adb/ksud` is not accessible for non root process */
u64 cap_for_ksud = profile->capabilities.effective | CAP_DAC_READ_SEARCH;
memcpy(&cred->cap_effective, &cap_for_ksud, sizeof(cred->cap_effective));
...
setup_selinux(profile->selinux_domain, cred);
commit_creds(cred);          /* ← 从这里开始当前进程就是 uid 0 + 该 capability */
```

所以 `/data/adb` 的 `0700 root:root` 对探测不构成障碍。v3 上「Shell 在超级用户列表里是 ROOT」
也反证了这一点（若 `-EACCES`，根本拿不到授权状态）。
**唯一残余风险**是 root profile 的 SELinux domain 若被改成受限域——默认配置不会，v5 未改动。

**此点无需修改代码。**

---

## 3. 质疑②：open 层确实没修，v5 补上

### 3.1 真实机制（三层拼出来的矛盾现象）

| 命令 | 命中的钩子 | 实际行为 |
|---|---|---|
| `ls -l /system/bin/su` | `ksu_handle_stat`（`fs/stat.c:198`） | 文件名被就地改写成 `/system/bin/sh`，显示的是 **sh 的大小** |
| `head -c 4 /system/bin/su` | 无（`do_sys_open` 里没有 KSU 钩子） | 按真实路径 lookup → 真实 su 不存在 → **ENOENT** |
| `su -c id` | `ksu_handle_execveat`（`fs/exec.c:1725`） | 改写目标；v3 探测 `kern_path("/data/adb/ksud", 0)` 不跟随符号链接，落进 `no_ksud` |

关键点：那个 **328384 字节不是 su，而是 `/system/bin/sh`**。stat 钩子把路径换掉了。
可以用 `stat -c %s /system/bin/sh` 验证——应等于 328384。

也就是说设备上**根本不存在真实 su 文件**（SukiSU 的设计前提），
所以 `open()` 必然 ENOENT，这个是「读文件异常」的根因，不是 sus_path。

### 3.2 关于 sus_path（更正 v3 的判断）

`fs/namei.c` 中的实例（`do_last`，约 3369 行）：

```c
if (dentry->d_inode) {
#ifdef CONFIG_KSU_SUSFS_SUS_PATH
    if (unlikely(dentry->d_inode->i_state & INODE_STATE_SUS_PATH) &&
        likely(current->susfs_task_state & TASK_STRUCT_NON_ROOT_USER_APP_PROC)) {
        dput(dentry);
        return -ENOENT;
    }
#endif
```

它**确实会拦 open**，但有前提 `TASK_STRUCT_NON_ROOT_USER_APP_PROC`。
该位只在 zygote `setresuid` 派生普通 APP 时设置（`kernel/hook/lsm_hook.c:33-80`）。
**adb shell(2000) 不带这个位**，所以 sus_path 对 shell 无效。
v3 上 shell 看到的 ENOENT 是 3.1 的 open 层缺口，不是 sus_path。

结论：v4 加的白名单是有价值的防御（防止管理器误配把 su 隐藏掉），
但它**不能解决 shell 读 su 的问题**——这一层 v4 确实没做。

### 3.3 v5 的修改

**改动 A：`fs/open.c` 的 `do_sys_open()` 增加 open 钩子**

```c
long do_sys_open(int dfd, const char __user *filename, int flags, umode_t mode)
{
	...
	if (fd)
		return fd;

#ifdef CONFIG_KSU
	ksu_handle_open(&dfd, &filename, &flags);
#endif

	tmp = getname(filename);
	...
```

**改动 B：`kernel/feature/sucompat.c` 实现 `ksu_handle_open()`**

```c
int ksu_handle_open(int *dfd, const char __user **filename_user, int *flags)
{
    if (!is_su_allowed(filename_user))
        return 0;

    if (flags && (*flags & (O_WRONLY | O_RDWR | O_CREAT | O_TRUNC)))
        return 0;

    ksu_sucompat_user_common(filename_user, "open", false);
    return 0;
}
```

两条约束：
1. `escalate = false`——open 只改路径不提权（stat/faccessat 同样如此）；
2. **只处理只读打开**。带写标志的 open 若被改写到 `/system/bin/sh` 会损坏系统 shell。

**改动 C：`fs/exec.c` 去掉重复的 `ksu_handle_execveat` 调用**

原文件同一处有两个 `#ifdef CONFIG_KSU` 块，钩子被调两次。第一次已把 `filename` 就地改写，
第二次会拿改写后的 `/data/adb/ksud` 或 `/system/bin/sh` 再跑一遍 su 匹配逻辑。虽因名字不匹配
通常无害，但属于确定性隐患，v5 合并为一次。

**改动 D：`fs/susfs.c` 白名单加固**

- 增加 `/system/system/bin/su`、`/system/system/xbin/su`、`/vendor/bin/su`
  （Android 上 `/system/bin` 是指向 `/system/system/bin` 的符号链接，两种写法都要拦）；
- 增加**目录**黑名单：`/system/bin`、`/system/xbin`、`/system/system/bin`、
  `/system/system/xbin`、`/sbin`、`/data/adb`、`/data/adb/ksu`、`/data/adb/ksu/bin`。
  隐藏这些目录等于连带隐藏整条提权链；
- 路径规范化：折叠重复斜杠、去掉 `./` 分量与结尾斜杠，防止 `//system//bin/su` 绕过；
- 含 `..` 分量或超长的路径一律拒绝（字符串层面无法可靠还原）。

## 6. 刷入后的验证顺序

```sh
# 1. 提权链路
su -c id                      # 应输出 uid=0(root)

# 2. 关键：open 层是否修好（v5 的核心）
head -c 4 /system/bin/su      # v3/v4 是 ENOENT；v5 应读到 ELF 头
cat /system/bin/su | wc -c    # 应等于 stat -c %s /system/bin/sh 的字节数
stat -c %s /system/bin/sh     # 对照：v3 上 ls 显示的 328384 应该就是它

# 3. 三条路径一致性
ls -l /system/bin/su
stat /system/bin/su
access /system/bin/su         # busybox 可用时

# 4. WiFi（v3 修复不能回退）
ls /sys/module | grep wlan_drv_gen4m
ip link | grep wlan0

# 5. 若仍异常
dmesg | grep -Ei "sucompat|su->|susfs|KernelSU" | tail -50
```

如果第 2 项仍然 ENOENT：说明问题不在 open 层，而在更底层的文件系统（例如该路径被 overlayfs
或某厂商 LSM 拦截）。届时需要 `ls -l /system/bin/su` 的真实 `inode` 与
`dmesg | grep ksu_handle_open` 的输出。

## 7. 仍未解决 / 已知风险

1. **未真机验证**。v5 的全部结论来自源码取证与反汇编，没有在设备上跑过。
2. `open` 钩子只覆盖 `do_sys_open`。若某进程用 `open_by_handle_at` 或直接走
   `filp_open`（内核态）读 su，仍然 ENOENT——这属于内核内部路径，正常用户态命令不会走到。
3. `susfs_add_open_redirect()` 只对 `current_uid() < 2000` 生效（`fs/namei.c:3835`），
   shell(2000) 不在范围内，因此它也不是本次问题的来源。
4. SuSFS 改了 `task_struct`(+16B) 与 `vfsmount`(+8B) 布局。ko 靠 CRC 放行能加载，
   但若厂商模块内联了偏移/尺寸仍可能错位。这条风险从 v3 起就存在，v5 无变化。
