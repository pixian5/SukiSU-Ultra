## 1. 结论先行

v4 之后用户提出两个质疑，逐条核实结果：

| 质疑 | 结论 |
|---|---|
| ① `ksu_ksud_binary_exists()` 可能在 shell/APP creds 下拿到 `-EACCES` | **不成立**。探测在 `escape_with_root_profile()` → `commit_creds()` 之后执行，且显式带 `CAP_DAC_READ_SEARCH` |
| ② v4 是否处理了 `/system/bin/su` 的 open 层 ENOENT | **没有处理**。4.14 的 `do_sys_open()` 之前没有任何 KSU 钩子，v4 与 v3 完全相同 |

另外**更正 v3 文档中的一个错误判断**：当时写「sus_path 只影响 readdir，不会让 open 返回 ENOENT」是错的。
本移植在 `fs/namei.c` 里挂了 17 处 `SUS_PATH → -ENOENT`，确实会拦 lookup。

## 2. 质疑①：探测的 creds 足够

`kernel/feature/sucompat.c` 两处调用都是**先提权、再探测**：

```c
/* ksu_sucompat_user_common()，约 287 行 */
ret = escape_with_root_profile();
if (!!ret)
    return ret;

// NOTE: we only check file existence, not exec success!
if (!ksu_ksud_binary_exists())
    goto no_ksud;
```

```c
/* ksu_handle_execveat_sucompat()，约 362 行 */
ret = escape_with_root_profile();
ksu_sulog_emit_pending(pending_root_execve, ret, GFP_KERNEL);
if (!!ret)
    return 0;

if (!ksu_ksud_binary_exists())
    goto no_ksud;
```

`kernel/policy/app_profile.c:107-206` 的 `escape_with_root_profile()`：

```c
cred->uid.val = profile->uid;   /* suid/euid/fsuid 同样置 0 */
cred->fsuid.val = profile->uid;
...
/* we need CAP_DAC_READ_SEARCH becuase `/data/adb/ksud` is not accessible for non root process */
u64 cap_for_ksud = profile->capabilities.effective | CAP_DAC_READ_SEARCH;
memcpy(&cred->cap_effective, &cap_for_ksud, sizeof(cred->cap_effective));
...
setup_selinux(profile->selinux_domain, cred);
commit_creds(cred);          /* ← 从这里开始当前进程就是 uid 0 + 该 capability */
```

所以 `/data/adb` 的 `0700 root:root` 对探测不构成障碍。v3 上「Shell 在超级用户列表里是 ROOT」
也反证了这一点（若 `-EACCES`，根本拿不到授权状态）。
**唯一残余风险**是 root profile 的 SELinux domain 若被改成受限域——默认配置不会，v5 未改动。

**此点无需修改代码。**

---

## 3. 质疑②：open 层确实没修，v5 补上

### 3.1 真实机制（三层拼出来的矛盾现象）

| 命令 | 命中的钩子 | 实际行为 |
|---|---|---|
| `ls -l /system/bin/su` | `ksu_handle_stat`（`fs/stat.c:198`） | 文件名被就地改写成 `/system/bin/sh`，显示的是 **sh 的大小** |
| `head -c 4 /system/bin/su` | 无（`do_sys_open` 里没有 KSU 钩子） | 按真实路径 lookup → 真实 su 不存在 → **ENOENT** |
| `su -c id` | `ksu_handle_execveat`（`fs/exec.c:1725`） | 改写目标；v3 探测 `kern_path("/data/adb/ksud", 0)` 不跟随符号链接，落进 `no_ksud` |

关键点：那个 **328384 字节不是 su，而是 `/system/bin/sh`**。stat 钩子把路径换掉了。
可以用 `stat -c %s /system/bin/sh` 验证——应等于 328384。

也就是说设备上**根本不存在真实 su 文件**（SukiSU 的设计前提），
所以 `open()` 必然 ENOENT，这个是「读文件异常」的根因，不是 sus_path。

### 3.2 关于 sus_path（更正 v3 的判断）

`fs/namei.c` 中的实例（`do_last`，约 3369 行）：

```c
if (dentry->d_inode) {
#ifdef CONFIG_KSU_SUSFS_SUS_PATH
    if (unlikely(dentry->d_inode->i_state & INODE_STATE_SUS_PATH) &&
        likely(current->susfs_task_state & TASK_STRUCT_NON_ROOT_USER_APP_PROC)) {
        dput(dentry);
        return -ENOENT;
    }
#endif
```

它**确实会拦 open**，但有前提 `TASK_STRUCT_NON_ROOT_USER_APP_PROC`。
该位只在 zygote `setresuid` 派生普通 APP 时设置（`kernel/hook/lsm_hook.c:33-80`）。
**adb shell(2000) 不带这个位**，所以 sus_path 对 shell 无效。
v3 上 shell 看到的 ENOENT 是 3.1 的 open 层缺口，不是 sus_path。

结论：v4 加的白名单是有价值的防御（防止管理器误配把 su 隐藏掉），
但它**不能解决 shell 读 su 的问题**——这一层 v4 确实没做。

### 3.3 v5 的修改

**改动 A：`fs/open.c` 的 `do_sys_open()` 增加 open 钩子**

```c
long do_sys_open(int dfd, const char __user *filename, int flags, umode_t mode)
{
	...
	if (fd)
		return fd;

#ifdef CONFIG_KSU
	ksu_handle_open(&dfd, &filename, &flags);
#endif

	tmp = getname(filename);
	...
```

**改动 B：`kernel/feature/sucompat.c` 实现 `ksu_handle_open()`**

```c
int ksu_handle_open(int *dfd, const char __user **filename_user, int *flags)
{
    if (!is_su_allowed(filename_user))
        return 0;

    if (flags && (*flags & (O_WRONLY | O_RDWR | O_CREAT | O_TRUNC)))
        return 0;

    ksu_sucompat_user_common(filename_user, "open", false);
    return 0;
}
```

两条约束：
1. `escalate = false`——open 只改路径不提权（stat/faccessat 同样如此）；
2. **只处理只读打开**。带写标志的 open 若被改写到 `/system/bin/sh` 会损坏系统 shell。

**改动 C：`fs/exec.c` 去掉重复的 `ksu_handle_execveat` 调用**

原文件同一处有两个 `#ifdef CONFIG_KSU` 块，钩子被调两次。第一次已把 `filename` 就地改写，
第二次会拿改写后的 `/data/adb/ksud` 或 `/system/bin/sh` 再跑一遍 su 匹配逻辑。虽因名字不匹配
通常无害，但属于确定性隐患，v5 合并为一次。

**改动 D：`fs/susfs.c` 白名单加固**

- 增加 `/system/system/bin/su`、`/system/system/xbin/su`、`/vendor/bin/su`
  （Android 上 `/system/bin` 是指向 `/system/system/bin` 的符号链接，两种写法都要拦）；
- 增加**目录**黑名单：`/system/bin`、`/system/xbin`、`/system/system/bin`、
  `/system/system/xbin`、`/sbin`、`/data/adb`、`/data/adb/ksu`、`/data/adb/ksu/bin`。
  隐藏这些目录等于连带隐藏整条提权链；
- 路径规范化：折叠重复斜杠、去掉 `./` 分量与结尾斜杠，防止 `//system//bin/su` 绕过；
- 含 `..` 分量或超长的路径一律拒绝（字符串层面无法可靠还原）。

## 7. 仍未解决 / 已知风险

1. **未真机验证**。v5 的全部结论来自源码取证与反汇编，没有在设备上跑过。
2. `open` 钩子只覆盖 `do_sys_open`。若某进程用 `open_by_handle_at` 或直接走
   `filp_open`（内核态）读 su，仍然 ENOENT——这属于内核内部路径，正常用户态命令不会走到。
3. `susfs_add_open_redirect()` 只对 `current_uid() < 2000` 生效（`fs/namei.c:3835`），
   shell(2000) 不在范围内，因此它也不是本次问题的来源。
4. SuSFS 改了 `task_struct`(+16B) 与 `vfsmount`(+8B) 布局。ko 靠 CRC 放行能加载，
   但若厂商模块内联了偏移/尺寸仍可能错位。这条风险从 v3 起就存在，v5 无变化。

## 9. 追加：build 号与符号可见性的核实（2026-11-20 03:20）

用户下载 S3 上 `ebf453f1…` 后提出两点。核实结果：**镜像没传错，符号也在**。

### 9.1 build 号为什么是 #7 而不是 #5

v4 是 `#4`（01:16:56）。v5 期间共链接了三次，每次 `make` 都会让
`out/.version` 加一，于是 v4 的 4 → 5、6、7：

| 次数 | 触发原因 |
|---|---|
| 5 | 首次带 open 钩子的完整编译 |
| 6 | 发现 `fs/exec.c` 里还残留一个重复 extern，删掉后重编 |
| 7 | 最终确认编译 |

镜像里的 `UTS_VERSION` 是 `#7 SMP PREEMPT Fri Nov 20 02:18:21 CST 2026`，
与 `out/include/generated/compile.h` 的 `version 7` 一致，**只有这一个版本串**。
所以 #7 是「同一份代码编了三次」的结果，不是三次不同的代码。

### 9.2 为什么 `/proc/kallsyms` 里没有 ksu_handle_open

`CONFIG_KSU_SUSFS_HIDE_KSU_SUSFS_SYMBOLS=y`，`kernel/kallsyms.c:651-662`：

```c
#else
	{
		if (strstr(iter->name, "ksu_") || !strncmp(iter->name, "susfs_", 6) || !strncmp(iter->name, "ksud", 4)) {
			return 0;
		}
		seq_printf(m, "%pK %c %s\n", (void *)iter->value, iter->type, iter->name);
	}
#endif
```

含 `ksu_` 的符号**一律不打印**。因此 `ksu_handle_open`、
`ksu_handle_umount`、`ksu_handle_stat`、`ksu_handle_faccessat`
在 `/proc/kallsyms` 里都看不到——这是 SuSFS 隐藏特性，属于预期行为。

用户提到「`ksu_handle_input` / `ksu_handle_umount` 都能找到」，实际是：

- `ksu_handle_input` **不是内核符号**。源码里 `ksud.c:629` 只是把字符串
  `"ksu_handle_input"` 赋给 `handle->name` 注册给 input 子系统，
  `ksu_handle_input_handle_event()` 本身是 `__maybe_unused` 的 dead code。
  `strings` 能扫到该字符串，`/proc/kallsyms` 里本来就没有。
- 若 `ksu_handle_umount` 确实出现在 `/proc/kallsyms`，说明当时读到的
  不是这份内核的输出（或读的是别的系统），因为按上面的过滤规则它同样会被隐藏。

### 9.3 ksu_handle_open 的权威地址

来自 `out/System.map` 与 `llvm-nm out/vmlinux`，两者一致：

```

ffffff8009075470 T ksu_handle_umount
ffffff80090755d8 T ksu_handle_faccessat
```

反汇编确认 `0xffffff800907583c` 是真实函数体（`sub sp, sp, #48` 开头），
`do_sys_open` 里 `bl <ksu_handle_open>` 位于 `bl <getname_flags>` 之前。

清单已随镜像上传：`cst:xbz/camellian/symbols-v5.txt`。

### 9.4 镜像一致性

## 10. 追加：v5 刷入后 su 仍失败的真因与 v6（2026-11-20 03:50）

v5 实测结果：`head -c 4 /system/bin/su` 已返回 `7f 45 4c 46`（open 钩子生效），
但 `su -c id` 仍报 `No such file or directory`，且 logcat 无任何 `su->ksud` / `su->sh`。
说明 **execve 分支没有走到 sucompat**。

### 10.1 先排除「去重删错调用点」

`fs/exec.c` 里钩子**仍在**，位于 `do_execveat_common()` 开头（L1719-1723），
且是函数内第一条 `bl`：

```
ffffff800843a33c: bl #12826948 <ksu_handle_execveat>
ffffff800843a37c: bl <unshare_files>
ffffff800843a3a0: bl <kmem_cache_alloc_trace>   ← 创建 bprm
```

位置正确：早于 `unshare_files` 与 bprm 创建，`filename` 还是原始值。

### 10.2 真因：`ksu_execveat_hook` 恒为 true，sucompat 被短路

`kernel/feature/sucompat.c` 原分派（上游 builtin 写法）：

```c
if (unlikely(ksu_execveat_hook)) {
    return ksu_handle_execveat_ksud(fd, filename_ptr, argv, envp, flags);
}
return ksu_handle_execveat_sucompat(fd, filename_ptr, argv, envp, flags);
```

`ksu_execveat_hook` 初值为 `true`（`.data` 中读出为 `0x01`），只在
`stop_execve_hook()` 里清零。而 `stop_execve_hook()` 的唯一调用点在
`ksu_handle_execveat_ksud()` 的 zygote 分支里，该分支在本构建中被
`KSU_COMPAT_USE_STATIC_KEY`（`kernel_compat.h:283` 定义）包成：

```c
#ifdef KSU_COMPAT_USE_STATIC_KEY
            static_branch_disable(&is_first_zygote);
#else
            first_zygote = false;
#endif
```

**没有调用 `stop_execve_hook()`**。于是 `ksu_execveat_hook` 永远是 `true`，
`ksu_handle_execveat()` 每次都在 ksud 分支 `return`，`ksu_handle_execveat_sucompat()`
一次都没执行过 —— 这就是 logcat 里没有任何 `su->` 日志的原因。

反汇编对照（同一地址，v5 vs v6）：

| 地址 | v5 | v6 |
|---|---|---|
| `...75d2c` | `cbnz w8, +0xf0` → ksud | 同 |
| `...75d38` | `bl <sucompat>` | 同 |
| `...75d78` | `bl <ksud>` | 同 |
| `...75d7c` | `b -64` → **跳过 sucompat，直接 ret** | `b -76` → **回到 0x5d30，继续走 sucompat** |

### 10.3 v6 的修复

只改一处分派，语义对齐上游 5.x 分支（那边同样是先调 ksud 钩子、再无条件调 sucompat）：

```c
if (unlikely(ksu_execveat_hook)) {
    (void)ksu_handle_execveat_ksud(fd, filename_ptr, argv, envp, flags);
}

return ksu_handle_execveat_sucompat(fd, filename_ptr, argv, envp, flags);
```

`ksu_handle_execveat_sucompat()` 第一件事就是 `memcmp(name, su_path)`，
非 su 路径立即返回 0，因此对普通 execve 的额外开销可忽略。

若为 `17ffffff`（`b #-64`）则是旧版 v5。

完整清单见 `cst:xbz/camellian/symbols-v6.txt` 与 `System.map-v6`。

### 10.6 刷入 v6 后预期

```sh
uname -v                      # #8 SMP PREEMPT Fri Nov 20 03:41:49 CST 2026
su -c id                      # uid=0(root)
dmesg | grep -E "su->ksud|su->sh"   # 应出现 "sys_execve su->ksud!" 之类
head -c 4 /system/bin/su      # 7f 45 4c 46（v5 已生效，v6 保持）
```

若 `su -c id` 仍失败但 dmesg 出现 `su->sh`，说明 `ksu_ksud_binary_exists()`
两个候选路径都不存在，需要检查 `/data/adb/ksud` 与 `/data/adb/ksu/bin/ksud` 的实际情况。
