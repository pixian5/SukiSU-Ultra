# SukiSU-Ultra 集成试编成功与 4.14 兼容适配

- 生成时间：2026-11-06 22:13
- 关联文档：[原版内核试编成功与工具链适配](./20261106-2201-原版内核试编成功与工具链适配-Claude-Opus-6.md)

## 0. 结论速览

**把 SukiSU-Ultra 接进这台手机的内核源码后，编译通过了。** `make` 返回 0，产出了带 root 方案的 `Image.gz-dtb`。核验不是只看返回码：最终内核里有 **347 个** SukiSU 符号，包含初始化入口和四个手动挂钩函数；`System.map`（内核符号地址表）里有 337 条对应记录；四个被修改的文件系统源码确实重新编译并链接进去了。

这回答了上一轮留下的问题：**这套 4.14 内核不仅能编原版，也能编进 SukiSU-Ultra 的 `builtin` 分支**。工具链、源码、集成三条路都验证通畅。

代价是在 4.14 老内核上补了 5 类兼容适配，并主动关闭了一批可选隐藏特性。详见第 3、4 节。

## 1. 这一轮的边界

**做了**：把项目 `builtin` 分支的内核侧代码接入云电脑上的官方内核源码、修改四个挂钩落点、补兼容适配、试编、核验产物、清理临时文件。

## 2. 集成方案

项目分支：`SukiSU-Ultra/SukiSU-Ultra` 的 `builtin` 分支，提交 `1cfa5734`（"Fix mount_hide crash and support pre-5.10 kernels"）。两个远端（个人分叉与上游）的该分支指向同一提交，与本机此前分析的版本一致。

项目自带的 `kernel/setup.sh` **只做三件事**：把 `kernel/` 目录软链接到目标内核的 `drivers/kernelsu`，在 `drivers/Makefile` 和 `drivers/Kconfig` 里加两行引用。**手动挂钩需要集成者自己改内核源码**，脚本不会代劳。本轮按脚本的思路手工完成，没有调用脚本（避免它自行 clone 上游仓库）。

内核侧是**单编译单元**：`kernel/Makefile` 只编 `ksu_main.c`，该文件用 `#include "xxx.c"` 把其余几十个 `.c` 文件全部包含进来。所以兼容适配都落在这一条编译链上。

### 内核源码树的改动（6 个文件，47 行）

| 文件 | 改动 |
| --- | --- |
| `drivers/Makefile` | 追加 `obj-$(CONFIG_KSU) += kernelsu/` |
| `drivers/Kconfig` | 在最后一个 `endmenu` 前追加 `source "drivers/kernelsu/Kconfig"` |
| `fs/exec.c` | 在 `do_execveat_common` 里调用 `ksu_handle_execveat`，接管执行程序请求 |
| `fs/open.c` | 在 `faccessat` 系统调用里调用 `ksu_handle_faccessat`，接管 su 访问探测 |
| `fs/stat.c` | 在 `vfs_statx` 里调用 `ksu_handle_stat`，接管 su 状态探测 |
| `fs/read_write.c` | 在 `vfs_read` 里调用 `ksu_handle_vfs_read`，安装配置读取钩子 |

四处插入都用 `#ifdef CONFIG_KSU` 包裹，并写了中文注释。`drivers/kernelsu` 是指向项目 `kernel/` 目录的软链接。

另外沿用上一轮的 `arch/arm64/boot/dts/camellian/cust.dtsi` 空占位文件（厂商构建时生成的板级配置，开源快照缺失）。

### 配置

```text
CONFIG_KSU=y
CONFIG_KSU_FEATURE_ADBROOT=y
# CONFIG_KSU_DEBUG is not set
# CONFIG_KPM is not set
# CONFIG_KSU_SUSFS is not set
```

`CONFIG_KSU` 在项目 `kernel/Kconfig` 里是布尔项、默认 `y`，帮助文本里"可编译为模块"是上游遗留的旧描述，实际不能设成 `m`。`CONFIG_KSU_SUSFS` 默认也是 `y`，但 4.14 上 `CONFIG_THREAD_INFO_IN_TASK=y` 让它会自动打开，而它会改变挂钩函数的参数类型，因此**必须显式关掉**，否则四处调用的类型全不匹配。

## 3. 4.14 上遇到的兼容障碍与修法

按实际发生顺序，共 5 类。所有改动都落在云电脑上的项目副本 `/workspace/SukiSU-Ultra/kernel/`，共 5 个文件、28 行，未提交回项目仓库。

### 障碍 1：缺 `linux/static_call.h`

`static_call`（静态调用，5.10 以后才引入的内核机制）在 `kernel_includes.h` 里被无条件包含，但全项目**没有任何一处实际使用**它。

修法：把这一行包进 `#if LINUX_VERSION_CODE >= KERNEL_VERSION(5, 10, 0)`。

### 障碍 2：缺 `vdso/datapage.h`、`vdso/clocksource.h` 及整套时钟类型

CPU 身份伪装扩展 `extension/cpu_spoof.c` 引用了新内核的 vDSO（虚拟动态共享对象，内核映射给用户态的时钟数据页）数据结构。4.14 只有 `struct vdso_data`，没有 `enum vdso_clock_mode`、`VDSO_CLOCKMODE_ARCHTIMER` 等定义，硬凑桩定义很脆弱。

修法：**在 4.14 上整体禁用 CPU 伪装扩展**，保留 `ksu_extension_cpu_spoof_io` 函数符号并返回 `-EOPNOTSUPP`，避免 `extension.c` 注册处理函数时链接断链。CPU 伪装是可选隐藏特性，不是提权核心。

### 障碍 3：`access_ok` 参数个数

4.14 的 `access_ok(type, addr, size)` 是三参数，新内核是两参数。项目 `kernel_compat.h` **本来就有** `ksu_access_ok` 兼容宏处理这个差异，只是 `extension/kpm/kpm.c` 那一处漏用、直接调了 `access_ok`，报"宏参数太少"。

修法：改成调用项目自己的 `ksu_access_ok`。

### 障碍 4：缺 `kvcalloc`

`supercall/dispatch.c` 用了 `kvcalloc`（4.18 才引入）。4.14 里其实已有 `kvmalloc`、`kvzalloc`、`kvmalloc_array`、`kvfree`，只缺这一个。

修法：在 `kernel_compat.h` 里补一行等价宏 `#define kvcalloc(n, size, flags) kvzalloc((n) * (size), (flags))`。

### 障碍 5：悬空调用 `susfs_parse_priority_app_strings`

`manager/pkg_observer.c` 两处调用这个函数，但**整个仓库里找不到它的定义**（隐藏特性关闭时没有实现），被 `-Werror` 判为隐式声明错误。

修法：两处调用用 `#ifdef CONFIG_KSU_SUSFS` 包住。

### 一处"看起来是坑、其实不是"

静态扫描项目引用的 157 个系统头文件时，`crypto/sha2.h`、`linux/hex.h`、`uapi/linux/mount.h` 也报"4.14 不存在"，但回看 `kernel_includes.h` 会发现这三处**项目本来就有内核版本条件分支**（4.14 分别走 `crypto/sha.h`、不引入、`uapi/linux/fs.h`），无需改动。记录在这里，避免以后重复排查。

## 4. 主动关闭的功能（必须如实记录）

为了把"能不能编通"这个问题和"每个隐藏特性都能用"分开，这一轮刻意做了取舍：

| 项目 | 状态 | 原因 |
| --- | --- | --- |
| SuSFS 隐藏套件 | 配置关闭 | 默认开启，会改变挂钩函数签名，且需要额外内核补丁 |
| KPM | 配置关闭 | 项目默认即关闭 |
| 调试模式 | 配置关闭 | 项目默认即关闭 |
| CPU 身份伪装扩展 | 代码层禁用 | 4.14 缺 vDSO 时钟类型，见障碍 2 |
| preinit 运行器 | 被构建系统自动禁用 | 编译输出目录里没有 `usr/include`，项目 Makefile 自动加 `-DKSU_NO_PREINIT` |

**所以这一轮验证的是「核心提权链路能否编译」，不是「全部隐藏特性能否在 4.14 上工作」。** 要恢复这些特性，需要逐个再做内核适配，工作量另算。

## 5. 产物核验

编译返回码 `build-ksu.rc = 0`。产物在云电脑 `/workspace/out/`：

| 文件 | 大小 | 校验值（MD5） |
| --- | --- | --- |
| `arch/arm64/boot/Image.gz-dtb` | 11,627,361 字节（12 MB） | `a1b39daa9f7257e2d1b2f46ff37f6824` |

与原版产物（11,573,496 字节）相比增大 **53,865 字节**，增量合理。

关键证据：

- 未压缩内核里的 SukiSU 符号共 **347 个**，其中：

```text
kernelsu_init                      初始化入口
__initcall_kernelsu_init6          已注册为设备初始化调用
ksu_handle_execveat               执行程序挂钩
ksu_handle_execveat_ksud          ksud 重定向
ksu_handle_execveat_sucompat      su 兼容处理
ksu_handle_faccessat              访问探测挂钩
ksu_handle_stat                   状态探测挂钩
ksu_handle_vfs_read               读取挂钩
ksu_supercall_handle_ioctl        特权调用入口
```

- `System.map` 里 337 条对应记录，说明符号不是只在目标文件里，而是真正链进了最终内核。
- 构建日志确认四个文件系统目标文件都重新编译：`fs/open.o`、`fs/read_write.o`、`fs/stat.o`、`fs/exec.o`。
- 内核版本串 `4.14.186-perf-gf4e416aea-dirty`，末尾 `-dirty` 表示源码树有未提交改动，符合预期。
- 编译器仍是官方 clang 11.0.1（r383902）＋ LLD 11.0.1。

## 6. 这个产物仍然绝对不能刷进手机

上一轮列的理由全部成立：设备树里厂商私有板级配置是空占位、私有模块被关掉、配置与量产内核不同、没有原厂启动内存盘（ramdisk），因此还没法打包成手机能用的启动分区镜像。

本轮又新增几条：

- 一批可选隐藏特性被关闭或禁用，功能不完整。
- **编译通过不等于运行时可用**：四个手动挂钩是否真的在 4.14 上被正确触发、初始化顺序是否正确、LSM（Linux 安全模块）钩子注册是否生效，这些只能通过刷入真机验证，而刷机需要用户明确点头，本轮没做。

它只证明「这条路能编通」，不是可交付固件。

## 9. 下一步需要拍板的事

现在的状态：**环境通、源码通、原版能编、集成版也能编**；手机仍是原有 Magisk Alpha；云电脑上有一份带 SukiSU 的编译产物，但没有可刷的启动分区镜像，也没有做过任何实机验证。

三个方向：

- **A：准备可刷镜像的材料。** 拿到原厂 `boot.img` 作为基线——从第三方镜像下载 5.4 GB 固件包并校验，或者（需要你明确授权动手机）直接从这台已 root 的手机导出当前启动分区。有了基线才能把自编内核连同原厂内存盘打包成可刷镜像。仍然可以不刷。
- **B：恢复被关闭的可选特性。** 逐个把 SuSFS 隐藏套件、CPU 伪装、preinit 等在 4.14 上适配回来。代价是还要处理一批内核接口差异，且部分特性可能根本无法在 4.14 上完整实现。
- **C：先做风险评估与方案对照。** 把「换成 SukiSU-Ultra 相对现有 Magisk Alpha 的得失、刷机风险、变砖后的恢复办法、数据备份清单」整理成完整文档，再决定要不要继续投入。

**推荐先做 C，同时并行准备 A 的材料。** 理由：编译可行性这条线已经彻底验证完，继续往前每一个动作的成本都在上升，尤其"刷入真机"是不可逆风险；先把风险和回退路径讲清楚，再决定是否真的要换，比继续闷头适配更划算。而 A 只是取材料、不刷机，可以顺手做掉，不影响决策。

无论选哪个，**刷入手机这一步都需要你单独明确授权**，我不会自行执行。
