## 一、中途出现的关键变化：另一台云电脑也发布了 v0.0.6

本轮开工时，仓库里最新的还是 v0.0.5。我们在云电脑上改源码、重编译的过程中，**另一台并行工作的云电脑按上一轮「阶段 1 建议」先发布了 `camellian-susfs-v0.0.6`**（提交 `62624b44`、`9b9461b9`，发布说明写于 04:29）。

它的做法是在 **SuSFS 接口层**把四条没有实现的命令写回 `err = -EOPNOTSUPP`（-95），让管理器明确报错；并解释了为什么不能用 126（`ERR_CMD_NOT_SUPPORTED` 会被后台程序当成「可忽略」而静默放行，等于换一种形式的假支持）。**这个实现比我们在命令分发处直接返回错误码更贴合用户态协议**：分发处返回非 0 会让重启系统调用落到原生路径，用户态收到的不是协议里约定的错误码。

因此做了明确取舍：

- **主线 = 对方发布的 v0.0.6**（接口层拒绝，协议正确，校验值 MD5 `3248b6a178b2aa91e423d95feab292ad`、SHA256 `02d4aecb764d798987ae680daa5274c400f3c504fb8451458e3bb749a4438fd3`）。
- **我们这份重编译产物 = 实验变体**，只用于验证「关掉全量符号暴露开关后能否正常编译」，**不作为刷机候选、不发布正式版本**。它的源码差异单独存档在 `tools/camellian-susfs/patches/experimental-kallsyms-off/`，不覆盖主线源码。
- 仓库里 `tools/camellian-susfs/kernel/fs/susfs_abi.c` 已恢复为对方的修复版本，避免把别人的正确修复冲掉。

v0.0.5（vanilla 1.4.2 核心 + 自写兼容层）的源码仍只留在另一台云电脑、从未提交，本轮无法对它做修改或复现，降级为「仅存档、不作为主线」。

配置都是从镜像内核里的 `ikconfig` 直接提取的，不是看文件名或发布说明推断的。**同一个版本号的镜像也可能来自不同机器、不同配置**，所以校验值是唯一身份。

同名对象 `camellian/boot-sukisu-susfs-lto-stockdtb.img` 在 03:56 与 04:12 至少被覆盖两次（MD5 `384c0248...` 与 `a5fa0ef3...`），两份都已归档到 `cst:xbz/camellian/archive/` 留证。现在该同名对象已被主线镜像覆盖（MD5 `3248b6a1...`），但**仍然不建议按固定名字取镜像**：正确做法是发布页资产 + 校验值，或 `releases/v0.0.6/boot-sukisu-susfs-v0.0.6-3248b6a1.img` 这种带校验值的路径。

## 四、实验变体的编译

- 云电脑：`/workspace/camellian-kernel`（厂商 4.14 源码）+ `/workspace/SukiSU-Ultra` + `/workspace/out`（独立构建目录），AOSP clang 11.0.1（r383902），量产 LTO/CFI 保留。
- 实验变量：`CONFIG_KALLSYMS_ALL=n`；四条命令在分发处返回「不支持」；开机日志加 `susfs: camellian build 0.0.6, honest feature set`。
- 两处让 root 授权能工作的修复（重启系统调用的通道钩子、读应用配置时返回默认档）在源码里复核在位。
- 打包沿用原厂启动镜像的内存盘、设备树、校验区段，AVB 尾部重定位；vbmeta 内哈希仍无法用厂商私钥重签。

**编译结果：成功**（`make` 返回 0、日志零报错），全量重编走完 LTO/CFI 全程序优化、模块检查与最终链接约 35 分钟。内核压缩后 13,512,508 字节、解压后 37,011,456 字节，比主线内核小；从镜像内核里提取的编译配置确认 `CONFIG_KALLSYMS_ALL is not set` 已生效，开机标记与 `susfs is initialized! version: v2.3.0` 都在。这说明「符号隐藏不依赖全量符号开关」的判断在编译层面成立，但**仍然不等于真机可用**。

打包用原厂内存盘 / 设备树 / 校验区段，12 项结构校验全通过：

```
文件   /workspace/dist/boot-sukisu-susfs-experimental.img（仅存于云电脑）
大小   67,108,864
MD5    5526db7c1e146e44c98109c5fcbf44af
SHA256 4f137e4d23d7463373f308bf2a08d63abc590b1b6f18b06acb12fdf3e9040a99
```

**产物处理**：不发布 Release、不占用版本号、不刷入手机，也没有回传本机（64 MB 上传到对象存储过慢，对不刷机的对照件没有必要）。镜像只留在云电脑 `/workspace/dist/` 作对照，校验值记在 `backup/camellian/IMAGE-VERSIONS.txt` 与 `SOURCES.txt`；**主线始终是另一台云电脑发布的 v0.0.6**。云电脑上的临时凭证文件与收尾脚本已删除。

## 六、刷机前的判据（**本轮不执行**）

1. 以 `camellian-susfs-v0.0.6` 发布页资产为准，先核对 SHA256；
2. 能开机、无重启循环，超过 3 分钟无反应视为失败；
3. 管理器显示「工作中」，后台有以 root 运行的子进程；
4. 内核日志出现 `susfs is initialized! version: v2.3.0`；
5. 管理器特性列表里看不到 `CONFIG_KSU_SUSFS_SUS_MAP`；
6. 尝试四条不支持的命令时应明确报错，而不是显示成功；
7. 用 Momo 复测隐藏效果并逐项记录；
8. **不要用 `adb shell su` 判断成败**（调试模式关闭时本来就不能提权）。

回退件 `boot_b-before.img`（MD5 `531c534bcc8d3172e03b12a2f6dd135d`）与同代干净原厂 `boot-stock.img` 都在 `backup/camellian/`。任何写入手机的动作仍需用户明确说「刷机」。
