## 一、克隆结果，以及一个必须记住的环境结论

```
仓库：MiCode/Xiaomi_Kernel_OpenSource
分支：camellian-t-oss（单分支、只取最后一次提交）
提交：f4e416aea Kernel: Xiaomi kernel changes for POCO M3 Pro 5G / Redmi Note 10 5G / Redmi Note 10T Android T
文件：78342 个，占用 1.4 GB
版本：Makefile 里 VERSION=4 / PATCHLEVEL=14 / SUBLEVEL=186
```

**克隆时出现了一个不能忽略的警告**：macOS 默认文件系统不区分大小写，而 Linux 内核源码里存在一批「只差大小写」的文件，例如 `xt_CONNMARK.h` 与 `xt_connmark.h`、`net/netfilter/xt_DSCP.c` 与 `xt_dscp.c`。检出时每一组只保留了一个，另一个的内容被覆盖，`git status` 显示 **12 个文件被标成已修改**（全在网络过滤子系统里）。

结论要分两半说：

- **做静态核对没问题**：读版本、读配置、定位函数与行号，这些都不受那 12 个网络过滤文件影响。
- **这份检出不能拿来编译**：文件系统层面的内容已经不一致，编译内核会出错或产出错误结果。真要编译，必须在**区分大小写**的文件系统上重新检出——Linux 机器，或 macOS 上单独建一个区分大小写的 APFS 卷/磁盘映像。这给上一份文档「本机编不了」又添了一条具体原因。

## 二、配置差异查到了哪一步

### 2.1 实际读到的配置

| 配置文件 | 行数 | 运行时挂钩 `CONFIG_KPROBES` | 符号全量表 `CONFIG_KALLSYMS_ALL` |
| --- | ---: | --- | --- |
| `camellian_defconfig` | 493 | `=y` | `=y` |
| `k6833v1_64_defconfig`（芯片平台基础） | 450 | `=y` | `=y` |
| `camellian_in_eea_defconfig`（欧洲区域片段） | 505 | 不含 | 不含 |
| `camellian_gl_defconfig`（全球区域片段） | 505 | 不含 | 不含 |

区域文件是**差异片段**（开头是交叉编译器前缀、版本串后缀、内核命令行等），不含这两项；联发科平台把「基础配置 + 区域片段」合并成最终配置。`arch/arm64/Makefile` 里只有标准的 `KBUILD_DEFCONFIG := defconfig`，具体选哪几份由外部构建流程决定，源码树本身看不出来。

### 2.2 与实机的矛盾仍在

手机里读到的实际内核是 `# CONFIG_KPROBES is not set` 与 `# CONFIG_KALLSYMS_ALL is not set`，而开源基础配置两项都是开的。**这说明量产固件的配置与开源快照的默认配置不是同一套**，不能凭配置文件名推断。要把这个悬着的问题彻底查实，仍需要下载官方线刷包、解出里面的启动镜像，用内核源码自带的 `extract-ikconfig` 提取量产配置后逐项比对——本轮按约定没有下载那 5.4 GB 的包。

有一个**待验证的推测**：如果按开源基础配置重新编译，运行时挂钩和符号全量表很可能是开启的，那样项目的常规分支（自动挂钩）也许就能用，不必手动改源码。但这是推测，只有真正编出内核并核对生成的配置才能确认，所以下面仍然把手动挂钩清单列全。

### 2.3 修正上一份文档的一处细节

上一轮引用的是 `build.config.common`（安卓开源项目的通用配置，工具链路径写作 `prebuilts-master/clang/...`）。这次在源码里看到，**这台联发科机型实际对应的是 `build.config.mtk.aarch64`**：

## 三、手动挂钩到底要改哪些文件（本轮核心产出）

### 3.1 先说清项目那边的机制

查的是本仓库分叉里的 `origin/builtin` 分支（专门给 5.10 以前内核的手动挂钩分支）：

- 全分支**没有任何运行时挂钩注册代码**（搜不到 kprobe、kretprobe、tracepoint 注册），确实是纯手动挂钩；
- 内核侧初始化由 `device_initcall(kernelsu_init)` 自动执行，**不需要改 `init/main.c`**；
- 切换用户身份与卸载模块的处理走**安全模块钩子**（`security_add_hooks` + `LSM_HOOK_INIT(task_fix_setuid, ...)`），所以**不需要改 `kernel/sys.c` 里的 `setresuid`**；
- 初始化里有一句条件编译：`#if LINUX_VERSION_CODE >= KERNEL_VERSION(5, 10, 0)` 才调用 SELinux 隐藏初始化，也就是说**在 4.14 上部分隐藏功能会被跳过**。这与该分支最近一次提交「support pre-5.10 kernels」的说法一致。

### 3.2 需要动手改的内核源码文件（行号为 4.14.186 实际位置）

| 内核文件 | 函数 / 行号 | 对应项目的入口函数 | 说明 |
| --- | --- | --- | --- |
| `fs/exec.c` | `do_execveat_common`，第 1699 行 | `ksu_handle_execveat_ksud`、`ksu_handle_execveat_sucompat` | 签名 `(int fd, struct filename *filename, struct user_arg_ptr argv, struct user_arg_ptr envp, int flags)`，与项目头文件里的参数类型对得上，是**最匹配的一个挂钩点** |
| `fs/open.c` | `SYSCALL_DEFINE3(faccessat, ...)`，第 362 行 | `ksu_handle_faccessat` | **4.14 里没有独立的 `do_faccessat` 函数**，`faccessat` 系统调用本体直接实现；上游旧指南写的是改 `do_faccessat`，照抄会找不到位置 |
| `fs/stat.c` | `vfs_statx`，第 166 行 | `ksu_handle_stat` | 签名 `(int dfd, const char __user *filename, int flags, struct kstat *stat, u32 request_mask)`；另有 `vfs_fstatat` 路径（第 364 行被调用）需一并考虑 |
| `fs/read_write.c` | `vfs_read`，第 432 行 | `ksu_handle_vfs_read` | 签名 `(struct file *file, char __user *buf, size_t count, loff_t *pos)`，与项目入口的地址型参数对应 |

另外 `kernel/reboot.c:280` 有 `SYSCALL_DEFINE4(reboot, ...)`、`kernel/sys.c:601` 有 `SYSCALL_DEFINE3(setresuid, ...)`，但在当前 `builtin` 分支里**没有找到需要由这两处调用的入口声明**，初步判断不必改；这一条标注为「待编译前复核」，不要当成已确定。

### 3.3 两个很容易踩的坑

**坑一：条件编译会改变函数签名。** `kernel/feature/sucompat.h` 里，开启隐藏补丁支持（`CONFIG_KSU_SUSFS`）时，`ksu_handle_faccessat`、`ksu_handle_stat`、`ksu_handle_execveat_sucompat` 的文件名参数从 `const char __user **` 变成 `struct filename **`；而 `ksu_handle_execve_sucompat` 只在**未开启**该选项时存在。手动加的调用代码必须用同样的条件判断包住，否则编译直接报类型不兼容。

**坑二：安全钩子接口有版本差异。** 这份 4.14 源码里 `security_add_hooks` 是三参数（钩子数组、数量、模块名），项目分支里同时写了三参数和两参数两种调用并用条件编译隔开。集成时要确认在 4.14 下选中的是三参数那一支。

### 3.4 集成脚本会改动哪些地方

`kernel/setup.sh`（在主分支和手动挂钩分支内容完全相同，靠调用参数区分）会做四件事：把项目仓库克隆到内核源码树的 `KernelSU/` 目录、在 `drivers/` 下建名为 `kernelsu` 的软链、在 `drivers/Makefile` 追加 `obj-$(CONFIG_KSU) += kernelsu/`、在 `drivers/Kconfig` 追加 `source "drivers/kernelsu/Kconfig"`。调用时传 `builtin` 才会切到手动挂钩那套代码。

因为内核源码要直接调用项目里的函数，这里必须把 `CONFIG_KSU` 设成 `y`（编进内核本体），不能设成 `m`（编成可加载模块）。

## 五、结论与下一步

**查清了两件事**：一是源码与实机的配置差异确实存在、且开源基础配置里运行时挂钩是开的，「必须手动挂钩」这个结论只在「沿用量产配置」的前提下成立，按开源配置重编有可能翻盘（待编译验证）；二是手动挂钩的实际落点已经具体到文件和行号，共 4 个主要源码文件，且确认不需要改启动初始化和用户身份相关的文件。

**又发现一个新的硬限制**：这份检出在 macOS 上因大小写冲突不完整，静态核对够用，编译必须换到区分大小写的文件系统。

剩下的选项（都仍不动手机）：

1. **到此为止**：信息已经够判断这条路值不值得走。
2. **下载官方线刷包，做配置比对的最后一环**：5.4 GB 下载，解出启动镜像提取量产配置，彻底确认 KPROBES 与符号全量表的真实状态。零设备风险。
3. **搭 Linux x86_64 环境，在区分大小写的卷上重新检出并试编一份未改动的原版内核**：成本最高，但能验证「能不能编出能开机的内核」，也是真正动手前必须过的一关。

推荐顺序：若只是想判断可行性，第 2 项把最后一个不确定点消掉就够了；只有确定要真的换 SukiSU，才值得投入第 3 项。

## 七、术语表

| 名词 | 含义 |
| --- | --- |
| 浅克隆 | 只下载某个分支最新一次提交的代码，省去历史记录 |
| 大小写敏感文件系统 | 能区分 `xt_DSCP.c` 和 `xt_dscp.c` 是两个不同文件的文件系统；Linux 默认如此，macOS 默认不区分 |
| 内核配置 / defconfig | 编译时决定哪些功能开启的配置文件；联发科平台常把基础配置与各区域差异片段合并使用 |
| 运行时挂钩 / 手动挂钩 | 在内核函数执行时插入代码：前者开机后动态注册，后者要改内核源码 |
| 符号全量表 | 内核里所有函数与变量地址的完整清单，某些补丁方案依赖它 |
| 安全模块钩子 | Linux 内核提供的一组回调接口，项目用它接管用户身份切换等事件，避免改内核核心代码 |
| 初始化调用 | 内核启动时按固定顺序执行的一段初始化代码，编进内核后自动运行 |
| 条件编译 | 同一份代码按配置开关或内核版本选择不同实现，签名也可能随之改变 |
| 系统调用 | 应用程序请求内核办事的入口，例如检查文件权限、执行程序、读取文件 |
| 启动镜像 / boot 镜像 | 开机时加载内核与初始系统的镜像，root 方案都改它 |
| 交叉编译工具链 | 在一种机器上生成另一种机器能运行的程序的编译器套装 |
