## 0. 一句话结论

回退件现在齐了：当前槽那份「带 Magisk（面具）的启动分区」已经被逐字节、经三重验证地读回电脑，将来授权试刷后如果开不了机，就具备「精确复原到刷机前状态」的能力。过程中发现并修掉了一个很隐蔽的坑——**这台设备的 USB 调试原始输出通道会把二进制里的换行字节改写**，直接读出来的备份是坏的。刷机剧本里原来那条备份命令因此被更正。

## 1. 先说清楚几个词

- **启动分区镜像**：手机开机时先加载的一小块分区内容，里面是内核和开机临时系统（内存盘）。改它等于改开机第一段代码。
- **当前槽 / 另一槽**：这台手机有两份物理启动分区，当前用的是 b 槽；试刷只写 b 槽，a 槽原样留着。
- **校验分区**：开机时用来核对各分区有没有被改过的一组小分区。默认不动它；动过就必须对称刷回。
- **设备树叠加分区**：告诉内核这块板子上有哪些硬件的一小段数据，随启动分区一起用。
- **只读备份**：通过 USB 调试，把手机上已有的分区内容**读**到电脑存成文件。不往手机写任何东西，也不需要重启或进刷机模式。
- **刷机模式**：开机前的一个底层维护界面，可以**写**分区。本轮没有进，也不允许为了备份而进。

## 3. 排查出来的坑：读回的二进制会被改写

### 3.1 现象

第一次读当前槽校验分区，得到 8,388,611 字节；内核报告这个分区实际是 8,388,608 字节，多出 3 个 0 字节。换不同的读取块大小、换另一种读取命令，结果完全一样，看起来像是「通道固定往末尾补 3 个 0」，于是最初按「截掉尾部」处理。

但读当前槽启动分区时这套解释崩了：读回 67,214,754 字节，比内核报告的 67,108,864 **多出 105,890 字节**，而且多出来的那段里含有非零内容，末尾还能看到校验尾 `AVBf` 被整体推后了。按大小截断的做法被脚本判为失败，理由是「尾部有非零数据」——这是对的，那些早期副本后来全部删除，没有留作回退件。

### 3.2 真正的原因

对读回的数据做字节统计：里面恰好有 **105,890 个「回车 + 换行」字节对**，**零个单独的换行字节**。把每个「回车 + 换行」还原成单个换行之后：

- 长度**精确等于** 67,108,864 字节；
- 开头 8 字节是 `ANDROID!`；
- 末尾 64 字节是校验尾，位置正好在 67,108,800；
- 校验分区的 3 个多余字节、另一个校验分区的 6 个、设备树叠加的 217 个，也都与各自数据里的换行字节数量吻合。

结论：**这个 USB 调试通道不是二进制干净的，会把数据里每一个换行字节写成「回车 + 换行」**。分区有效内容里换行字节越多，读回来就膨胀得越多；几乎全是 0 的分区看起来就像「只多几个 0」。

还原之所以是精确的：原始数据里如果本来就有「回车 + 换行」，在线上会变成「回车 + 回车 + 换行」，把末尾那对还原后正好回到原样，不会误删。「还原后长度必须精确等于内核报告的大小」就是用来兜住这一点的硬校验。

### 3.3 修正后的做法

固化在 `tools/camellian/scripts/backup_partitions_readonly.py`：

1. 现场解析分区对应的真实设备节点（重启后节点编号可能变），读内核报告的分区大小；
2. 逐块读取，把每个「回车 + 换行」还原成单个换行；
3. **长度不精确相等就拒绝**，绝不凑合；
4. 每个分区**独立读两遍**逐字节比对；
5. 最关键的启动分区再走**第三条通道**：在手机端用自带的文本编码把数据变成纯文本（不含裸二进制字节），传回电脑解码后与前面结果比对。

三份证据一致才算通过。本轮结果：`boot_b base64 cross-check: MATCH`、`RESULT: 12/12 partitions verified, nothing failed`，系统命令独立复算的 MD5 / SHA256 也与清单一致。

## 4. 怎么证明读回来的是「带面具的那份」，不是干净原厂版

解析 `boot_b-before.img` 的启动头：

| 项 | 备份里的值 | 原厂线刷包里的值 |
| --- | --- | --- |
| 启动头版本 | 2 | 2 |
| 页大小 | 2048 | 2048 |
| 内核大小 | 13,342,418 | 13,342,418（**完全一致**） |
| 内存盘大小 | 21,246,673 | 21,078,370（**多 168,303 字节**） |
| 尾部校验结构 | 在 67,108,800 处 | 同样在 67,108,800 处 |

内存盘解压后能直接搜到 Magisk 标记。内核没变、内存盘变大且带面具标记，正是「Magisk 只改了开机临时系统」的典型形态。所以这份备份是**精确复原件**：刷回去能回到现在的 root 环境；而线刷包里那份原厂启动镜像刷回去会变成无 root。

## 5. 两槽对比里一个值得记下的观察

四组校验分区和设备树叠加分区在 a/b 两槽内容完全相同，符合「同版本系统更新后两槽同步」的常见状态。两个启动分区内容不同。另一槽的供应商启动分区开头是全 0，整份 64 MiB 与当前槽那份明显不同，看起来是空的。

**这只是一条观察，不能据此断定另一槽一定不可启动**——也可能这台设备本来就只在当前槽使用那份分区。但它确实进一步支持刷机剧本里既有的结论：**切到另一个槽不是第一回退手段**，同槽刷回精确复原件才是。

## 6. 顺带更正的一处文档错误

刷机剧本第 6.2 节原先给的备份命令是「把读出的内容直接重定向到文件」。在这台设备上这条命令会产生被改写、被撑大的**损坏备份**，拿去刷回有风险。现已改为调用本轮固化并验证过的只读备份脚本，并写明三条必须同时成立的判据（长度精确相等、两次读取一致、文本编码交叉比对一致）。第 10 节回退剧本引用的文件名不变。

## 7. 现在的回退能力，以及仍然不能做的事

**已经具备**：当前槽启动分区、当前槽及另一槽各校验分区、设备树叠加、供应商启动分区的精确字节副本；一份设备状态快照；一份可核对的校验清单；一份可复跑的只读备份脚本。

**仍然没做、需要另行明确授权**：

- 把任何文件**刷回**手机（这是写分区）；
- 重启手机、进刷机模式、切换系统槽；
- 写或擦除校验分区、推送文件、安装或卸载应用；
- 执行官方刷机脚本、试刷自编内核。

用户仍未说出「刷机」。按既定边界，含糊的「继续」「下一步」不构成授权。云电脑上的自编启动镜像也还只是文件，没有回传本机、没有刷入。
