> 环境：云电脑 Ubuntu 24.04.5 LTS，x86_64，`/workspace` 为区分大小写文件系统
> 边界：**产物只是两个文件，没有刷入手机、没有连接手机写分区、没有切换系统槽。**

---

## 1. 目标

把上一轮编译成功的、集成了 SukiSU-Ultra 内核侧代码的 4.14 内核，替换进官方原厂 `boot.img`（启动分区镜像）里，重新打包成一个**结构和原厂一致、可以逐字段核对**的启动分区镜像，供将来试刷使用。本轮只做到「准备好」。

## 3. 原厂启动镜像的精确布局

用只读解析脚本把官方 `boot.img` 拆开，得到的结构比上一轮的记录更细（上一轮只看到「设备树追加在内核尾部」，本轮发现设备树其实是**独立的一段**，而且前面还有联发科私有头）：

| 区段 | 偏移 | 长度 | 内容 |
|------|------|------|------|
| 启动镜像头 | 0 | 2,048 | `ANDROID!`，头版本 2，页大小 2048，头长度字段 1660，内核命令行 `bootopt=64S3,32N2,64N2 buildvariant=user` |
| 内核 | 2,048 | 13,342,418 | gzip 压缩内核，**纯 gzip，尾部没有追加设备树** |
| 内存盘 | 13,344,768 | 21,078,370 | gzip 压缩内存盘，解压后约 41,617,152 字节的 cpio，含 `first_stage_ramdisk/fstab.mt6833` 等原厂初始化文件 |
| 设备树区 | 34,424,832 | 161,792 | **前 64 字节是联发科私有头**（魔数 `d7b7ab1e`，其后写有设备树长度 161,191），第 65 字节起是标准设备树（魔数 `d00dfeed`，声明长度 161,127），尾部补零 |
| 内嵌校验数据 | 34,586,624 | 1,664 | 魔数 `AVB0`，sha256 哈希描述符，覆盖前 34,586,624 字节 |
| 校验尾标 | 67,108,800 | 64 | 魔数 `AVBf`，记录「被校验镜像长度 = 34,586,624」「校验数据偏移 = 34,586,624」 |
| 其余 | — | — | 全是零填充，把文件补齐到正好 64 MiB（分区大小） |

> 更正：上一轮根据 `dtb_size` 字段的旧式读法，判断「设备树追加在压缩内核尾部」。本轮用文件魔数搜索确认全文件**只有一处**标准设备树魔数，位于设备树区偏移 +64 处，内核区里没有。所以这台机器用的是启动镜像头版本 2 的**独立设备树区段**，不是老式的「内核尾部追加」。这直接决定了打包方式。

## 4. 三个关键打包决策

### 4.1 用 `Image.gz`，不用 `Image.gz-dtb`

自编产物里 `Image.gz-dtb`（11,627,361 字节）= `Image.gz`（11,495,575 字节）+ 尾部追加的自编设备树（131,786 字节）。既然原厂布局把设备树放在独立区段，打包时就必须**只取 `Image.gz` 这一半**，否则等于往内核区里塞了一段原厂引导程序不会去读的设备树。

### 4.2 保留原厂设备树，不自编设备树

自编内核编译时，因为官方开源快照缺一个原厂构建阶段生成的板级配置文件（`cust.dtsi`），当时补了一个**空占位文件**才把设备树编出来。所以自编设备树（131,786 字节）比原厂设备树（161,127 字节）少了约 29 KB 的真实板级配置。

**保留原厂设备树整段 161,792 字节（含联发科私有头）原样不动**，理由有三：

1. 原厂设备树是量产配置，板级信息比占位文件编出来的完整；
2. 内核与设备树来自同一套源码树，驱动匹配用的兼容字符串一致，可以配对；
3. 联发科那 64 字节私有头的字段含义没有完整资料，原样保留最稳妥。

### 4.3 保留原厂内存盘

内存盘里有原厂 `init`、挂载配置表（`fstab.mt6833`）、首阶段初始化脚本。自编内核只换了内核本体，这些必须原样保留，否则系统起不来。

> 顺带说明当前状态：内存盘里**没有** SukiSU 的用户态守护程序。也就是说这个镜像刷进去以后，系统应当能正常开机，但 root 还不会激活——需要后续安装管理器应用，由管理器把守护程序放到系统数据分区后，内核里的挂钩才会接管。这属于「刷完之后的事」，本轮没有涉及。

### 4.4 校验数据怎么办

内嵌的 `AVB0` 校验数据用小米私钥签名，我们无法重签。打包时**原样保留这一段**，只把校验尾标里的两个偏移字段改成新布局对应的值。这样引导程序的解析路径和原厂完全一致，只有哈希比对会失败——在已解锁的启动锁下，验证错误是非致命的（详见风险对照文档第 6 节）。

## 5. 打包实现

脚本：`tools/camellian/scripts/pack_boot.py`（已回传本机仓库）。流程：

1. 解析原厂头，算出四个区段的原始偏移，抽出内存盘、设备树区、内嵌校验数据三段原始字节；
2. 复制原厂 2,048 字节启动镜像头，只改两处：`kernel_size` 改成自编内核长度；`id`（构建时的 SHA1 指纹，非安全校验字段）改成新载荷的摘要；
3. 按页大小 2048 重算各区段偏移：内核 2,048 → 内存盘 11,499,520 → 设备树 32,579,584 → 内嵌校验数据 32,741,376；
4. 组装成**仍是 67,108,864 字节**的镜像（保持分区大小不变，这样校验尾标仍然落在分区最后 64 字节，引导程序能找到）；
5. 把校验尾标里的「被校验镜像长度」和「校验数据偏移」都改成 32,741,376；
6. 重新读回文件，做 12 项结构校验。

### 12 项校验，全部通过

| # | 校验项 | 结果 |
|---|--------|------|
| 1 | 大小与原厂一致（64 MiB） | 通过 |
| 2 | 启动镜像头魔数 `ANDROID!` | 通过 |
| 3 | 内核长度字段已改成 11,495,575 | 通过 |
| 4 | 内存盘长度字段未改动 | 通过 |
| 5 | 内核字节与自编 `Image.gz` 逐字节一致 | 通过 |
| 6 | 内存盘字节与原厂逐字节一致 | 通过 |
| 7 | 设备树区字节（含私有头）与原厂逐字节一致 | 通过 |
| 8 | 内嵌校验数据字节与原厂逐字节一致 | 通过 |
| 9 | 校验尾标魔数 `AVBf` | 通过 |
| 10 | 尾标「被校验镜像长度」已重定位 | 通过 |
| 11 | 尾标「校验数据偏移」已重定位 | 通过 |
| 12 | 各区段之间的补白全是零，没有夹带旧数据 | 通过 |

打包后还用另一份独立写的解析脚本重新读取，确认头字段、三个区段的魔数（内核 `1f8b0800`、内存盘 `1f8b0800`、设备树 `d00dfeed`）、校验尾标偏移全部对得上。

## 7. 已知遗留问题（如实记录）

1. **校验哈希是过期的**：换过内核后，保留的 `AVB0` 里那个 sha256 必然对不上。已解锁启动锁下这是可容忍的验证错误，但没有真机验证过「一定会启动」。现有 Magisk Alpha 已经改过启动分区且能开机，是最有说服力的旁证。
2. **内核配置与原厂量产配置有偏差**：本轮自编时链接时优化 / 控制流完整性被 Kconfig 回退成关闭（`CONFIG_LTO_NONE=y`），量产配置是开启的；另外为了编译通过打开了 `CONFIG_KPROBES`、`CONFIG_KALLSYMS_ALL`、`CONFIG_IKCONFIG_PROC`，关闭了 `CONFIG_MILLET`、 SuSFS、KPM 等。稳定性、性能、隐藏能力都不等于原厂。
3. **用户态部分还没接上**：内核侧代码已编进去，但管理器应用、用户态守护程序都还没装进系统，刷进去也不会立刻获得 root。
4. **没有做开机验证**：因为本轮不碰手机，所以「能开机 / 能提权 / 隐藏是否生效」全部是未验证状态。
5. **没做防回滚与校验状态的组合测试**：单槽试刷、切槽、全量恢复这些路径只做了机制核对，没有实机演练。
