## 1. 术语说明（本文第一次出现时都会先讲人话）

- **链接时优化（LTO）**：普通编译是一个个源文件分别优化，LTO 是在最后把所有代码合到一起做全局优化。产物更大、编译更慢，但更接近原厂。
- **控制流完整性（CFI）**：运行时检查「函数指针有没有被改成不该去的地方」，是一项安全加固。
- **瘦归档（thin archive）**：一种不把目标文件真正打包、只记录路径的中间归档方式。它对「同一个目标文件被列了两遍」不宽容，会直接报重复符号。
- **clang / gcc**：两种编译器。原厂量产内核用的是谷歌安卓源码树里预编译的 clang 11.0.1，这个内核的 LTO 与 CFI 只有 clang 支持。
- **defconfig**：内核的「默认配置片段」，构建时用来生成最终配置文件 `.config`。
- **ikconfig**：内核镜像里内嵌的一份「我当时是用什么配置编译出来的」清单。我们从原厂启动镜像里把它提取出来，当作量产真相。
- **UAPI**：内核与手机上普通程序之间的调用约定（编号、命令字、数据结构）。两边编号对不上，程序就调不通。
- **管理器安装包验签白名单**：内核不比对整个安装包，而是取出安装包签名区里第一张证书，比它的长度和 SHA256 是否与内核里写死的几条记录一致；一致才认这个管理器。
- **启动分区镜像（boot.img）**：手机开机时先加载的那一段，里面放内核、内存盘、设备树和校验信息。
- **AVB（安卓启动校验）**：开机时校验启动分区有没有被改过。自编内核改了内容，原厂那段校验哈希必然对不上；启动锁已解锁时这个错误不致命，但这一点**尚未实机验证**。

## 2. 根因更正（本轮最重要的发现）

### 2.1 之前写错的那句话

`20261106-2234` 报告第 7 节和 `20261106-2314` 复跑手册第 4 节都写过：

> 开源 `camellian_defconfig` 里只有 `CONFIG_LTO_CLANG=y`、`CONFIG_CFI_CLANG=y`，漏了父开关 `CONFIG_LTO=y` / `CONFIG_CFI=y`，所以配置展开时回退成了关闭。

**这句话是错的，已在两份旧文档里加更正并指向本文。**

### 2.2 真实情况

直接查云电脑上的开源内核源码：

```text
camellian-kernel/arch/arm64/configs/camellian_defconfig:29:CONFIG_LTO_CLANG=y
camellian-kernel/arch/arm64/configs/camellian_defconfig:30:CONFIG_CFI_CLANG=y
camellian-kernel/arch/arm64/configs/camellian_in_eea_defconfig:28:CONFIG_LTO_CLANG=y
camellian-kernel/arch/arm64/configs/camellian_in_eea_defconfig:29:CONFIG_CFI_CLANG=y
```

父开关不需要、也不应该由 defconfig 手写：`CONFIG_LTO` / `CONFIG_CFI` 是由架构能力和 `CONFIG_LTO_CLANG` / `CONFIG_CFI_CLANG` 被选中后自动带出来的依赖结果。原厂 `ikconfig` 里能看到它们，正是因为它们生效了，不是因为有人手写了两行。

### 2.3 那到底是谁把配置删掉的

内核主构建文件 `Makefile` 第 1250–1261 行有一个自动检查（原文摘录）：

```make
PHONY += check-clang-specific-options
check-clang-specific-options: $(KCONFIG_CONFIG) FORCE
ifneq ($(cc-name),clang)
ifneq ($(findstring y,$(shell $(CONFIG_SHELL) \
	$(srctree)/scripts/config --file $(KCONFIG_CONFIG) \
		$(foreach c,$(clang-specific-configs),-s $(c)))),)
	@echo WARNING: Disabling clang-specific options with $(cc-name) >&2
	$(Q)$(srctree)/scripts/config --file $(KCONFIG_CONFIG) \
		$(foreach c,$(clang-specific-configs),-d $(c)) && \
	$(MAKE) -f $(srctree)/Makefile olddefconfig
endif
endif
```

链条是这样的：

1. 第一次原版试编时，我们把 `CC=clang` 只放在环境变量里，被内核构建系统覆盖，实际用了 gcc（当时的日志里确实出现过 `WARNING: Disabling clang-specific options with gcc`）。
2. 上面这段检查发现「当前编译器不是 clang，但配置里还有一堆只有 clang 能用的选项」，于是**主动把这些选项从 `.config` 里删掉，并自动跑一次配置重算**。`CONFIG_LTO_CLANG`、`CONFIG_CFI_CLANG` 等就在被删名单里。
3. 之后我们虽然改成把 `CC=clang` 写在 `make` 命令行上、编译也成功了，但**从来没有把被删掉的选项补回来**。于是后面每一次自编（包括集成 SukiSU 的内核）都继承了这份「缺了 clang 专属配置」的 `.config`。

所以这不是小米开源快照不自洽，是我们自己的构建历史留下的一次配置污染。教训改成：**编译器参数一定要写在构建命令上；一旦出现过「用错编译器」的告警，要回头检查最终配置文件有没有被自动改写，不能只看后续编译是否成功。**

顺带说明：`20261106-2234` 里「量产构建必须用 clang」这个结论本身没错，错的是它的推导依据；现在依据换成了「原厂 `ikconfig` 里 LTO/CFI 全套为 y」加「clang 专属选项被删除的机制」，结论反而更硬。

## 3. 把量产配置补回来的操作

先把污染前的配置留档为 `/workspace/out/.config.prelto`，再用内核自带的配置工具显式打开对应项，最后让内核重新推导依赖：

```bash
cd /workspace/camellian-kernel
scripts/config --file /workspace/out/.config \
  -e LTO_CLANG -e CFI_CLANG -e LTO -e CFI -e THINLTO \
  -e CFI_CLANG_SHADOW -e THIN_ARCHIVES -d LTO_NONE -d CFI_PERMISSIVE
make O=/workspace/out ARCH=arm64 CC=clang ... olddefconfig
```

恢复后的关键配置逐行摘录（已存为 `tools/camellian/config/lto-cfi-config-options.txt`）：

```text
CONFIG_THIN_ARCHIVES=y
CONFIG_LTO=y
CONFIG_THINLTO=y
# CONFIG_LTO_NONE is not set
CONFIG_LTO_CLANG=y
CONFIG_CFI=y
# CONFIG_CFI_PERMISSIVE is not set
CONFIG_CFI_CLANG=y
CONFIG_CFI_CLANG_SHADOW=y
```

与原厂 `ikconfig` 对照，这七行**完全一致**：

```text
[factory]                        [self-built, after fix]
CONFIG_THIN_ARCHIVES=y            CONFIG_THIN_ARCHIVES=y
CONFIG_LTO=y                     CONFIG_LTO=y
CONFIG_THINLTO=y                 CONFIG_THINLTO=y
CONFIG_LTO_CLANG=y               CONFIG_LTO_CLANG=y
CONFIG_CFI=y                     CONFIG_CFI=y
CONFIG_CFI_CLANG=y               CONFIG_CFI_CLANG=y
CONFIG_CFI_CLANG_SHADOW=y        CONFIG_CFI_CLANG_SHADOW=y
```

## 4. 全量重编与第 6 处适配

### 4.1 过程

- 后台启动的全量重编被会话清理打断，日志停在中途且没有退出码；改为前台续编，日志以 `build-lto4.log` 为准。这也是这一轮耗时较久、用户感觉「卡了半天」的原因——中间还叠加了一次链接错误排查。**整个过程都在云电脑上，与手机无关。**
- 重编前先清理旧目标文件但保留 `.config`，避免用旧的非 LTO 目标文件混进新链接。
- 最终 `build-lto4.log` 里 `error:` 计数为 **0**，末行是 `CAT arch/arm64/boot/Image.gz-dtb` 与正常退出。

### 4.2 新暴露的链接错误

打开 LTO 后链接器报 `duplicate symbol`，定位到厂商的一处构建配置：`drivers/media/platform/mtk-vcu/Makefile` 把 `mtk_vcodec_mem.o` 列了两遍——一次通过组合目标 `mtk-vcu-y`，一次直接挂在模块列表上。普通链接方式可能会容忍，瘦归档 + LTO 不会去重，于是同一个符号进了两次。

修复（已存为 `tools/camellian/patches/kernel-lto-mtk-vcu.patch`）：

```diff
-obj-$(CONFIG_VIDEO_MEDIATEK_VCU) += mtk-vcu.o mtk_vcodec_mem.o
+obj-$(CONFIG_VIDEO_MEDIATEK_VCU) += mtk-vcu.o
```

同时清掉已经包含重复成员的瘦归档再续编。这是本项目第 6 处为让官方开源快照能编译而做的适配；前 5 处见 `20261106-2213` 集成报告。

## 7. 用户态组件：电脑侧准备与契约核对

### 7.1 下载并校验

从官方发布页 `v4.3.0-r2` 取三件，只放在云电脑 `/workspace/userspace/`：

| 文件 | 大小（字节） | SHA256 |
|------|--------------|--------|
| `ksud-aarch64-linux-android`（用户态后台守护程序） | 7,867,384 | `dec34535789f28e3ecda2788618a2e57c70f77b17b5ce129ff50026b9ba42f35` |
| `ksuinit-aarch64`（早期启动用的初始化程序） | 643,840 | `c7034b996c739734ecefe4357397549443725830c3e395ee4e2dd7913a4c2b26` |
| `SukiSU_v4.3.0-r2_41150-release.apk`（管理器安装包） | 20,131,351 | `6fe64e7bcf9fd768c58f46afea2f27ee9fb85d2783472a7e81334df21e700636` |

### 7.2 内核到底去哪里找它们

内核侧 `kernel/runtime/ksud.h` 写死：

```c
#define KSUD_PATH "/data/adb/ksud"
```

并在启动脚本注入逻辑里以 `exec u:r:... root -- /data/adb/ksud post-fs-data` 拉起后台程序。也就是说：**后台程序必须落在手机数据分区的 `/data/adb/ksud`**，管理器安装包则要作为普通应用装进系统。这两件事都是写手机，按当前边界未执行。

打包时也没有把 `ksud` / `ksuinit` 塞进内存盘：内核逻辑默认找 `/data/adb/ksud`，改内存盘会引入额外的启动脚本改动、增加打包复杂度，而且在不能开机的前提下根本无法验证它是否奏效，本轮不做这种「改了也验证不了」的变更。

### 7.3 管理器安装包能不能被这颗内核认出来

内核 `kernel/manager/apk_sign.c` 的白名单第一条是 `{ 0x35c, "947ae944...eef" }`。用 `tools/camellian/scripts/verify_manager_apk.py` 在电脑上复现内核的解析方式（解析安装包签名区，取第一签名者证书的长度与 SHA256）：

```text
APK: userspace/SukiSU_v4.3.0-r2_41150-release.apk
size: 20131351 bytes
  signing block pair id 0x7109871a  size 1510   (v2 签名)
  signing block pair id 0x42726577  size 2538   (verity 填充)
v2 signing blocks: 1
  signer 0 certificate size: 860 (0x35c)
  signer 0 certificate sha256: 947ae944f3de4ed4c21a7e4f7953ecf351bfa2b36239da37a34111ad29993eef
```

**与白名单第一条完全一致**，且签名区里只有 v2 签名和 verity 填充两类数据，属于内核能接受的结构。也就是说官方管理器与这颗内置内核在验签这一关是对得上的。

### 7.4 接口契约是否一致

两边 `KERNEL_SU_UAPI_VERSION` 都是 **6**（内置分支用 `DECLARE(__u32, KERNEL_SU_UAPI_VERSION, 6)`，发布版用 `static const __u32 ... = 6`，只是写法不同）。

用 `tools/camellian/scripts/compare_uapi.py SukiSU-Ultra/uapi userspace/uapi-release` 做常量级比较，输出 4 处差异：其中 3 处是脚本把头文件里的宏定义文本误当成常量的解析噪声（键名显示为 `name`），**唯一实质差异是发布版多一个 `KSU_IOCTL_SET_SPOOF_VERSION`**（`_IOC(_IOC_WRITE,'K',102,0)`），内置分支没有这个命令字。它对应的是「伪装系统版本号」这项可选扩展；本轮 4.14 适配里 CPU 身份伪装整体被禁用，因此这个缺失目前不影响已启用功能，但属于需要记在账上的契约差异。

> 注意：比较脚本的第一个参数必须是仓库根目录下的 `uapi/`，不是 `kernel/uapi/`（后者不存在）。本轮第一次复跑时传错路径，得到「129 处差异、内置侧全空」的假结果，已纠正。

## 8. 「用户态接好」现在到哪一步，还差什么

**已经做完（电脑侧）**：组件下载与校验、内核期望路径确认、管理器验签核对、接口版本与常量差异核对、启动脚本注入逻辑确认。

**没做（手机侧，需要授权）**：把 `ksud` 放到 `/data/adb/ksud` 并给可执行权限、安装管理器安装包、首次开机后确认后台程序被拉起并能在管理器里看到授权界面。这些都会写手机数据，用户明确说过「在我明确说刷机之前，你不要修改我手机的数据。你可以只读」，因此**本轮一步都没有执行，也不把「把用户态部分接好」理解成允许往手机装东西**。

**这意味着什么**：现在这份启动分区镜像即使刷进去，也只是「内核里的提权通道编译进去了」；没有 `/data/adb/ksud` 和管理器，开机后不会立刻有可用的 root 授权界面。所以真正要试的那一天，必须把「刷启动分区」和「装用户态组件」当成同一批动作来安排，不能只刷镜像就以为完成。

## 9. 还没验证的事与遗留风险

1. **开机 / 提权 / 隐藏能力全部未验证**。编译通过、结构校验通过，都不等于能开机。
2. **AVB 校验哈希仍然过期**，依赖已解锁启动锁容忍验证错误，未实机验证。
3. **可选特性仍为关闭或禁用**：SuSFS、KPM、CPU 身份伪装、preinit 等为让 4.14 编译通过而关掉；`CONFIG_KSU_SUSFS`、`CONFIG_KPM` 未启用。隐藏能力弱于手机现在装的 Magisk Alpha。
4. **设备树仍是原厂那份**：自编时 `cust.dtsi` 是空占位，打包保留原厂独立设备树区段，没有用自编设备树。
5. **契约差异**：发布版多 `KSU_IOCTL_SET_SPOOF_VERSION`，内置内核没有；未决定是否补。
6. **后台程序没有进内存盘**，理由见 7.2。
