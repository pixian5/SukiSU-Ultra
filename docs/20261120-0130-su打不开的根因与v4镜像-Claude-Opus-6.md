# su 打不开：根因不是 sus_path，而是 sucompat 降级（v4 镜像）

- 时间：2026-11-20 01:30（GMT+8）
- 现象：v3 刷入后 Shell 在超级用户列表显示 ROOT，但
  `head -c 4 /system/bin/su` 与 `su -c id` 均返回 No such file or directory
- 产物：`dist/boot-sukisu-susfs-allowlist-fix-v4.img`
  - 67,108,864 B，MD5 `6aab260ff8331a8b15a682dd4685242b`
  - SHA256 `5ca4f6a1424fe541d29bbf2e77c7996537afe0a87b000ddbd2804cc575aada63`
- 边界：未刷机、未连手机、未发布主线 Release，v1/v2/v3 未覆盖

## 一、结论：不是 sus_path

逐条核对后，`sus_path` 不是原因：

1. **默认值是空的**：`userspace/ksud/src/susfs_config/store.rs:83`
   `config.insert(KEY_SUS_PATHS, String::new())`。全仓库检索没有任何预设
   把 `/system/bin/su` 写进 sus_path。
2. **sus_path 不会让 open 返回 ENOENT**：内核实现（`fs/susfs.c`）只做两件事——
   给 inode 打 `INODE_STATE_SUS_PATH` 标记，以及在
   `susfs_sus_ino_for_filldir64()` 里返回 1。后者只被 `filldir64` 调用，
   即**目录遍历时跳过该条目**，不拦截 `open()` / `stat()` / `execve()`。
   与「ls 能看到、head 打不开」的现象不一致。

## 二、真正原因：sucompat 把 su 改写成 sh

SukiSU 的设计前提是**系统里没有 su 文件**。任何对 `/system/bin/su` 的访问
都由 `kernel/feature/sucompat.c` 在内核里改写：

```c
ret = escape_with_root_profile();
if (!!ret)
    return ret;

// NOTE: we only check file existence, not exec success!
struct path kpath;
if (!!kern_path("/data/adb/ksud", 0, &kpath))   // ← 缺失 LOOKUP_FOLLOW
    goto no_ksud;

path_put(&kpath);
memcpy((*filename_ptr)->name, ksud_path, sizeof(ksud_path));  // → 提权
return 0;

no_ksud:
memcpy((*filename_ptr)->name, sh_path, sizeof(sh_path));      // → /system/bin/sh
```

两个独立缺陷叠加：

### 缺陷 A：`kern_path()` 用了 flags=0，不跟随符号链接

`/data/adb/ksud` 在 4.14 树里可能是符号链接（ksud 真实二进制在
`/data/adb/ksu/bin/ksud`，见 `userspace/ksud/src/defs.rs` 的
`DAEMON_PATH` 与 `DAEMON_LINK_PATH`）。`kern_path(path, 0, ...)` 不跟随
符号链接，探测失败 → 落到 `no_ksud` → **su 被静默改写成 `/system/bin/sh`**。

于是：
- `su -c id` → 实际执行 `sh -c id` → `id: not found`
- `head -c 4 /system/bin/su` 走的是 `open()`（4.14 未挂 open 钩子），
  读到的是设备上那个真实的 328384 字节 su 文件；若该文件恰好是指向
  `/data/adb/ksu/bin/su` 的符号链接而目标不存在，即返回 ENOENT。

### 缺陷 B：失败路径静默降级，不报错

`no_ksud` 分支只打一行 `pr_info("... su->sh!")`，用户态完全感知不到。
root 因此「看起来授权正常、实际不可用」。

## 三、附带确认：原厂 ramdisk 没有 su

解包 `/workspace/rom/boot-stock.img` 的 ramdisk（cpio，920 个条目）确认
**没有任何 su 条目**，`sbin/` 也为空。所以设备上的 328384 字节 su 是外部
安装的（Magisk 残留或管理器写入），不是本内核产物。

## 四、改动（两处，均在内核）

### 1. `kernel/feature/sucompat.c`

新增候选路径探测（跟随符号链接），替换两处 `kern_path(..., 0, ...)`：

```c
static bool ksu_ksud_binary_exists(void)
{
    static const char *const candidates[] = {
        "/data/adb/ksud",
        "/data/adb/ksu/bin/ksud",
    };
    struct path kpath;
    int i;

    for (i = 0; i < ARRAY_SIZE(candidates); i++) {
        if (!kern_path(candidates[i], LOOKUP_FOLLOW, &kpath)) {
            path_put(&kpath);
            return true;
        }
    }
    return false;
}
```

调用点改为 `if (!ksu_ksud_binary_exists()) goto no_ksud;`，
覆盖 `ksu_sucompat_user_common()` 与 `ksu_handle_execveat_sucompat()`。

### 2. `fs/susfs.c`：su 路径白名单

即使管理器或用户配方误把提权路径加进 sus_path，也在内核侧拦截：

```c
static const char *const susfs_protected_su_paths[] = {
	"/system/bin/su",
	"/system/xbin/su",
	"/sbin/su",
	"/data/adb/ksu/bin/su",
	"/data/adb/ksud",
	"/data/adb/ksu/bin/ksud",
};
```

位置在 `susfs_core_add_sus_path()` 入口，命中直接返回 `-EPERM`。

### 3. `fs/susfs_abi.c`：把拒绝原因写回用户态

原来忽略返回值，管理器以为添加成功。现在把 `err` 写回结构体
`st_susfs_sus_path.err` 偏移，管理器会明确看到失败。

## 八、如果 su 仍不可用

```bash
dmesg | grep -iE "su->ksud|su->sh|ksu_handle"
```

| dmesg | 含义 | 下一步 |
| --- | --- | --- |
| `do_execveat_common su->ksud!` | 改写成功，走提权路径 | 若仍失败，问题在 ksud 自身 |
| `do_execveat_common su->sh!` | 仍降级到 sh | 确认 `/data/adb/ksud` 或 `/data/adb/ksu/bin/ksud` 是否存在、SELinux 上下文 |
| 无任何 su 日志 | 钩子未触发 | 确认 `ksu_su_compat_enabled`、`TIF_SECCOMP`、uid 是否被授予 root |
| `refuse to hide protected su path` | 白名单生效 | 正常，说明有人在隐藏 su |

补充判据：`ls -l /data/adb/ksud /data/adb/ksu/bin/ksud`，
`ksud --version`。

## 九、关于「只改用户态就不用重编」

无法只改用户态绕过：降级发生在**内核**的 `sucompat.c`，
用户态（ksud/管理器）拿不到这个决策点。因此本次必须重编内核。
管理器侧的 sus_path 默认值本身已经正确（空），无需改动。
