# SUSFS v2.3.0 移植与编译验证

> 时间：2026-11-08 02:10（GMT+8）
> 模型：DeepSeek-V4.1-Flash
> 范围：在远程 Linux 沙箱完成源码移植与完整编译验证；**没有刷机、没有碰手机**。

---

## 0. 一句话结论

SUSFS 已接入 SukiSU 的 4.14 手动挂钩内核：**上游 v1.5.5 的 4.14 原生核心 + v2.3.0 ABI 兼容层**，在本沙箱用 AOSP clang-r383902 从零完整编译通过，`Image.gz` 产物中 51 个 `susfs_` 符号与全部命令入口齐全，版本字符串为 `v2.3.0`。产物是**编译验证镜像**，不是可刷机镜像（原因见第 6 节）。

---

## 1. 为什么不直接套 v2.3.0 补丁

| 事实 | 影响 |
| --- | --- |
| 上游 `susfs4ksu` 的 `kernel-4.14` 分支停在 **v1.5.5**（2025-02） | 命令 ABI 是旧的：`int fn(struct st_* __user)`，结构体没有 `err` 字段 |
| SukiSU `builtin`（设备当前在用分支）要求 **v2.3.0** ABI | `void fn(void __user **)`、结构体带 `err`、新增 `sus_map` / `avc_log_spoofing` / `priority_uid_filter` / `sus_path_loop` |
| v2.3.0 的官方补丁只面向 5.10+ | 直接套 4.14 会涉及 mm/selinux/fs 大量不存在的接口 |

因此采用三层混合：

```
SukiSU kernel/  ──调用 v2 ABI──▶  fs/susfs_abi.c（翻译层）
                                        │
                                        ▼
                              fs/susfs.c（v1.5.5 4.14 原生核心）
                                        │
                                        ▼
                     上游 50_add_susfs_in_kernel-4.14.patch 的 21 处钩子
```

ABI 翻译层参考了 `yao140514/oppoa2m-sukisu-susfs` 在 4.19 上的同类移植（GPL-2.0），按 4.14 与 SukiSU 4.3 重新适配。

## 2. 四处必要的 SukiSU 侧修复

### 2.1 sucompat 的 5.x 实现被错误编进 4.14（会开机即崩）

`kernel/feature/sucompat.c` / `sucompat.h` 里，只要 `CONFIG_KSU_SUSFS=y` 就启用 5.x 版钩子：它把 `vfs_statx`/`faccessat` 传进来的**用户路径字符串**当成 `struct filename *` 解引用。社区已有实测：刷入后开机 1 秒内 data abort（`pc: ksu_handle_stat`）。

修复：条件改为 `defined(CONFIG_KSU_SUSFS) && LINUX_VERSION_CODE >= KERNEL_VERSION(5,0,0)`，4.14 继续走经典实现。

### 2.2 setresuid 钩子缺失（管理器认不出驱动）

SUSFS 模式下 LSM `task_fix_setuid` 钩子不注册，改用 `ksu_handle_setresuid()`。但 4.14 的 `SYSCALL_DEFINE3(setresuid)` 从未调用它，导致 zygote 孵化的应用既不关 seccomp、也不装驱动 fd。

修复：在 [kernel/sys.c](../kernel/sys.c) 的 `SYSCALL_DEFINE3(setresuid)` 入口调用 `ksu_handle_setresuid()`。

### 2.3 `strncpy_from_user_nofault()` 不存在

该函数 5.8 才引入，4.14 的 sulog 在 SUSFS 模式下会用到。修复：在 `kernel_compat.h` 里用 `strncpy_from_user()` 做等价替代（调用点在进程上下文）。

### 2.4 adb_root 入口签名不匹配

SUSFS 版只有 `ksu_adb_root_handle_execveat(const char *, void ***)`，4.14 手动钩子调用的是非 SUSFS 的 `_manual` 版本。修复：SUSFS 下改调新入口，并把 `&envp.ptr.native` 作为 envp 指针位置传入。

## 4. 编译期踩到的三个厂商树问题（与 SUSFS 无关）

1. **`linux/static_call.h` 不存在**：SukiSU 源码默认无条件包含；仓库 `tools/camellian/patches/sukisu-kernel.patch` 已有 5.10 版本守卫，本次一并应用。
2. **mtk-vcu 重复目标文件**：`obj-$(CONFIG_VIDEO_MEDIATEK_VCU) += mtk-vcu.o mtk_vcodec_mem.o`，而 `mtk-vcu.o` 已包含该对象；thin archive 下报一串 duplicate symbol。删掉重复项。
3. **厂商闭源符号缺失**：`hq_regiser_hw_info`、`get_huaqin_pcba_config`、`get_audio_pa_vendor` 由 `CONFIG_HQ_SYSFS_SUPPORT` 提供；通用 defconfig 默认关闭，开启即可。`CONFIG_MIHW` 依赖仓库里不存在的 `vendor/xiaomi/kernel_modules/mihw`，关闭。

## 5. 能力边界（不要高估）

| 功能 | 状态 | 说明 |
| --- | --- | --- |
| sus_path | 可用 | 由 setresuid 钩子给应用进程打标记 |
| sus_mount | 可用 | v1.5.5 的 mnt_id 伪造与 sus 挂载隐藏 |
| sus_kstat | 可用 | |
| uname / cmdline 伪装 | 可用 | |
| open_redirect | 可用 | |
| enable_log / 隐藏 ksu 符号 | 可用 | 需要 KALLSYMS_ALL |
| sus_path_loop | 部分 | 退化为一次性添加 |
| sus_map | **不生效** | 只标记 inode，没有过滤 `/proc/pid/maps` 的钩子 |
| avc_log_spoofing | **不生效** | 没有 selinux avc 钩子；`susfs_add_sus_avd_allowed_by_type` 为兼容空实现 |
| priority_uid_filter | **不生效** | 只记录，不参与判定 |
| try_umount | 未启用 | v1.5.5 可选特性，需要额外 KSU 支撑 |
| KPM | 不可用 | 与 SUSFS 无关，4.14 缺 KernelPatch 钩子 |

管理器里 `sus_map` / `avc_log_spoofing` / `priority_uid_filter` 可能显示为「支持」，因为 ABI 命令已注册；**实际不隐藏任何东西**。

## 6. 这份产物为什么不能直接刷

1. 用的是通用 `camellian_defconfig`，不是设备出厂配置（量产配置来自原厂 `ikconfig`）；
2. 为缩短编译时间关闭了 LTO/CFI，与出厂内核不一致；
3. `CONFIG_MIHW` 关闭、`FRAME_WARN=0`，并开启了通用 defconfig 里默认关闭的厂商驱动；
4. 只产出 `Image.gz`，没有按 `pack_boot.py` 打 boot 镜像，也没有回传本机；
5. 从未在真机验证。

要得到可刷镜像，必须：用出厂配置 + LTO/CFI → `integrate-susfs.py` 接入 → 编译 → `pack_boot.py` 打包 → 用户明确授权后刷 `boot_b`。
