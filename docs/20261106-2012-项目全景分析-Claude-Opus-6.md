## 一、一句话结论

这是一个**从 KernelSU 分叉出来、独立演进的 Android 内核级 root 方案**。它把「内核里给权限」「系统里跑守护进程」「手机上做管理界面」三件事做成一条完整链路，并在 KernelSU 之上叠加了大量自有能力：可加载内核模块扩展、隐藏检测痕迹的成套机制、多管理器识别、以及一个正在快速膨胀的**主题商店与个性化外观生态**。

从最近 8 次提交看，148 个变更文件落在管理器 App、只有 4 个落在内核（且是从上游回移的重构），说明**当前主战场已经从内核 root 实现转移到管理器端的在线内容平台**，内核侧进入维护与上游同步状态。

## 二、分层全景地图

先解释几个后面会反复出现的名词，第一次出现时都在这里给全：

| 名词 | 全称 / 含义 |
| --- | --- |
| root | Android 上的超级用户权限。本项目在 Linux 内核里完成提权，而不是靠改 `/system` 分区 |
| GKI | Generic Kernel Image，谷歌从 Android 12 起推行的通用内核镜像规范。符合规范的内核可以只替换一个内核模块就获得 root |
| LKM | Loadable Kernel Module，可加载内核模块。本项目的内核产物就是 `kernelsu.ko` |
| ksud | KernelSU Daemon，注入到系统里以 root 身份运行的用户态守护程序兼命令行工具，部署在 `/data/adb/ksud` |
| ksuinit | 开机最早阶段替换 `/init` 的静态小程序，负责把内核模块加载进内核 |
| UAPI | Userspace API，内核与用户态之间约定的控制命令与数据结构，本仓库集中在 `uapi/` 目录的头文件里 |
| ioctl | 对文件描述符下发控制命令的系统调用，是本项目内核与用户态之间的主要通信方式 |
| App Profile | 每个应用单独配置的 root 权限模板，可以限定 UID/GID、能力集、SELinux 域、是否卸载模块挂载 |
| KPM | Kernel Patch Module，基于 KernelPatch 的内核补丁模块，可在运行时往内核里加载额外功能 |
| SuSFS | 一套给 KernelSU 用的隐藏 root 痕迹的内核补丁与用户态工具，本项目内置其管理界面 |
| Manager | 本项目配套的 Android 应用，包名 `com.sukisu.ultra`，普通用户通过它管理授权、模块和设置 |
| WebUI | 模块自带的网页界面，管理器用 WebView 承载，网页通过 `kernelsu` 这个 npm 包调用 root 能力 |

仓库按职责可以分成六层：

```
第 1 层  内核实现      kernel/            纯 C，产出 kernelsu.ko
                         ├─ 授权策略、SELinux、系统调用挂钩、隐藏套件、扩展框架
                         └─ 开机早期 runner（vendored nolibc）
第 2 层  接口契约      uapi/              纯 C 头文件，内核与用户态共用
                         └─ ioctl 命令号、feature/extension 编号、数据结构
第 3 层  用户态        userspace/
                         ├─ ksud     Rust，模块系统、boot 镜像修补、su、KPM/SuSFS 管理
                         └─ ksuinit  Rust，开机早期加载内核模块
第 4 层  手机端        manager/           Kotlin + Jetpack Compose，管理器 App
                         ├─ :app     主应用（另有 :ai-api 桥接模块）
                         └─ 主题商店、账号体系、WebUI 宿主、刷写界面
第 5 层  前端生态      js/                npm 包 kernelsu，模块 WebUI 的 JS SDK
第 6 层  工程化        .github/workflows/、scripts/、根目录两个 Python 打包脚本、docs/
```

一条典型的提权请求会从上往下穿过第 4 → 第 3 → 第 2 → 第 1 层，再原路返回。

技术栈要点：

- **内核纯 C，不是 Rust**：`kernel/` 下没有任何 `.rs` 文件。Rust 全部用在用户态（`ksud` / `ksuinit`），workspace 用 edition 2024、`resolver = 3`，release 配置为体积优先（LTO、尺寸优化、异常直接终止）。
- **管理器**：Kotlin 2.4.20 + AGP 9.4.1 + Compose BOM 2026.09，最低 SDK 24、目标与编译 SDK 37、Java 21、NDK 29；四种架构含较少见的 riscv64。
- **双 UI 实现并存**：Material 3 与 Miuix 两套界面成对维护，大量 `XxxMaterial.kt` / `XxxMiuix.kt` 文件，功能改动常要同步改两份。
- **Root 通道**：libsu + 自写 JNI（`Natives.kt` 加载 `libkernelsu.so`）+ AIDL 服务，底层统一走 `ksud`。

## 四、内核侧：它到底怎么给 root

### 4.1 提权链路

1. **两种发起方式**：管理器通过 JNI 调用 `ksud`，由 `ksud` 下发 `GRANT_ROOT` 控制命令；或者某个应用去执行 `/system/bin/su`，内核把 `faccessat` / `newfstatat` / `execve` 这几个系统调用里的路径重定向到 `/data/adb/ksud`，命中后再提权（`kernel/feature/sucompat.c`）。后者让传统 `su` 命令继续保持可用，但系统里其实没有那个文件。
2. **授权判定**：`kernel/policy/allowlist.c` 用 RCU 哈希表保存每个应用的配置，持久化在 `/data/adb/ksu/.allowlist`（魔数 `0x7f4b5355`，格式版本 4）。系统 UID 默认拒绝，管理器恒允许，其余按配置里的 `allow_su` 决定。
3. **真正的提权**：`kernel/policy/app_profile.c` 的 `escape_with_root_profile()` 改写进程凭据——UID/GID/附属组、完整能力集、SELinux 域（默认 `u:r:ksu:s0`）、挂载命名空间，并关掉 seccomp 过滤。
4. **SELinux 配套**：`kernel/selinux/` 直接操作内核策略数据库，新建 permissive 的 `ksu` 域和 `ksu_file` 类型，同时保存一份原始策略副本，供后面的「伪装策略没被改过」使用。
5. **审计**：`kernel/sulog/` 记录三类事件（root 命令执行、su 兼容命中、控制命令提权），用户态可用 `ksud debug sulogd` 读取。

### 4.2 内核与用户态之间怎么说话

**没有设备节点**。`kernel/supercall/supercall.c` 用匿名 inode 创建名为 `[ksu_driver]` 的文件描述符，用户态先通过带两个魔数的 `reboot` 系统调用触发安装，再对这个描述符下发 ioctl。`uapi/supercall.h` 定义了 22 个主命令（取信息、上报开机事件、读写 App Profile、读写 feature、获取包装文件描述符、查符号等），当前接口版本为 6；`kernel/supercall/dispatch.c`（1138 行）是分发表，**每条命令都挂着一个权限检查函数**，区分「仅管理器」「仅 root」「管理器或 root」「任意进程」。

实际上有三条通道，别混为一谈：

| 通道 | 用途 | 证据 |
| --- | --- | --- |
| 匿名 inode 文件描述符 + ioctl | 主通道，几乎所有管理能力 | `kernel/supercall/`、`userspace/ksud/src/ksucalls.rs` |
| `reboot` 系统调用 + 魔数 | 安装上述文件描述符、SuSFS 命令 | `kernel/supercall/supercall.c`、`userspace/ksud/src/susfs/abi/syscall.rs` |
| `prctl` | 旧版本兼容探测，仅剩遗留痕迹 | `userspace/ksuinit/src/lib.rs` |

管理器身份靠**验签**：`kernel/manager/apk_sign.c` 手工解析 APK 签名块 v2，比对编译期写进内核的证书大小与 SHA-256；`throne_tracker.c` 扫描已安装应用完成「加冕」，包变动时由 fsnotify 监视器重扫。

### 4.3 隐藏检测痕迹的成套机制

这是本项目相对上游最显眼的增量，均有代码证据：

| 要藏的东西 | 做法 | 文件 |
| --- | --- | --- |
| SELinux 策略被改过 | 用保存的原始策略副本回答查询，并伪造 selinuxfs 状态页 | `kernel/feature/selinux_hide.c`（1284 行，最复杂的单文件） |
| 模块挂载点 | 过滤 `/proc/<pid>/mountinfo|mounts|mountstats` 中含 `/adb/modules` 的记录，注释明确针对全进程差分探测与 Android 17 隔离进程两类检测 | `kernel/feature/mount_hide.c` |
| 审计日志里的 su 域 | 钩 `slow_avc_audit`，把 SID 换成普通特权应用 | `kernel/feature/avc_spoof.c` |
| 内核版本 / CPU 身份 | 伪装 uname、MIDR、bogomips、hwcap、vDSO | `uts_spoof.c`、`extension/cpu_spoof.c`、`extension/version_spoof.c` |
| 模块本身 | 按应用配置卸载挂载、隐藏卸载路径、复用内核原生模块黑名单、删掉 LKM 在 `/sys/module` 的痕迹 | `kernel/feature/kernel_umount.c`、`module_blacklist.c`、`core/init.c` |

### 4.4 扩展框架（fork 自研的架构性改动）

`uapi/extension.h` 开头有一段很直白的说明：原先每个复杂子系统都自己占一个 ioctl 编号（KPM、多管理器、卸载路径、CPU 伪装……），现在统一收进单个 `KSU_IOCTL_EXTENSION`，负载前四个字节是扩展 ID，后面由各自的处理器解释。框架支持三类扩展形态、ABI 版本探测、能力位（可持久化 / 可按 UID / 需重启 / 被强制）、枚举与清除，还能用 `force_extension=` 启动参数覆盖。

目前注册的扩展有 6 个：KPM、CPU 伪装、卸载路径表、动态管理器、SuSFS、版本伪装。

### 4.5 兼容老内核的做法

- 大量按 `LINUX_VERSION_CODE` 条件编译（5.10 到 6.18+，覆盖 LSM 回调形态、`task_security_struct` 差异、seccomp 反向移植等），`Kbuild` 还会探测目标内核的函数签名与结构体字段，生成兼容宏。
- 通过 kallsyms 符号解析与 BTF（内核类型信息）拿未导出符号和结构体偏移，再用架构相关的页表改写手段打补丁；`kernel/hook/` 下有 arm64、x86_64、riscv64 三套实现。
- `ksuinit` 自己做 ELF 未定义符号重定位，加载失败时从内核日志读 vermagic 改写模块信息再重试，用来对付厂商内核版本串不一致。
- 文档说明 `main` 分支用 kprobe + tracepoint 运行时注册（无需改内核源码），非 GKI 与手动挂钩走远端的 `builtin` / `builtin-new` 分支；当前检出里旧的 `CONFIG_KSU_MANUAL_HOOK`、`ksu_trace.h` 已被移除，文档里专门留了一页废弃说明。

## 五、用户态：`ksud` 与 `ksuinit`

`ksud` 是部署到 `/data/adb/ksud` 的 Rust 命令行程序，既是开机各阶段的脚本执行器，也是管理员工具。顶层命令约 30 组，主要包括：模块安装/启用/卸载/Action/Lua 脚本、开机三阶段事件、boot 镜像修补与还原、LKM 加载与卸载、SELinux 策略修补、App Profile、feature 与 extension 开关、KPM 管理、SuSFS 全套配置、动态管理器注册表、软重启、resetprop、审计日志等。Android 端用完整命令集，PC 端（给 boot 镜像打补丁）用精简命令集。Rust 侧通过 `build.rs` 里的 bindgen 直接把 `uapi/` 头文件生成绑定，保证契约不会两边各写一份。

`ksuinit` 是开机最早期的静态程序，先挂载 procfs、加载 `/kernelsu.ko`、写模块黑名单，再 exec 真正的 `/init`。

**启动链**：内核把三段 `exec u:r:ksu:s0 root -- /data/adb/ksud ...` 注入 init 读取的 rc 内容（`kernel/runtime/ksud_integration.c`），于是 `post-fs-data`、`services`、`boot-completed` 三个阶段都能执行模块脚本；模块自己的 preinit 则由 `kernel/preinit/` 里那个用 nolibc 写的静态 runner 在更早的 init 阶段完成。

## 六、Android 管理器：从工具 App 变成内容平台

### 6.1 功能地图

基础能力齐全：root 授权与 App 列表、App Profile 编辑器、模块安装/开关/排序/仓库、刷入与内核修补、KPM 与 SuSFS 界面、内核模块与卸载路径管理、日志与模板、脚本执行、模块 WebUI 宿主、设置与多语言（48 个 `values*` 目录）。

近八次提交几乎全部集中在**主题商店 + 个性化外观**，逐条核实到的功能包括：

- 主题商店的自适应网格与详情页横向「胶片条」画廊；
- 主题设置分组与组内选项重排（Material / Miuix 两份界面同步改）；
- 作者关注（按「镜像源 + 作者身份」聚合，混合多源时隐藏按钮）；
- 成人内容分级门槛：首次进入需同意协议，同意记录刻意放在不参与备份的目录；
- 一次性密钥登录：App 显示设备码，用户在网页账号中心确认，App 轮询换取会话；
- 分布式主题上传：服务端下发多个边缘节点与票据，客户端实测速度选节点、分块并发、断点续传；
- 每台安装独立的轮换读取凭据，按站点哈希隔离存储，明确排除云备份与设备迁移；
- `sukisu-theme://open` 深链直达指定主题，且校验只允许跳到已配置源；
- 自定义外观叠层、主题包加密导入导出、四个底栏标签可换自定义图标、首页贴纸与沉浸式状态栏、主题上传快捷入口。

服务端默认地址写在 `ThemeStoreDefaults.kt`（`https://themes.neko.shirkneko.top:8443/`），账号、投稿、评论、消息、关注等接口走同一站点的 `account/api/`；模块仓库另走 `https://modules.kernelsu.org/`，App Profile 模板走 `kernelsu.org`。这些都是运行时可配置的多源设计，不是写死单一后端。

### 6.2 可选的 AI 助手

`manager/ai-api/` 是一个**始终存在、但不含实现**的桥接模块（SPI）：定义宿主能力接口、共享数据模型、GitHub Release 下载地址白名单校验。真正实现是可选的 `:ai` 模块或预编译 `ai.aar`，通过反射按类名发现；缺失时所有 AI 入口隐藏，App 照常编译。当前仓库里既没有 `manager/ai/` 目录也没有 `ai.aar`，按 README 说明完整实现位于另一个分支。

### 6.3 模块 WebUI 的前端库

`js/` 是发布到 npm 的 `kernelsu` 包（当前 3.3.0），给模块自带的网页提供 `exec`（root shell）、`spawn`（长进程流）、`fullScreen`、`toast`、`moduleInfo`，以及 `ksu.pm`（包管理）和 `ksu.io`（root 文件读写）门面。管理器在 `WebViewHelper.kt` 里用 `addJavascriptInterface` 注入 `ksu` 桥，两侧一一对应。

## 七、构建与发布链路

**本地开发**：`justfile` 提供两个快捷任务——`bk` 用 cross 交叉编译 `ksud`，`bm` 把产物拷成 `libksud.so` 放进管理器 JNI 目录再跑 Gradle 构建；`scripts/setup_cargo_config.py` 负责探测 Android NDK 生成交叉编译配置。

**内核产物**：`kernel/setup.sh` 把本仓库软链进内核源码的 `drivers/kernelsu`；`Kbuild` 列出约 55 个目标文件，按提交数、GitHub 最新发行和 git 标签计算版本号，把管理器包名与验签哈希注入模块；`build-all.sh` 系列用 DDK 批量构建 8 个内核版本的 `kernelsu.ko`（android12-5.10 到 android17-6.18）。`check_symbol` 工具会在构建后校验模块里未定义的符号能否在 vmlinux 中解析。

**CI 主链路**（`.github/workflows/build-manager.yml`，991 行、9 个 job）：生成临时签名证书并提取证书信息注入内核模块 → 计算版本号 → 构建 LKM / ksuinit / ksud（四个 target）→ Gradle 打管理器 APK（含「伪装包名」矩阵，构建前用 `manager/randomizer` 脚本全文替换包名）→ 重打包重签 → 发布滚动预览版 → 按架构拆分后分发。另有独立工作流负责 LKM、ksud、ksuinit、npm 发布和四类代码检查（clippy、rustfmt、clang-format、shellcheck）。

**打包脚本**：根目录 `repack_apk.py` 把各架构 `ksud` 塞进 APK 的 `lib/<abi>/libksud.so`，做 16 KB 页对齐并用 apksigner 重签；`split_apk_by_arch.py` 再把多架构包拆成单架构包以减小体积。

**最终产物清单**：`kernelsu.ko`（按内核版本分发）、`ksud`（多平台二进制，内嵌 busybox/ksuinit/内核模块）、`ksuinit`（四架构静态程序）、管理器 APK（正式包与伪装包名包）、修补后的 boot 镜像、npm 包 `kernelsu`。AnyKernel3 刷机包由外部 GKI 内核仓库生成，本仓库只提供识别与刷写逻辑。

## 八、和上游 KernelSU 的关系

**它是 fork，而且主动维持 fork 身份**，证据很硬：

- `uapi/feature.h` 第 14 行注释写明「本分支自有功能从编号 16 开始，上游从 0 往上分配，留空档避免 rebase 时编号被悄悄改动」；
- 提交历史里大量带 `(tiann/KernelSU#3969)` 之类编号的回移提交，最近一次提交正是这类；

## 十、结构性观察（供后续维护参考）

- **签名与版本强耦合**：管理器 APK 的证书哈希在编译内核模块时写死，管理器侧还有最低支持内核版本常量。换签名、伪装包名构建或内核/管理器版本错配，都会直接导致「管理器认不出 root」。CI 因此要在 PR 构建时先生成临时证书再把信息注入内核模块，这条链路不能省。
- **双 UI 实现的维护成本**：多数界面改动需要同时落地 Material 与 Miuix 两份文件，近期几乎每次管理器提交都体现这一点，是后续改动最容易漏改的地方。
- **跨内核适配面很广**：依赖大量未导出符号，靠 kallsyms + 类型信息 + 逐版本条件编译 + 三套架构的页表改写来覆盖 5.10 到 6.18+，每个新内核版本都可能触发一轮适配，这也是内核侧难以停更的原因。
- **能力边界在仓库外**：KPM、SuSFS 内核实现、完整 AI 助手、主文档站、AnyKernel3 刷机包都在别处。评估「这个项目能不能做 X」时，必须先确认 X 的实现落点在本仓库还是外部仓库。
- **文档偏薄**：仓库内只有 8 个双语 Markdown，安装与集成指南都指向外部站点，且没有任何文档构建或部署工作流；新人上手主要得读代码。
- **本地是干净的只读分析**：本次分析未修改任何源码、未执行构建或测试，只新增本文件与两处文档索引。
