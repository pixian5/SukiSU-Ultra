# v0.0.5 源码缺失结案：不再等任何外部机器

- 时间：2026-11-08 09:30（GMT+8）
- 用户指令：针对「v0.0.5 那条路线的源码还没交回来」——「你来解决」
- 边界：全程电脑侧只读/下载与写仓库，**没有对手机做任何写入**

---

## 一、结论先说

1. 那份**私有源码找不回来了**：它只存在于另一台云电脑的工作目录，从未提交、从未打包上传；那台机器不在本会话可访问的范围内，本会话唯一能连的云电脑是另一条技术路线的源码树，且本轮唤醒失败。
2. **但已经不需要它了**。我找到了公开的、在 4.14 内核上实现同一套扩展接口的完整源码（`iput-object/kernel_xiaomi_sm6250`，commit `9700db64...`），核对后把三个核心文件固化进了本仓库 `tools/camellian-susfs/reference/4.14-extension-uapi/`。以后要重建「SuSFS 隐藏」这条能力，输入全是公开仓库 + 本仓库文件，**不再依赖任何一台特定机器或另一个 AI**。
3. 因此把 **v0.0.5 从「候选镜像」正式除名**：镜像与文档保留作历史证据，标注「不可复现」，并关闭所有文档里「等另一台云电脑交源码」的待办。主线仍是 `camellian-susfs-v0.0.6`，不受影响。

---

## 二、找过哪些地方（逐项留证）

| 位置 | 结果 |
| --- | --- |
| GitHub 主仓库全部远端分支（含 3 个并行 AI 分支、`feat/susfs-4.14`） | 只有 v2.3.0 接口翻译层的移植包，没有 1.4.2 兼容层 |
| GitCode 镜像仓分支 | 只有 `main`，内容与 GitHub 主仓一致 |
| 对象存储全桶（`cst:xbz/` 递归列对象） | 只有两份早期交接补丁、两份本轮源码包、镜像与清单，无兼容层源码包 |
| 云电脑 `/workspace`（顶层目录、`export*`、`sukisu-fork`、`susfs4ksu`） | 是 v2.3.0 路线（`fs/susfs_abi.c`）的源码树，不是 1.4.2 兼容层；本轮唤醒这台机器超时 10 分钟 |
| GitHub Release `camellian-susfs-v0.0.5` 资产 | 只有镜像与 `SHA256SUMS.txt` |
| GitHub 代码搜索（扩展接口特征函数） | 找到公开的 4.14 等价实现（见下节） |

顺带核实了交接文档里的关键判断：`ShirkNeko/susfs4ksu` 的 `kernel-4.14` 分支确实**不含** `SUSFS_MAGIC`、`ADD_SUS_PATH_LOOP`、`KSTAT_SPOOF`，所以「换个 1.4.2 就够了」不成立，这也是当初必须自研兼容层的原因。

## 三、公开替代实现（已固化进仓库）

来源：`https://github.com/iput-object/kernel_xiaomi_sm6250`，分支 `base`，commit `9700db640bbb5b27dca74ea06450d4c59550ebcc`，内核版本 4.14.356（非 GKI），GPL-2.0。

| 本仓库文件 | 原始路径 | 大小 |
| --- | --- | --- |
| `tools/camellian-susfs/reference/4.14-extension-uapi/susfs.c` | `fs/susfs.c` | 59,404 B |
| `.../susfs.h` | `include/linux/susfs.h` | 7,450 B |
| `.../susfs_def.h` | `include/linux/susfs_def.h` | 5,665 B |
| `.../SOURCE.txt` | 来源、commit、许可说明 | — |

静态核对结果：

- 版本串 `SUSFS_VERSION "v2.3.0"`，与管理器的接口版本一致；
- `SUSFS_MAGIC 0xFAFAFAFA`、23 条 `CMD_SUSFS_*` 命令码、12 个 `KSTAT_SPOOF_*` 细粒度标志；
- 14 个 `void fn(void __user **)` 形式的新式命令入口（正是 SukiSU 扩展接口要求的签名）；
- 具备 `susfs_add_sus_path_loop`、`susfs_add_sus_kstat`、`susfs_get_enabled_features`、`susfs_show_version/variant`、`susfs_extra_works` 等；
- **缺 3 个**增强函数：`susfs_set_priority_uid_filter`、`susfs_parse_priority_app_strings`、`susfs_add_sus_avd_allowed_by_type`。这三者在 v0.0.5 里本来也是空壳，不影响主线隐藏能力；真需要时可从 SukiSU 的 GKI 分支补。

这份实现所在的源码树是 4.14 完整内核，等于把「4.14 兼容」这件事本身做完了；它**不是** v0.0.5 镜像里的那份私有兼容层，两者不会逐字节一致，也**没有在本项目里编译验证过**。它的价值是：往后任何人重建这条路，起点是公开、可审计、可追溯的源码，而不是一台找不到的机器。

## 五、自足的重建任务书（可直接交给任何 AI / 任何新云电脑）

> 目标：在红米 Note 10 5G（camellian，4.14.186，非 GKI）上重新编出带 SuSFS 隐藏能力的可刷启动镜像。**所有输入都是公开仓库或本仓库文件，不依赖任何历史云电脑。**

1. **源码**
   - 厂商内核：`https://github.com/MiCode/Xiaomi_Kernel_OpenSource`，分支 `camellian-t-oss`
   - SukiSU：`https://github.com/SukiSU-Ultra/SukiSU-Ultra`，分支 `builtin`（v4.3.0-r2 对应 `1cfa573`）
   - 原厂底包：`V14.0.4.0.TKSEUXM` 线刷包里的 `boot.img`，MD5 必须是 `f8e4f42a4538b03c519bb70921d88bcc`
   - 本仓库：`tools/camellian-susfs/patches/`（内核树与 SukiSU 树集成补丁）、`tools/camellian-susfs/kernel/`（v2.3.0 移植包）、`tools/camellian-susfs/reference/4.14-extension-uapi/`（上节的公开 4.14 实现）
   - 若坚持走 1.4.2 老路：`gitlab.com/simonpunk/susfs4ksu` tag `1.4.2-kernel-4.14`，但**必须自建扩展接口兼容层**，见 `docs/20261108-0350-SuSFS隐藏方案编译完成记录-Kimi-K3.md` 第 2 节
2. **工具链**：AOSP clang-r383902（clang 11.0.1）+ LLD 11；`binutils-aarch64-linux-gnu`、`bc`；保留量产 `CONFIG_LTO_CLANG=y` / `CONFIG_CFI_CLANG=y`
3. **配置**：从原厂 `boot.img` 内核里提取出厂 `ikconfig` 作底，再开 KSU/SuSFS；参考 `tools/camellian-susfs/config/ikconfig-v0.0.6-mainline.txt`
4. **集成**：应用两个集成补丁；`drivers/kernelsu` 软链接到 SukiSU 的 `kernel/`；`kernel/reboot.c` 的授权通道钩子与 `dispatch.c` 的默认应用配置回退**必须保留**，否则管理器授权会失效
5. **十个构建坑**：直接照 `docs/20261108-0350-...` 第 3 节执行（MILLET 关闭、DTS 的 `cust.dtsi` 引号、`headers_install` 先于全量编译、`sulog/event.c` 的 4.14 兼容等）
6. **打包**：`python3 tools/camellian/scripts/pack_boot.py <输出>`，12 项结构校验全 PASS；原厂内存盘、设备树、校验区段逐字节保留，AVB 尾部重定位
7. **发布**：GitHub Release（`pixian5/SukiSU-Ultra`）+ `SHA256SUMS.txt`，同步 GitCode；**不要往 `cst:xbz/camellian/boot-sukisu-susfs-lto-stockdtb.img` 这个固定名字写**，用带版本与校验值的路径
8. **验收**：编译返回 0、内核日志有 `susfs is initialized!`、管理器「工作中」、后台有 root 子进程、特性列表与四条不支持命令表现符合预期、Momo 复测记录；**真机刷入必须等用户明确说「刷机」**
