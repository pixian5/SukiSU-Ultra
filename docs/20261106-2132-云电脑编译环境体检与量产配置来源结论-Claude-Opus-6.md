只做了三件事：

1. 唤醒云电脑并做只读体检（系统、CPU、内存、磁盘、文件系统、已装工具）。
2. 在云电脑上做纯网络探测，只用几 MiB 的分段请求测速和查目录，**没有下载完整固件包**。

**没有做**：连接手机、读写手机分区、重启、刷写、下载 5.4 GB 完整固件、编译内核、修改任何内核源码或项目代码。

## 2. 官方指定的编译器到底还拿不拿得到

官方构建配置 `build.config.mtk.aarch64` 里写的是：

```sh
CLANG_PREBUILT_BIN=prebuilts/clang/host/linux-x86/clang-r383902/bin
LINUX_GCC_CROSS_COMPILE_PREBUILTS_BIN=prebuilts/gcc/linux-x86/aarch64/aarch64-linux-android-4.9/bin
```

这里的 `clang-r383902` 是「谷歌安卓源码树里一套预编译编译器所在目录的名字」，不是 Git 分支名。这一点容易查错，本轮实际验证过程：

- 直接查 `platform/prebuilts/clang/host/linux-x86` 仓库里名为 `clang-r383902` 的分支 → 返回空；该仓库共有 1079 个分支，确实没有这个分支名。
- 改查各分支下的目录列表 → `android11-release`、`android11-gsi`、`android11-dev` 三个分支里**都有** `clang-r383902` 这个子目录；`master` / `main` 分支里没有。
- 结论：**官方指定的那版编译器仍可获取**，要从 `android11-release` 分支取，而不是去 clone 一个不存在的分支。

网络可达性与速度（云电脑侧，只用小请求测）：

| 目标 | 结果 |
| --- | --- |
| `codeload.github.com` | 7.3 MB/s（下载内核源码压缩包时实测） |
| `android.googlesource.com` | 可达 |
| 清华 AOSP 镜像 `mirrors.tuna.tsinghua.edu.cn` | 可达 |

Ubuntu 软件源里可直接安装的替代品：`clang-14`、`clang-15`、`clang-16`、`clang-17`、`clang-18`、`lld`、`device-tree-compiler`、`bison`、`flex`、`bc`、`ccache`、`gcc-aarch64-linux-gnu`。也就是说，即便不去取那套老编译器，也能很快凑出一套可试编的工具链。

## 3. 一个此前没注意到的硬约束：这份配置只能用 clang 编译

`arch/arm64/configs/camellian_defconfig` 里的关键行：

```text
CONFIG_LOCALVERSION="-perf"
CONFIG_KALLSYMS_ALL=y
CONFIG_KPROBES=y
CONFIG_LTO_CLANG=y
CONFIG_CFI_CLANG=y
```

- `CONFIG_LOCALVERSION="-perf"` 与实机内核版本串 `4.14.186-perf-gf8d872e9279c` 中的 `-perf` 对上了，说明这份配置确实属于这台机器所用的量产分支，不是别的机型的配置。
- `CONFIG_LTO_CLANG` 指「链接时优化」，是把整个内核在链接阶段一起优化的功能，只有 clang 编译器支持；`CONFIG_CFI_CLANG` 指「控制流完整性检查」，同样是 clang 专属功能。
- 源码里另有一份纯 GCC 的构建配置 `build.config.mtk.aarch64.gcc`（`CC=gcc`，交叉编译器为 `aarch64-linux-gnu-6.3.1`）。但只要上面两项开着，**这份 GCC 配置就编不了 `camellian_defconfig`**，除非先手工关掉两项。

所以「图省事直接用系统自带的 GCC 交叉编译器」这条路走不通，clang 工具链是必需品，不是可选项。

> 这一条是根据源码配置做的静态判断，尚未经过试编验证，标记为待验证。

## 4. 「量产配置与开源配置不一致」这个悬念，不需要下载 5.4 GB 的包

这是本轮最重要的结论，也**修正了上一份文档里留下的待办**（原先写的是「还没从 boot.img 提取配置，所以差异未最终查实」）。

推理链条：

1. 实机当时能读到 `/proc/config.gz`。这个文件本身就是「内核编译时把自己的配置文件压缩后内嵌进内核，并允许在系统里读出来」的产物，对应配置项是 `CONFIG_IKCONFIG` 和 `CONFIG_IKCONFIG_PROC`。
2. 源码 `arch/arm64/configs/defconfig` 第 14、15 行正好是 `CONFIG_IKCONFIG=y` / `CONFIG_IKCONFIG_PROC=y`，与实机现象吻合，互相印证。
3. 从原厂固件包里的 `boot.img` 用内核源码自带的 `scripts/extract-ikconfig` 脚本提取出来的，**就是同一份内嵌配置数据**，只是换了一个读取入口。两者必然一致，下整包不会带来任何新信息。

因此权威结论现在就可以定下来，不必等固件包：

| 来源 | `CONFIG_KPROBES` | `CONFIG_KALLSYMS_ALL` |
| --- | --- | --- |
| 实机 `/proc/config.gz`（量产内核） | 未开启 | 未开启 |
| 开源 `camellian_defconfig` | 开启 | 开启 |
| 开源 `k6833v1_64_defconfig` | 开启 | 开启 |

补充检索：源码 `arch/arm64/configs/` 下所有配置文件里，**没有任何一处**写了 `# CONFIG_KPROBES is not set` 或 `# CONFIG_KALLSYMS_ALL is not set` 这样的显式关闭语句。也就是说，开源快照里不存在「某个文件悄悄把这两项关掉」的可能。

**差异只能来自小米内部未开源的构建覆盖步骤，或者量产时用的配置文件根本没有放进开源快照。** 这不是我们漏查了某个文件。

顺带一个对后续集成有利的推论：如果按开源 `camellian_defconfig` 自己编译，编出来的内核反而会打开 `CONFIG_KPROBES` 和 `CONFIG_KALLSYMS_ALL`——这正是 SukiSU-Ultra 主分支「自动挂钩」（依靠内核探针动态接管函数调用）所需要的两项。不过这台手机是 4.14 内核，走的是需要手动改源码挂钩的 `builtin` 分支，本来就不依赖这两项，所以开或不开都不构成障碍。

| 检查项 | 实测结果 |
| --- | --- |
| 文件大小 | `Content-Length: 5844714100` 字节（约 5.44 GiB） |
| 格式 | 前两字节 `1f 8b`，确实是 gzip 压缩的 tar 包 |
| 是否支持断点续传 | 支持（`Accept-Ranges: bytes`，分段请求返回 206） |
| ETag | `"34D8F9DE800F358F790967ADED38892C-400"` |
| MD5（官方公布） | `af69a61f516331e275f8580ea53d662f` |
| 本机 Mac → 官方下载站 | HTTP 403；拒绝页显示 `Forbid_code: 020200`、`Client_ip: 111.34.198.69`，属于下载站侧的地区/防盗链限制 |
| 云电脑 → 官方主站，单连接 | 约 22–27 KB/s |
| 云电脑 → 官方镜像站 `hugeota`，单连接 | 约 25 KB/s |
| 云电脑 → 官方站，12 条连接并发分段 | 合计约 273 KB/s（基本是「每条连接单独限速」的线性叠加） |

**所以本轮没有下载完整包。** 若将来确实需要原厂 `boot.img`（作为打包新内核或救砖的基线），有两条更合适的路：

1. **第三方镜像**：AndroidFileHost 与 mifirm.net 都收录了同名、同 MD5 的这个文件，可改从那里下载；下载后必须先校验 MD5 再用。
2. **直接从这台手机导出当前启动分区**：手机已有 root 权限、启动锁也已解锁，导出本机分区比任何网上固件都更贴近当前实际状态。但这需要连接手机并读取分区，属于「动手机」，本轮没有做，需要用户明确点头。

## 6. 现在的进度，以及下一步需要拍板的事

**已完成**：云电脑可用性与工具链来源、编译器硬约束、量产配置差异定论、固件下载可行性。

**仍未做**：安装工具链、在区分大小写文件系统上重新检出源码、试编原版内核、集成 SukiSU-Ultra、任何手机操作。手机仍是原来的 Magisk Alpha 环境，状态没有被改动。

### 选项 A（推荐）：先在云电脑上试编一次完全没改过的原版内核

- **具体做什么**：用系统软件源装好 `clang-14` / `lld` / `dtc` / `bison` / `flex` / `bc` / `ccache`，从 `android11-release` 分支取官方那套 `clang-r383902`，在云电脑区分大小写的 `/workspace` 里重新浅克隆 `camellian-t-oss` 分支，然后按官方配置跑一次编译。编译出来的内核不刷、不留到手机上。
- **代价**：约 2–4 GB 工具链下载；4 核机器编译一次约 20–60 分钟；4.14 老内核配新编译器很可能报错，需要逐个打补丁，不保证一次成功。
- **价值**：这是唯一能确认「这台环境到底能不能产出可启动内核」的办法，也是后面所有工作的前提。全程只在云电脑上，**完全不碰手机**。

### 选项 B：先把原厂固件基线弄到手

- **具体做什么**：从第三方镜像下载 5.4 GB 线刷包、校验 MD5、解出 `boot.img` 备用。
- **代价**：下载耗时不确定；而且按第 4 节结论，它对「配置差异」这个问题**没有增量信息**，主要价值是将来打包新内核或救砖时有个基线。

### 选项 C：先停在纸面，决定是否真的要换掉现有 root 方案

- **具体做什么**：什么都不动，我把「换成 SukiSU-Ultra 相对当前 Magisk Alpha 的得失、要承担的风险、出问题怎么退回去」整理成一份对照。
- **代价**：零风险；但「内核能不能编出来」这个不确定点仍然存在。

**为什么推荐 A**：手机目前已经有能用的 root，没有时间压力；真正卡住判断的是「这台 4.14 老内核能不能在这套环境里编译出来」，这件事不试编就只能一直猜。A 全程在云电脑上、不接触手机，代价可控，而且无论成功还是失败，结果都能直接决定后面还要不要继续投入。

## 7. 复核命令

云电脑体检（只读）：

```sh
uname -a; cat /etc/os-release; nproc; free -h; df -h /workspace
P=$(mktemp -d -p /workspace .caseprobe.XXXXXX); touch "$P/aA" "$P/Aa"; ls -1 "$P" | wc -l; rm -rf "$P"
for t in git clang gcc make llvm-nm ld.lld dtc bc bison flex ccache docker; do command -v "$t"; done
```

确认官方编译器所在分支：

```sh
git ls-remote --heads https://android.googlesource.com/platform/prebuilts/clang/host/linux-x86 | wc -l
curl -sS 'https://android.googlesource.com/platform/prebuilts/clang/host/linux-x86/+/refs/heads/android11-release/?format=JSON' | sed '1d' | grep -o 'clang-r383902' | head -1
```

本机源码配置检索：

```sh
cd /Users/x/code/camellian-kernel
grep -rn 'CONFIG_\(KPROBES\|KALLSYMS_ALL\|IKCONFIG\|LTO_CLANG\|CFI_CLANG\|LOCALVERSION\)' arch/arm64/configs/
grep -rn 'KPROBES is not set\|KALLSYMS_ALL is not set' arch/arm64/configs/
```
