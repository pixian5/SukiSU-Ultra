## 一、直接回答：这个版本的内核源码怎么找

### 1.1 先纠正一个常见误区

**小米不是按 MIUI 小版本号开源内核的**，所以不存在「`V14.0.4.0` 专属源码」这种东西。厂商按 **机型 + 安卓大版本 + 区域** 发布一份源码快照，一个快照覆盖该机型那一代系统下的多个小版本。找源码的正确姿势是先把版本码拆开：

| 片段 | 含义 |
| --- | --- |
| `V14.0.4.0` | MIUI 14 的第 4 次小版本更新，只用于找固件包，**不用于找内核源码** |
| `T` | 安卓大版本代号，`T` 对应 Android 13 |
| 中间几位 | 机型/项目代号（本机是 `camellian`） |
| `EU` | 区域，欧洲经济区（EEA）版本 |
| `XM` | 小米固定后缀 |

所以目标不是搜这个完整版本号，而是搜 **「camellian + Android 13（T）」**。这一步走错，就会一直找不到。

### 1.2 正确落点：官方开源仓库的 `camellian-t-oss` 分支

小米官方开源索引 `MiCode/Xiaomi_Kernel_OpenSource` 里，与这个机型相关的分支只有两个（用只列引用的方式查到，没有下载源码）：

| 分支 | 对应设备 | 安卓版本 | 提交号 |
| --- | --- | --- | --- |
| `camellia-r-oss` | Redmi Note 10 **4G 版**（另一台机器） | Android 11（R） | `4b6c276ac99c` |
| **`camellian-t-oss`** | **POCO M3 Pro 5G / Redmi Note 10 5G / Redmi Note 10T** | **Android 13（T）** | `f4e416aea06c` |

`camellian-t-oss` 最后一次提交是 2026-07-09，提交说明原文就写着「Kernel: Xiaomi kernel changes for POCO M3 Pro 5G / Redmi Note 10 5G / Redmi Note 10T Android T」。**千万别拿 `camellia-r-oss`**，那是 4G 版，内核与刷机包都不通用。

### 1.3 四条证据说明「找对了」

| 证据 | 官方源码分支 | 实机读数（上一轮已记录） | 是否对上 |
| --- | --- | --- | --- |
| 内核版本 | `Makefile` 里 `VERSION=4 / PATCHLEVEL=14 / SUBLEVEL=186` | `4.14.186-perf-gf8d872e9279c` | ✅ 完全一致 |
| 版本串后缀 | 区域配置里 `CONFIG_LOCALVERSION="-perf"` | 版本串里的 `-perf` | ✅ |
| 编译器 | 构建配置要求 `clang-r383902` | 内核版本串里 `clang version 11.0.1 (based on r383902)` | ✅ |
| 构建日期 | 官方线刷包文件名含 `20230914` | 内核编译时间 `Thu Sep 14 ... 2023` | ✅ |

### 1.4 为什么「精确到那次构建」做不到

拿内核版本串里的那串提交哈希 `f8d872e9279c` 去公开仓库反查，返回的是「找不到该提交」。这说明小米放出来的是某个时间点的**源码快照**，不是带完整提交历史的开发仓库。因此：能对齐到「机型 + 安卓大版本 + 内核版本 + 编译器 + 构建日期」，但**没法定位到与量产固件逐字节一致的那一笔提交**。这也是为什么后面必须做配置比对，不能拿来就编。

## 三、一个必须先解决的坑：源码配置和实机配置不一致

从源码分支里读到的两个关键差异：

| 配置开关 | 官方 `camellian_defconfig` | 实机 `/proc/config.gz`（上一轮实测） |
| --- | --- | --- |
| 运行时挂钩（`CONFIG_KPROBES`） | `=y`（开启） | `is not set`（**未开启**） |
| 内核符号全量表（`CONFIG_KALLSYMS_ALL`） | `=y`（开启） | `is not set`（**未开启**） |

而 `camellian_in_eea_defconfig` 只有 505 行、是一份**区域差异片段**（开头是 `CONFIG_CROSS_COMPILE`、`CONFIG_LOCALVERSION` 等），并不包含上面这两个开关。联发科平台的构建方式通常是「基础配置 + 区域片段」合并生成最终配置，所以：

- **不能凭某个 defconfig 推断量产内核到底开了什么**；
- 正确做法是从线刷包里解出 `boot.img`，用内核源码自带的 `extract-ikconfig` 脚本提取里面的配置，再与实机已记录的 `/proc/config.gz` 逐项比对，找出实际使用的那份配置组合；
- 有一个**值得验证的推测**：如果按官方 `camellian_defconfig` 重编，运行时挂钩和符号全量表可能是开启的，那么项目的常规分支（自动挂钩）也许能用，就不必走手动挂钩。但这只是推测，**必须实际编译并核对生成的配置才能下结论**，不能据此跳过手动挂钩的准备。

## 四、编译环境实测：本机不具备条件

### 4.1 本机读数

| 项目 | 实测 |
| --- | --- |
| 系统 | macOS 27.2，Apple Silicon（arm64） |
| 编译器 | Apple clang 21.0.0、GNU Make 3.81、系统自带 gcc/g++ |
| 交叉编译工具链 | **没有**：缺 `aarch64-linux-gnu-gcc`、`dtc`、`ninja`、`ccache`、`llvm-config` |
| Android 开发包 | 有 platform-tools（调试工具），**没有 NDK、没有 SDK 里的 CMake** |
| 容器 | Docker 客户端 29.9.2 已装，但**服务没启动**（连不上后台进程） |
| 其他 | Homebrew 7.0.12、git-lfs 3.8.1、Python 3.13 可用 |
| 磁盘 | 工作区可用约 254 Gi，空间足够 |

### 4.2 源码分支要求的工具链（原文）

`build.config.common`：

```
BRANCH=android-4.14
KERNEL_DIR=common
CC=clang
LD=ld.lld
CLANG_PREBUILT_BIN=prebuilts-master/clang/host/linux-x86/clang-r383902/bin
BUILDTOOLS_PREBUILT_BIN=build/build-tools/path/linux-x86
```

`build.config.aarch64`：

```
ARCH=arm64
CLANG_TRIPLE=aarch64-linux-gnu-
CROSS_COMPILE=aarch64-linux-androidkernel-
LINUX_GCC_CROSS_COMPILE_PREBUILTS_BIN=prebuilts/gcc/linux-x86/aarch64/aarch64-linux-android-4.9/bin
```

### 4.3 结论

**这台 Mac 本机编不了这颗内核**，三个硬原因：

1. 工具链是 **Linux x86_64 的预编译二进制**（路径里写死 `linux-x86`），包括特定版本的 clang r383902 与 gcc 4.9，macOS 上的 Apple clang 不能替代；
2. 本机是 **arm64** 芯片，即便装了 Linux 虚拟机，要跑 x86_64 的预编译工具链仍需指令集模拟，速度极慢；
3. 内核构建脚本依赖一套 Linux 主机工具与完整的 AOSP 预编译目录结构（`prebuilts-master/`、`build/build-tools/`），不是装个交叉编译器就能解决。

可行的三条环境路线：

| 路线 | 具体做法 | 代价 |
| --- | --- | --- |
| 云主机 / 物理 x86_64 Linux（最实际） | 租一台 Ubuntu x86_64，拉源码和工具链编译，编好把产物传回来 | 有成本；要传几个 GB 的文件 |
| 本机 Docker | 启动 Docker 服务，用 x86_64 的 Linux 镜像（`--platform linux/amd64`）跑编译 | 需要先启动服务；arm64 上模拟 x86_64，编译会很慢 |
| 第三方 ROM 的编译流水线 | 参考社区现成的构建脚本 | 面向 LineageOS，不是当前 MIUI 基线 |

## 八、结论与下一步（仍然不动手机）

**找得到，而且已经定位准了**：官方 `camellian-t-oss` 分支的 4.14.186、`-perf` 后缀、clang r383902、以及线刷包里的 `20230914`，四处都与这台手机对得上。找不到「V14.0.4.0 专属源码」不是方法错了，而是厂商本来就不按小版本开源。

**但编译环境本机不具备**：需要一台 Linux x86_64 机器加整套 AOSP 预编译工具链，Mac 本机只能做调研和文件核对。另外官方源码的默认配置与实机配置在「运行时挂钩」「符号全量表」两项上不一致，动手前必须用线刷包里的 boot 镜像做配置比对。

三个后续选项（都不碰手机）：

1. **到此为止**：信息已经齐了，手机继续照常用。
2. **把源码浅克隆下来做静态核对**（推荐）：花几个 GB 磁盘，把 `camellian-t-oss` 拉到本机，实际比对 defconfig、确认手动挂钩要改哪些文件、把集成清单列清楚。不动手机、不编译、零设备风险。
3. **搭 Linux x86_64 环境试编一份原版内核**：成本最高，需要云主机或容器、几个 GB 的工具链和较长编译时间，但能真正验证「能不能编出能开机的内核」以及 KPROBES 到底开没开。

推荐先做第 2 项：它正好把「配置不一致」这个悬着的问题查清楚，也能给出手动挂钩的准确落点，再决定值不值得投入第 3 项。

## 九、术语表

| 名词 | 含义 |
| --- | --- |
| 内核源码 | 编译手机内核（系统最底层程序）用的完整代码 |
| 源码快照 | 厂商在某个时间点打包放出的一份代码，不带完整开发提交历史 |
| 分支 | 同一个仓库里并行的不同代码版本，这里用来区分不同机型/安卓版本 |
| 只列引用 | 只读取远端分支名和提交号，不下载代码内容 |
| 浅克隆 | 只下载某个分支最新一次提交的代码，省去历史记录 |
| 区域片段 / defconfig | 内核编译时决定「哪些功能开启」的配置文件；联发科平台常把基础配置和各区域差异分开存放 |
| 运行时挂钩 / 手动挂钩 | 在内核函数执行时插入自己代码的两种办法：开机后动态注册，或直接改内核源码 |
| 符号全量表 | 内核里记录所有函数与变量地址的完整清单，某些补丁方案依赖它 |
| 线刷包 / 卡刷包 | 官方完整固件包：前者在电脑上线刷、含各分区原始镜像；后者在手机上通过恢复模式升级 |
| boot 镜像 | 开机时加载内核与初始系统的那一小块镜像，root 方案都改它 |
| 交叉编译工具链 | 在一种机器（这里是 x86_64 Linux）上生成另一种机器（手机 arm64）能运行的程序的编译器套装 |
| AOSP 预编译工具链 | 安卓开源项目提供的、固定版本的编译器与构建工具，路径和版本都由构建配置写死 |
| Docker / 容器 | 在本机里跑一个隔离的 Linux 环境；Apple Silicon 上跑 x86_64 镜像需要模拟，速度较慢 |
| MD5 | 文件完整性校验值，用来确认下载的文件没坏、没被改动 |
