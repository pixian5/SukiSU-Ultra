## 二、对方根因的核对结果

对方说根因是 `sucompat.c` 里：

```c
if (kern_path(KSUD_PATH, 0, &kpath) < 0)
    goto no_ksud;   // 把 su 改写成 sh
```

本机未修改的源码确实是 `kern_path(KSUD_PATH, 0, &path)`，`flags=0` 表示不跟随符号链接。**这一点对得上。**

但有两点它没有解释，可能影响 v4 是否真的修好：

### 1. 探测时的权限问题

`/data/adb` 权限是 `0700 root:root`。`su` 由 shell（uid 2000）或普通 APP 执行，`kern_path("/data/adb/ksud", ...)` 在**当前进程的 creds** 下会因为没有目录 traverse 权限返回 `-EACCES`，即使加了 `LOOKUP_FOLLOW` 也一样失败。

如果 `ksu_ksud_binary_exists()` 没有用 `override_creds(ksu_cred)`（或等效的 root creds）来探测，`goto no_ksud` 仍然会走到，su 仍然被改写成 sh。

### 2. `head -c 4 /system/bin/su` 报 ENOENT 无法用 sucompat 解释

`sucompat` 只拦 `execve`，不拦 `open()`。但 v3 上：

```
ls -l /system/bin/su     → 正常
stat /system/bin/su      → 正常
head -c 4 /system/bin/su → No such file or directory
```

说明还有一层**路径打开层**的问题（`sus_map` / `open_redirect` / 文件系统），与「su 被改写成 sh」是两件事。v4 只改了 sucompat 和 sus_path 白名单，**没有提到这一层**。

## 三、结论与建议

- v4 的产物本身没问题（校验、结构、标志、配置都过）；
- 但它是否能真正修好 su，**取决于上面两点**：探测权限是否已用 root creds、open 层是否还有隐藏；
- **在对方确认这两点之前，不建议刷**——刷了可能还是 `su -c id` 失败，白折腾一次。
