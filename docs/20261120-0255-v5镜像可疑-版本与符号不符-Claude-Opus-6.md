# v5 镜像可疑：内核版本与 `ksu_handle_open` 符号对不上

- 时间：2026-11-20 02:55（GMT+8）
- 镜像：`boot-sukisu-susfs-allowlist-fix-v5.img`
  - 67,108,864 字节，MD5 `87163d9525870543214ff12a33213f33`
  - SHA256 `ebf453f15ff676d31263488e7bf019a7ef40e1f5b122d706741190907a6ae1a4`（与对方一致）
- 结论：**校验值通过，但内核版本和核心新增符号对不上，疑似上传的不是它验证的那份**

---

## 一、版本号异常

| 版本 | 内核 build |
| --- | --- |
| v4 | `#4 SMP PREEMPT Fri Nov 20 01:16:56` |
| **v5（S3 下载的这份）** | **`#7 SMP PREEMPT Fri Nov 20 02:18:21`** |

对方在 v5 说明里没有写 build 号，但按 v4 的 `#4` 推算，v5 至少是 `#5`。这份是 `#7`，说明中间还有 `#5`、`#6` 两次编译，或者上传的文件不是它验证的那一次产物。

---

## 二、核心修复的符号缺失

v5 的关键改动是给 `do_sys_open()` 加 `ksu_handle_open()`。但在这份镜像的内核里：

```
strings Image | grep -iE 'handle_open|ksu_handle'
→ ksu_handle_input
→ ksu_handle_umount
（没有 ksu_handle_open）
```

`CONFIG_KALLSYMS_ALL=y` 下，`ksu_handle_input`、`ksu_handle_umount` 这类名字都能找到；新增的 `ksu_handle_open` 却找不到。对方给的反汇编是 `bl <ksu_handle_open>`（不是内联），按这个逻辑符号应该存在。

**两种可能**：

1. 上传的 `ebf453f1…` 不是它验证的那次编译产物（`#7` vs 它说的版本）；
2. `ksu_handle_open` 实际没编进去，v5 的核心修复不在这份镜像里。

## 四、结论

**不建议刷这份 v5**。校验值一致只能证明「下载没坏」，不能证明「它就是对方验证的那份」。

需要对方确认：

1. S3 上 `ebf453f1…` 这份镜像对应的内核 build 号是 `#几`；
2. `ksu_handle_open` 在它验证的 v5 里的地址是多少（`grep ksu_handle_open System.map` 或 `nm vmlinux | grep ksu_handle_open`）；
3. 如果它验证的产物里该符号存在，而这份没有，请重新上传正确的文件并给出内核 build 号。
