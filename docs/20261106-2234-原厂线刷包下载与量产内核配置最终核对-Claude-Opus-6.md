## 0. 结论速览

**下第一个：线刷包（`.tgz`，5.4 GB），不要下卡刷包。** 已经下好并校验完成。

理由很简单：我们下一步要做的是「把自编内核打包成手机能用的启动分区镜像」，需要的基线材料是**原厂 `boot.img`**（启动分区镜像，含原厂内核和内存盘）。线刷包里 `images/boot.img` 直接就有；卡刷包在这台双槽位手机上通常是 `payload.bin`（增量升级载荷），要额外工具解、且不保证能拿出可直接改写的启动分区镜像。线刷包还附带全部分区镜像和官方刷机脚本，是将来救砖回退的完整材料。

**意外收获（本轮最重要的技术发现）**：从原厂固件内嵌的内核配置里，不但最终坐实了「量产配置与开源配置不一致」，还发现**上一轮我对编译器的「更正」本身是错的**——量产内核确实启用了 clang 的链接时优化，只是开源配置文件漏抄了父开关。详见第 6、7 节，前两份文档已同步加更正提示。

## 2. 该下哪一个：明确结论与理由

| | 线刷包（第一个，`.tgz`） | 卡刷包（第二个，`.zip`） |
| --- | --- | --- |
| 大小 | 5,844,714,100 字节（5.4 GB） | 3,818,027,879 字节（3.6 GB） |
| 安装方式 | 电脑用 fastboot 直接写各分区 | 手机 Recovery / 系统更新安装 |
| 启动分区镜像 | **直接提供 `images/boot.img`** | 通常是 `payload.bin`，需额外解包 |
| 完整分区镜像 | 有（救砖、回退可用） | 没有 |
| 官方刷机脚本 | 有 | 没有 |

四条理由：

1. **直接的打包基线**：把自编内核换进原厂启动分区镜像，需要原厂的 `boot.img` 来取内存盘（ramdisk）和分区布局。线刷包开箱即用。
2. **卡刷包多一道工序且不确定**：这台手机是双槽位（此前 fastboot 读到 `slot-count: 2`），卡刷包多为 A/B 升级载荷，要专门工具解，解出来的还不一定是能直接改写的启动分区镜像。
3. **救砖与回退材料**：完整分区镜像是「刷坏了怎么退回去」的物质基础，上一轮推荐先做风险评估，这份材料正好补上。
4. **代价很小**：只多 1.8 GB，按实测速度多约 3 分钟。

> 补充：如果目标只是「读量产内核配置」，其实两个包都不用下——实机 `/proc/config.gz` 已经给出了。下包是为了**打包基线和救砖材料**。

## 6. 量产内核配置：三来源交叉验证，结论最终坐实

用内核源码自带的 `scripts/extract-ikconfig`（从压缩内核里提取编译时内嵌的配置）成功导出 5486 行配置。这是**独立于手机**的第二个来源。

| 来源 | `CONFIG_KPROBES` | `CONFIG_KALLSYMS_ALL` |
| --- | --- | --- |
| 实机 `/proc/config.gz` | 未开启 | 未开启 |
| **原厂 `boot.img` 内嵌配置** | **未开启** | **未开启** |
| 开源 `camellian_defconfig` | 开启 | 开启 |
| 我们编译用的最终配置 | 开启 | 开启 |

两个独立来源互相印证，此前「量产配置与开源配置文件不一致，差异来自小米内部未开源的构建覆盖步骤」的判断**最终坐实**。开源配置文件里也确实找不到任何显式关闭这两项的语句。

顺带再次确认：按开源配置自编的内核会打开这两项，而 SukiSU-Ultra 的 `builtin` 分支走手动挂钩，本来就不依赖它们，所以开或关都不影响集成。

## 7. 再次更正：关于「是否必须用 clang」的最终定论

这个问题前后判断过三次，现在用原厂配置把根因彻底查清了：

| 时间 | 当时的判断 | 后来如何 |
| --- | --- | --- |
| 21:32 | 「必须用 clang」——依据是开源配置文件里 `CONFIG_LTO_CLANG=y`、`CONFIG_CFI_CLANG=y` | 结论对，但推导依据不完整 |
| 22:01 | 「不必 clang，那两行是历史残留」——依据是我们构建时它们被清成了 `CONFIG_LTO_NONE=y` | **错误**，漏看了父开关 |
| 22:34 | 量产构建确实必须用 clang；开源配置文件不完整 | 最终结论 |

原厂内嵌配置的真实内容：

```text
CONFIG_LTO=y                    ← 父开关
CONFIG_LTO_CLANG=y
CONFIG_CFI=y                    ← 父开关
CONFIG_CFI_CLANG=y
CONFIG_CFI_CLANG_SHADOW=y
# CONFIG_LTO_NONE is not set
```

而开源 `camellian_defconfig` 里**只有** `CONFIG_LTO_CLANG=y`、`CONFIG_CFI_CLANG=y`，**漏了 `CONFIG_LTO=y` 和 `CONFIG_CFI=y`**。

在 4.14 的 `arch/Kconfig` 里，`config LTO` 是一组互斥选项的总开关，`LTO_NONE` / `LTO_CLANG` 是它的子项。父开关没被选中时，配置展开会把互斥组回退到默认值 `LTO_NONE`，子项随之被清掉——这正是我们前两轮编译时看到的现象。

**因此**：

- 量产内核确实是用 clang 的链接时优化（LTO，把整个内核在链接阶段一起优化）和控制流完整性检查（CFI，运行时校验函数调用合法性）编译的，**「必须 clang」成立**。
- 22:01 报告里说「那两行是历史残留、不构成编译器约束」是错的，已在那份文档里加更正提示。
- 我们编译出的内核**没有** LTO/CFI，与量产内核在优化和加固上不同；这属于优化/安全加固差异，不影响功能，但将来若要更贴近原厂，需要在配置里补上 `CONFIG_LTO=y` / `CONFIG_CFI=y` 再重编。
- 这又是一条「小米开源快照与量产构建不自洽」的证据：和此前的私有模块缺失、板级配置文件缺失、私有符号配置漏开是同一类问题。

教训：配置文件里写了某个 `CONFIG_XXX=y` 不代表它生效；但反过来，**看到它在自己的构建里没生效，也不能直接断定它是残留**——要先查它的父开关和互斥组，最好拿量产产物反查。

## 8. 官方刷机脚本里发现的风险点（将来真要刷机时很重要）

`flash_all.sh` 显示：

- **双槽位**：`boot_a` 和 `boot_b` 都要刷，另有 `vbmeta_a` / `vbmeta_b`。
- **校验分区**：脚本会刷 `vbmeta.img`、`vbmeta_system.img`、`vbmeta_vendor.img`。自编启动分区镜像若不处理校验，很可能起不来——这是将来自刷内核最大的一个坎。
- **防回滚检查**：脚本开头读 `fastboot getvar anti`，存在安全版本（anti-rollback）限制。
- 同目录另有 `flash_all_lock.sh`（会重新锁上启动锁），**绝不能用于跨区域或自编固件刷写**。

这些都是「要不要真的刷」这个决策里必须写进风险清单的内容，本轮只是读脚本，没有执行任何一条。

## 9. 这批材料能做什么、不能做什么

**能**：作为把自编内核打包成启动分区镜像的基线（内核 + 内存盘 + 设备树布局）、作为救砖回退的完整固件、作为量产配置的独立核对来源。

**不能**：直接刷进手机（本轮没做任何打包或刷写）；也不能据此判断自编内核在真机上能否正常启动——校验分区、防回滚、双槽位、手动挂钩运行时行为都还没验证。
