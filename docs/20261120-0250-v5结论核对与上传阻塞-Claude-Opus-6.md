# v5 结论核对：su 其实是 sh，上传一度阻塞

- 时间：2026-11-20 02:50（GMT+8）
- 背景：v5 完成后对方说明根因与修复，同时 S3 未上传

## 一、实测确认「su 其实是 sh」

在 v3 上执行：

```
stat /system/bin/sh  → 328384
stat /system/bin/su  → 328384（被 ksu_handle_stat 改写成 sh）
ls -l                → 两者都是 328384
su -c id             → No such file or directory
sh -c id             → 正常
```

原厂 ramdisk 里没有 su；`stat/ls` 看到的 328384 字节文件是 sh。`head` 没有 open 钩子，读真实路径报 ENOENT。对方的三层解释成立。

## 二、对第 1 点质疑的回应

对方说明探测发生在 `escape_with_root_profile()` 之后（uid 0 + `CAP_DAC_READ_SEARCH`），`/data/adb` 的 0700 不挡。**我的质疑不成立，接受。**

## 三、v5 修复方向

- `do_sys_open()` 加 `ksu_handle_open()`（只处理只读打开）；
- `fs/exec.c` 去掉重复钩子；
- 白名单加固（19 项单元测试）。

## 四、上传

对方按「用完即删」清掉了 S3 凭证，v5 一度无法上传；后续已上传（见 v5 镜像验证报告）。
