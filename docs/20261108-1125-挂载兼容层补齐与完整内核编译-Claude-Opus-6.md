## 一、先更正一个错误结论

上一轮 `docs/20261108-1022-公开4.14扩展接口编译验证-Claude-Opus-6.md` 说「9 个外部符号里 7 个没有实现、链接必然失败」。**这个结论是错的**，本轮逐行复核后更正如下：

| 分类 | 符号 | 实际情况 |
| --- | --- | --- |
| 头文件里的内联函数 | `susfs_is_current_proc_umounted`、`susfs_is_current_proc_umounted_app` | `susfs_def.h` 里就是 `static inline bool` 定义 |
| 同一个文件里的函数定义 | `susfs_is_inode_sus_kstat`、`susfs_open_redirect_spoof_do_sys_openat` | `susfs.c` 里已定义（分别带 `__attribute__((hot))`、结构体指针返回） |
| 只是注释 | `susfs_exit` | 一行 `//void __init susfs_exit(void)`，不是调用 |
| 现有补丁已提供 | `ksu_handle_setresuid`、`susfs_is_current_ksu_domain` | 内核树 / SukiSU 树补丁里有 |
| **真正需要外部提供** | `susfs_get_non_sus_mnt_id_from_mnt`、`susfs_get_non_sus_vfsmnt_from_vfsmnt` | `susfs.c` 里有 `extern` 声明，实现在公开内核树的 `fs/namespace.c` |

误判原因：上一轮的静态检查只匹配「返回类型 + 函数名 + 左括号」这一种定义形式，漏掉了带编译属性、结构体指针返回和头文件内联的情况，还把注释里的名字算成调用。旧文档已加醒目更正段，保留原文不篡改历史。

**结论：适配工作量比上一轮说的小得多，只需补 2 个函数。**

## 二、适配层的来源与实现

新增 `tools/camellian-susfs/reference/4.14-extension-uapi/mnt_compat.c`（GPL-2.0，中文注释）：

- 两个函数体**原样取自** `iput-object/kernel_xiaomi_sm6250` @ `9700db64` 的 `fs/namespace.c`，只补齐了 include 与注释，没有自己编逻辑；
- 作用是沿挂载父链向上回溯，取回未被 SuSFS 伪装成超大编号（`>= DEFAULT_KSU_MNT_ID`）的原始挂载编号 / 原始 `vfsmount`，供隐藏挂载功能使用；
- 依赖的 `struct mount`、`real_mount()`、挂载哈希锁来自 `fs/mount.h`（厂商 4.14 树里存在），`DEFAULT_KSU_MNT_ID` 已在参考 `susfs_def.h` 里定义；
- 文件里明确写了「编译与链接验证用的适配层，功能未在真机验证，不要当成可用隐藏能力」。

## 三、验证脚本升级

`tools/camellian-susfs/scripts/verify-public-uapi.sh` 本轮改动：

1. 把适配层一起送进内核树 `fs/susfs_mnt_compat.c`，并在 `fs/Makefile` 追加编译目标；退出时连同临时 `.o` 一起清理，仍保证内核树还原；
2. 并发数改为 `JOBS` 可调（默认 2）——上一轮 `-j4` 在这台 7.7 GB 的机器上卡在依赖扫描阶段近 20 分钟；
3. **两段式编译**：先单独编译 `fs/susfs.o` 与 `fs/susfs_mnt_compat.o`（几秒出结论），再跑完整内核编译。即使全量阶段卡住，也能留下语法/字段层面的准确结果。

## 四、版本号

本轮新增了内核适配源码，按「每轮修改源代码就把版本号加 0.0.1」的规则，`tools/camellian-susfs/VERSION` 由 `0.0.6` 升到 **`0.0.7`**。

需要说明的取舍：`0.0.6` 是另一台云电脑发布的**主线镜像标签**，本轮的 `0.0.7` 只代表本工具包/备用路线的迭代，不代表主线镜像被替换，也没有占用 `camellian-susfs-v0.0.7` 发布标签。若以后这条路线真要发候选，再单独对齐标签与校验值。

## 五、编译结果

**阶段 1（单文件编译）已完成，返回码 0。** 云电脑日志出现 `CC      fs/susfs.o` 与 `CC      fs/susfs_mnt_compat.o`，全程零 error。这证明公开的扩展接口实现加上新写的挂载编号兼容层，在厂商 4.14.186 上的语法、结构体字段、宏、相对头文件都兼容，`struct mount` / `real_mount()` / 挂载哈希锁 / `DEFAULT_KSU_MNT_ID` 这些依赖也都在。`llvm-nm` 查看两个目标文件的未定义符号时，没有发现残留的 `susfs_*` / `ksu_*` 外部依赖。

**阶段 2（完整内核编译）未通过**：`JOBS=2` 正常推进到 `CC fs/stat.o` 后报 2 个编译期错误，`make` 以 Error 2 退出，没有生成新的 `Image.gz`：

```
fs/stat.c:43:41: error: use of undeclared identifier 'TASK_STRUCT_NON_ROOT_USER_APP_PROC'
fs/stat.c:44:30: error: use of undeclared identifier 'INODE_STATE_SUS_KSTAT'
```

根因不是链接缺符号，而是**内核树里还留着另一条路线的 SuSFS 钩子**：旧版 `susfs_def.h` 用 `INODE_STATE_SUS_PATH/KSTAT/...`（`BIT(24)`–`BIT(28)` 打在 `inode->i_state`）与 `TASK_STRUCT_NON_ROOT_USER_APP_PROC`（`BIT(24)` 打在 `task_struct->susfs_task_state`）；公开实现改用 `TIF_PROC_*` 线程标志位（33–35）和另一套 stat 标记，头文件里没有这些旧宏。

受影响的是内核树里被旧补丁改过的 7 个文件：`fs/stat.c`、`fs/readdir.c`、`fs/namei.c`、`fs/statfs.c`、`fs/proc/fd.c`、`fs/proc/task_mmu.c`、`fs/dcache.c`，共 **+273 行纯新增**的旧钩子（见 `tools/camellian-susfs/patches/experimental-kallsyms-off/camellian-tracked.patch`）。要真正让公开实现编出完整内核，需要把这 7 处钩子逐一遍到新接口或整体回滚后重接，属于一次中等规模移植，且全部要重新做真机验证。

**结论**：单文件兼容不等于整棵树兼容。公开的 4.14 扩展接口实现是合格的重建素材，但**不能直接换三个文件 + 一个兼容层就编出可刷镜像**；本轮验证到「编译期宏不兼容」这一层就足够了。主线 `camellian-susfs-v0.0.6` 不受影响，仍是唯一候选。

```
日志   /workspace/verify-uapi.log（云电脑）
返回码 /workspace/verify-uapi.rc = 143
```

> 返回码 143 是收尾时手动终止挂起任务得到的；真正的失败原因是上面 2 个编译错误导致的 `make Error 2`，日志里明确记录了「错误行数：2」。编译失败后 `make` 还挂着几个并行收尾任务（`Waiting for unfinished jobs`），终止后脚本才走完收尾逻辑。

**收尾检查（已完成）**：脚本退出后，用备份目录把 5 个文件逐一还原并核对 MD5，全部一致——`fs/susfs.c` `473f588a...`、`fs/susfs_abi.c` `f603a766...`、`include/linux/susfs.h` `475aa865...`、`include/linux/susfs_def.h` `96c8da19...`、`fs/Makefile` `cd5bcfef...`；新增的 `fs/susfs_mnt_compat.c` 与临时 `.o` 已清理，无残留进程。**云电脑内核树回到原样，主线构建不受影响。**
