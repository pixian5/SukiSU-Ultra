# 双槽 / 虚拟 A/B 分区下的单槽试刷与回退风险对照

> 撰写时间：2026-11-06 23:14（模型：Claude-Opus-6）
> 对象：红米 Note 10 5G（`M2103K19C`，机型代号 `camellia` / `camellian`，联发科 MT6833，Android 13，MIUI `V14.0.4.0.TKSEUXM`）
> 边界：本文只做机制核对与方案对照。**没有连接手机写入任何分区、没有切换系统槽、没有刷机。** 文中出现的命令都是「将来真要动手时才执行」的示例，本次一条都没有执行。

## 0. 先回答那个问题

**你的判断方向是对的**：试刷自定义内核时，应该只写当前系统槽的那一份启动分区，把另一份原封不动留着当后路。我上一轮说「官方全量恢复脚本会刷两个槽」，那是**全量恢复**场景，和**试刷**是两个目标，混在一起讲容易误导，这里更正。

**但「失败就从另一个分区启动」这句话需要补三个前提**，否则真出问题时可能救不回来：

| 前提 | 为什么不能省略 |
|------|----------------|
| 切槽必须**显式下命令**，不会自动发生 | 启动失败时，引导程序多数情况下只会反复尝试当前槽；有些实现连续失败几次会回退，但次数和行为不保证，不能当保险 |
| 另一个槽必须是**可启动状态** | 这台机器的另一个槽通常是上一次系统更新前的旧系统，可能带着「未成功启动」标记，也可能和当前用户数据不兼容 |
| 切槽动的不只是启动分区 | 用户数据分区是两个槽**共用**的，切到旧系统可能读不懂现有数据而卡开机；虚拟 A/B 的快照合并状态也会被牵动 |

所以更稳妥的顺序是：**先把原厂启动镜像刷回同一个槽**（几秒钟、不动别的分区），切槽只作为第二层保险。第 5 节给出完整决策顺序。

| 证据 | 读到的值 | 说明 |

| `ro.boot.dynamic_partitions` | `true` | 系统分区放在一个叫 `super` 的动态分区里，分区表可以在系统内调整 |

刷机脚本 `flash_all.sh` 里既有 `fastboot flash boot_a ...` / `boot_b ...`，也有 `fastboot flash super ...`（不带槽后缀），和分区表完全对得上。

## 2. 「虚拟 A/B」到底影响哪些分区（最容易误解的一点）

**虚拟 A/B**（Virtual A/B，也写作 VAB）是安卓在系统更新时省空间的一种做法：系统分区（`system`、`vendor`、`product` 等逻辑分区）都放在同一个物理分区 `super` 里，两套系统通过**写时复制快照**共用存储，而不是把两套完整系统各存一份。系统更新把新版写进非当前槽时，先记录「哪里和旧版不一样」，等新版启动成功后再把差异合并（这个动作叫快照合并）。

**动态分区**（Dynamic Partitions）指 `super` 里面的逻辑分区大小可以在系统内调整，不再由固定分区表写死。

关键区别在这里：

- **启动相关分区是真双份**：`boot_a` / `boot_b` 是两块**物理上独立的存储区域**。写 `boot_b` 完全不会碰到 `boot_a`。所以「只刷一个槽、另一个槽原封不动」这条策略在启动分区上是**成立的**，也确实是试刷自定义内核的正确做法。
- **系统分区不是两套独立系统**：`super` 是共用的，`userdata`（用户数据）也是共用的。切到另一个槽时，读的是同一个 `super` 里另一组逻辑分区的状态，加上可能还没合并完的快照；用户数据还是同一份。这就是「切槽回退」比「刷回原厂启动镜像」麻烦得多的根本原因。

一句话概括：**VAB 影响的是系统分区的存放方式，不改变启动分区双份独立这个事实；用户说的「一次只刷一个」针对启动分区，完全正确。**

## 3. 三个场景必须分开看

| 场景 | 目标 | 对槽位做什么 | 官方脚本的行为 |
|------|------|--------------|----------------|
| **① 试刷自定义内核**（本轮准备的镜像属于这一类） | 验证自编内核能不能启动，随时能退回 | **只写当前槽 `boot_b`**；`boot_a` 一个字节都不动；不动 `super`、不动 `vbmeta`、不切槽、不做系统更新 | 不使用官方脚本，手动单条命令 |
| **② 官方全量恢复 / 救砖** | 把整机恢复成出厂状态，放弃「留一个好槽」 | `boot_a`、`boot_b` **都刷**；`super` 重建；`userdata` 重写（**数据全清**）；最后 `set_active a` 切到 a 槽 | `flash_all.sh` 就是这么写的，合理，因为它的目标本来就是「两台都变成原厂」 |
| **③ 系统更新合并快照** | 更新完成后把另一槽同步到新版 | 由系统在后台完成，可能持续到下次重启之后 | 不涉及线刷；试刷期间不要触发 |

上一轮我把 ② 的「刷两个槽」当成风险点来讲，但没说清它是**全量恢复**，容易让人以为试刷也得刷两个槽。这里明确：**① 和 ② 的目标相反，槽位策略自然相反。**

## 4. 单槽试刷的正确写法（将来动手时）

当前槽是 **b**，所以目标分区是 `boot_b`：

```sh
# 只写当前槽；明确写出槽后缀，不要写不带后缀的 "boot"
fastboot flash boot_b boot-sukisu-stockdtb.img
```

**为什么一定要带 `_b`**：不带槽后缀的 `fastboot flash boot ...` 到底写哪一个分区，由这台设备的引导程序里的分区别名映射决定——有的写当前槽，有的会同时写两个槽。只有明确写 `boot_b`，才能确定「只动一个槽」，事后也好核对。

试刷期间**明确不要做**的事：

- 不要刷 `boot_a`（留作回退基线）
- 不要刷 `vbmeta_a` / `vbmeta_b`（除非第 6 节说的启动失败兜底）
- 不要刷 `super`、不要 `erase metadata`、不要 `flash userdata`
- 不要 `fastboot --set-active=a`（除非执行第 5 节的第二层回退）
- 不要在这期间做系统更新（会触发虚拟 A/B 的快照合并）

动手前建议先记录这几个只读变量，出问题时能对照：

```sh
fastboot getvar all          # 重点看 current-slot、slot-count、unlocked、secure、anti
fastboot getvar anti         # 防回滚计数，官方全量恢复脚本会读它
```

## 5. 回退路径：按这个顺序，不要跳级

### 第一优先：同槽刷回原厂启动镜像（最快、最干净）

因为只改过 `boot_b`，把原厂镜像刷回 `boot_b` 就能完全回到试刷前的状态。不动 `super`、不动用户数据、不切槽、不用重启到另一套系统：

```sh
fastboot flash boot_b boot.img        # 原厂镜像，MD5 f8e4f42a4538b03c519bb70921d88bcc
fastboot reboot
```

如果试刷时还动过 `vbmeta_b`，要**对称地刷回**原厂 `vbmeta.img`，否则校验状态会一直停在「已关闭」：

```sh
fastboot flash vbmeta_b vbmeta.img
```

### 第二优先：切到另一个槽（只在第一优先不可用时）

```sh
fastboot --set-active=a
fastboot reboot
```

执行前必须确认四件事，缺一件就别切：

1. **a 槽确实有一套完整、成功启动过的系统**，不是「上次更新写了一半」的状态。刷机模式变量里能看槽位标记（是否标记为成功启动 / 是否可启动）。
2. **a 槽的系统版本能读懂当前 `userdata`**。用户数据分区是共用的，跨大版本回退（例如从较新的系统回到较旧的系统）常常因为数据格式、密钥库版本不兼容而卡在开机动画，最坏情况要清数据。
3. **当前没有进行到一半的虚拟 A/B 快照合并**。合并过程中切槽，可能让两个槽的系统都处于不一致状态。
4. **切槽会把「当前槽」改成 a**，之后所有不带后缀的刷写命令含义都变了，后续操作必须重新确认槽位。

另外：引导程序连续启动失败后自动回退到另一槽的行为，在这台联发科平台上没有确认过，**不能当作保险机制依赖**。

### 第三优先：官方线刷包全量恢复

前两条都失效（例如连刷机模式都进不去、或者启动分区被写坏到无法回写）时，用官方线刷包的 `flash_all.sh`。代价要提前认清：

- `userdata` 会被重写，**用户数据全部清空**；
- `metadata` 会被擦除；
- `boot_a` 和 `boot_b` 都会被刷成原厂镜像，两个槽都不再是「留着的后路」；
- 会刷 `vbmeta` 系列镜像，恢复完整校验；
- 脚本开头会读 `fastboot getvar anti` 并和 `CURRENT_ANTI_VER=1` 比较，**如果手机的防回滚计数已经大于 1，脚本会拒绝执行**；
- 脚本结尾执行 `fastboot set_active a` 并重启，也就是恢复完从 a 槽启动。

### 决策顺序（文字版）

> 起不来 → 还能进刷机模式吗？
> 能 → 直接把原厂 `boot.img` 刷回 `boot_b` → 重启 → 结束。
> 刷回后仍起不来 → 检查是否动过 `vbmeta_b`，动过就把原厂 `vbmeta.img` 刷回 → 重启。
> 仍不行 → 确认 a 槽满足上面四个前提 → `set_active a` → 重启。
> 连刷机模式都进不去，或两个槽都坏了 → 官方线刷包全量恢复（接受清数据）。

## 6. 启动校验、签名与防回滚

### 6.1 原厂启动镜像里的校验结构（本轮实测）

**安卓启动校验**（Android Verified Boot，缩写 AVB）是开机时逐级核对分区内容是否被改过的机制。原厂 `boot.img`（67,108,864 字节，正好 64 MiB）的尾部结构实测如下：

| 项目 | 值 |
|------|-----|
| 启动镜像头 | `ANDROID!`，版本 2，页大小 2048 |
| 内核区 | 偏移 2048，13,342,418 字节（gzip 压缩内核） |
| 内存盘区 | 偏移 13,344,768，21,078,370 字节（gzip 压缩内存盘） |
| 设备树区 | 偏移 34,424,832，161,792 字节（前 64 字节是联发科私有头，之后是标准设备树） |
| 内嵌校验数据 | 偏移 34,586,624，1,664 字节，魔数 `AVB0`，`avbtool 1.2.0` 生成 |
| 校验尾标 | 文件最后 64 字节，魔数 `AVBf`，标记「被校验的镜像长度 = 34,586,624」 |
| 校验描述符 | sha256 哈希描述符，覆盖上述 34,586,624 字节 |
| 顶层校验标志位 | `flags = 0`（校验开启） |

### 6.2 换掉内核之后必然发生什么

自编内核的长度和内容都和原厂不同，**那个 sha256 哈希必然对不上**。要让它重新对上，必须用小米的私钥重新签名，我们手里没有、也不该有这个私钥。所以：

- 刷入自编启动镜像后，**AVB 校验会报「验证失败」**；
- **启动锁已解开的状态下**，引导程序通常采用「允许验证错误」策略：显示黄/橙色启动提示后继续启动，而不是直接拒绝。这台机器**现在装着的 Magisk Alpha 本身就已经改写了启动分区并且能正常开机**，这是最直接的实证——同一台设备、同样的解锁状态，「被改过的启动分区能启动」已经被验证了；
- **启动锁如果是锁上的**，这个镜像起不来。这也是第 7 节把「重新上锁」列为绝对禁区的原因。

### 6.3 可选兜底件（只在第一次启动失败时才考虑）

本轮另外准备了一个 `vbmeta-verification-disabled.img`（4 KiB，校验标志位设为「关闭校验 + 关闭哈希树」，不含任何描述符、不需要签名），等价于刷机工具在刷入时加 `--disable-verity --disable-verification` 生成的东西。将来如果因为校验被拒启动，标准做法是：

```sh
fastboot --disable-verity --disable-verification flash vbmeta_b vbmeta.img
```

**代价必须说清**：这会关掉系统分区的哈希树校验，改变整机安全状态；部分系统在校验状态变化后可能要求清除用户数据；而且它动了 `vbmeta_b`，回退时必须把原厂 `vbmeta.img` 刷回去（见第 5 节第一优先）。**它不是必需步骤，只是备用件**，能不动就不动。

### 6.4 防回滚

官方脚本里 `CURRENT_ANTI_VER=1`，开头读 `fastboot getvar anti`，手机当前计数大于 1 就拒绝刷。**只刷 `boot_b` 一个分区不涉及防回滚计数**，这也是单槽试刷相对全量恢复更安全的一点。但一旦走到「官方全量恢复」那一步，就要先读这个变量，别等脚本报错才发现。

## 7. 绝对不能碰的东西

| 禁区 | 后果 |
|------|------|
| `flash_all_lock.sh`（同目录下还有 `.bat` 版） | **会重新锁上启动锁**。自编内核 + 锁上的启动锁 = 必定起不来，而且可能要走一遍官方解锁流程才能恢复，代价极高 |
| 不带槽后缀的 `fastboot flash boot ...` | 不知道会写到一个槽还是两个槽，破坏「留一个好槽」的前提 |
| 试刷期间顺手 `flash super` / `erase metadata` / `flash userdata` | 用户数据全清，且虚拟 A/B 快照状态被打乱 |
| 在 a 槽状态没确认前 `set_active a` | 可能切到一套起不来、还读不懂现有数据的旧系统 |
| 试刷期间做系统更新 | 触发快照合并，回退路径变得不确定 |

## 8. 换成 SukiSU-Ultra 的得失对照（相对现在已装好的 Magisk Alpha）

| 维度 | 保持现状（Magisk Alpha 28103） | 换成 SukiSU-Ultra |
|------|-------------------------------|--------------------|
| 当前可用性 | 已确认 `uid=0(root)`，模块、隐藏机制都在正常工作 | 只做到了「内核编译成功 + 启动镜像打包成功」，**尚未刷入、尚未验证能开机、尚未验证能提权** |
| 部署方式 | 现成方案，用户态修补启动镜像 | 4.14 非通用内核规范机型，必须自己编译内核、手动挂钩，本轮已经跑通编译 |
| 授权模型 | Magisk 的授权管理 | 内核态授权名单 + 应用权限模板，理论上更细 |
| 隐藏能力 | 依赖已装模块 | 项目自带 SELinux / 挂载 / 内核版本伪装等，但**本轮为了在 4.14 上编过，主动关掉了 SuSFS、KPM、CPU 身份伪装等可选特性**，实际隐藏能力反而弱于现状 |
| 风险 | 已经稳定，几乎为零增量风险 | 自编内核与原厂有配置偏差（链接时优化/控制流完整性未恢复、部分调试开关打开），稳定性、续航、兼容性都未知 |
| 回退难度 | 不需要 | 按第 5 节可回退，但过程需要电脑 + 刷机模式 |

**结论**：从纯收益角度看，现在换过去是「用一个已经跑得好好的 root 方案，换一个还没验证过的自编内核」，风险明显大于收益。合理的做法是先把可刷镜像和回退路径备好（本轮已完成），等确实需要 SukiSU-Ultra 的某项能力、并且愿意承担试刷风险时再动手。

- [ ] 电池电量充足，数据线可靠，中途不拔线
- [ ] 知道 `flash_all_lock.sh` 不能用

## 10. 本轮实际做了什么、没做什么
