## 3. 先把几个名词说清楚

- **启动分区镜像**：手机开机时先加载的一小块分区内容，里面装着内核和内存盘。改它等于改开机要走的第一段代码，所以这份文档里所有产物都只是文件，没有写进手机。
- **开机早期运行器（preinit）**：SukiSU 在安卓系统还没起来之前就要执行的一小段程序，用来在最早时机准备好 root 环境。项目自带一套极简 C 库，不依赖系统库，因此对新旧内核头文件差异特别敏感。
- **CPU 身份伪装**：让某些检测程序读到的处理器型号、主频、指令集能力变成指定值，属于隐藏检测的一类手段。
- **内核补丁模块（KPM，`CONFIG_KPM`）**：允许在内核里动态加载一段补丁代码的功能。项目里的这份实现并不是自己完成加载，而是把请求转发给另一套叫 **KernelPatch** 的内核钩子。
- **SuSFS**：一套专门做隐藏的内核补丁，需要改动内核很多处并新增头文件，属于「另外打一整套补丁」，不是编译配置里勾一下就有。
- **链接时优化 / 控制流完整性（LTO / CFI）**：原厂量产内核真实开启的两种编译与保护机制，上一轮已经查明并补回；这一轮保持不变，避免和量产状态产生偏差。

## 4. 逐项详情与证据

### 4.1 开机早期运行器：真正补回来了

**之前为什么被关掉**：项目的构建脚本会检查编译产物目录里有没有一个内核导出的头文件（`$(objtree)/usr/include/linux/unistd.h`）。没有就自动加一个「禁用早期运行器」的编译参数，所以之前那份内核里其实根本没有这段程序。

**这一轮怎么做**：
1. 在云电脑跑 `make O=/workspace/out ARCH=arm64 headers_install`，生成内核导出的头文件目录，让构建脚本不再自动禁用。
2. 那套自带极简 C 库是按较新内核写的，在 4.14 上连续报出四处不兼容，逐一修掉：
   - 没有 `clone3` 系统调用和对应的参数结构 → 改回 4.14 有的 `clone()` 调用方式；
   - 没有 `linux/mount.h` 头文件 → 挂载标志位改从 4.14 有的 `linux/fs.h` 取；
   - 没有 `ksys_close()` 这个函数 → 改用 4.14 里等价的 `sys_close()`；
   - 没有「64 位时间结构」这个类型（`struct __kernel_timespec`，要 5.x 内核才有）→ 补一个内存布局等价的兜底类型定义。

**为什么这个兜底不算造假**：我核对过这台 4.14 arm64 内核的系统调用表，老的时间系统调用（`clock_gettime`、`clock_getres`、`clock_nanosleep`、`timerfd_gettime`、`ppoll`、`pselect6`）**全都在**，而对应的新 time64 调用**一个都没有**。也就是说那套精简 C 库里所有用到「64 位时间结构」的代码分支，在这颗内核上永远不会被执行；只有两个转换辅助函数被无条件编译，需要一个完整类型才能过编译。补类型定义只是让编译器满意，不改变任何实际运行逻辑。

**证据**：
- 单独编译出来的运行器可执行文件 `runner.elf` 为 15,160 字节；
- 最终内核里 `ksu_preinit_runner_start` 到 `ksu_preinit_runner_end` 两个地址相减**正好也是 15,160 字节**，说明这段程序被原样内嵌进了内核，不是空壳；
- 初始化函数 `ksu_preinit_init`、运行器相关处理函数都在最终内核的符号表里；
- 删掉全部中间产物后从头重编一次，编译返回 0，日志无错误。

### 4.2 CPU 身份伪装：补了能补的那部分，不假装补另一部分

第一次集成时，4.14 缺整套虚拟动态共享对象（vDSO，一种加速时间读取的机制）相关的时钟类型，所以整块功能被改成「返回不支持」。

**这一轮真正实现的三项**（都是这颗内核里确实存在的东西，按名字查到内核变量后改写）：
- 每个处理器核心的型号寄存器 `cpu_data[].reg_midr`；
- 主频基准值 `loops_per_jiffy`（对应 BogoMIPS）；
- 指令集能力位图 `elf_hwcap`。

我特别核对了这三个变量在最终内核里**全部存在**（`cpu_data`、`elf_hwcap`、`loops_per_jiffy` 都在符号表里），所以调用时不会退化成「不支持」。也在内核二进制里搜到了这次新写的提示字符串，确认代码没有被编译器优化掉。

**明确没做、也不谎称支持的两项**：vDSO 时钟模式改写、64 位 `elf_hwcap2` 改写。原因是 4.14 内核里连对应的结构体字段、枚举值都根本不存在。项目自己的处理接口会返回它实际写入的结果，而不是无条件回报「支持」。日志里也写明了这是「4.14 部分实现，没有 vDSO / hwcap2 改写」。

### 4.3 内核补丁模块：开关补齐了，功能链还断着（本轮最重要的负面发现）

开关已经打开，最终内核里也确实能找到入口函数、转发函数和桥接函数（`ksu_extension_kpm_io`、`do_kpm`、`sukisu_kpm_bridge` 等）。**但这不等于功能可用**，有两层原因：

1. **它依赖另一套内核钩子**。项目里这个桥接函数自己不加载补丁，而是借用一个系统调用处理函数、传入约定的魔数，去探测内核里有没有 KernelPatch 的钩子；只有钩子存在，后续加载、卸载、查询等操作才会被转发过去。这颗小米官方 4.14 内核并没有集成 KernelPatch。
2. **连它要借用的符号名字都对不上**。桥接函数依次找 `__arm64_sys_truncate`、带 `.cfi_jt` 后缀、带 `.cfi` 后缀这三种新内核命名；我在这颗 4.14 内核的符号表里查到的是老名字 `sys_truncate`，那三个新名字**一个都没有**。因此探测必然直接返回「不支持」。

换句话说：这一项是**结构性的不可用**，不是「少准备一个补丁模块文件」。要真正用起来，得另外把 KernelPatch 移植到这颗内核，并准备实际的补丁模块文件，两者本轮都没做、也没验证。项目自己的配置说明也写着「适合需要强制启用的场景，可能影响系统稳定性」，默认是关的。

### 4.4 SuSFS：不是开关能补的，明确放弃

试开该开关后编译直接报 `linux/susfs.h` 头文件不存在；项目构建输出本身就打印了一句「你还没有把 SuSFS 集成进内核」，并给出外部补丁仓库地址。它是需要改动内核多处、新增头文件和进程标志位的外部补丁集，而这颗 4.14 内核连它依赖的进程标志位都没有。

给它塞一个空的假实现，只会让界面显示「支持」而实际什么都不做。这种做法一律不做，最终配置保持明确关闭。

### 4.5 调试模式：保持关闭

项目默认关闭，打开只会往内核日志里多输出调试信息，对隐藏能力没有任何帮助，反而更容易暴露。不做改动。

## 6. 现在有两份候选启动镜像，试刷时该怎么选

这一节是为了将来真要刷的时候不用再临时猜。目前**两份都只是文件，都没有写进手机**。

**现在的情况**：上一轮的 `boot-sukisu-lto-stockdtb.img`（MD5 `4bc14c88fb8b76c370619f3b36c76437`）功能少，但内核里走的代码路径最少；这一轮新出的 `boot-sukisu-features-lto-stockdtb.img` 多了开机早期运行器和 CPU 身份伪装，也多了一个实际用不了的内核补丁模块开关。两者的共同点是：都从未开机验证过，都无法保证第一次就能起来。

**不弄清楚会怎样**：刷机剧本里写的命令用的是上一轮那个文件名。如果将来直接照脚本执行，刷进去的会是功能较少的旧版，补齐的这一轮等于白做；反过来，如果随手把文件名换成补齐版，就要承担开机早期运行器在这颗 4.14 内核上第一次运行的不确定性——它执行得比安卓系统还早，一旦有问题，表现就是开不了机，只能靠回退剧本救回来。

**三个选择**：

| 选择 | 具体做什么 | 代价 |
| --- | --- | --- |
| A：维持上一版为推荐产物 | 剧本里什么都不改，补齐版只作为资料留存 | 早期运行器、CPU 伪装依旧没进要刷的内核；但这几个能力本来也都还没验证过效果 |
| B：改成补齐版为推荐产物 | 把剧本里所有出现旧文件名的地方换成新文件名，执行前把新镜像从云电脑回传本机并复算校验值 | 多一段开机早期执行路径，首次开机的不确定性更高；且内核补丁模块开关在这颗内核上实际不产生收益 |
| C：两份都先不动，先做一次只验证「能否开机」的最小试刷 | 需要用户另行明确授权，并且仍要选一份 | 多一轮操作；不减少任何风险，只是把决策推后 |

**我的推荐：A（先维持上一版为推荐，补齐版作为候选保留）**。理由有三条：
1. 这一轮真正补上的两项里，开机早期运行器跑在开机最前端、完全未经真机验证，是新增风险最集中的一处；
2. 内核补丁模块这个开关在本内核上被证实不可用，等于只增加了内核代码量而没有实际收益；
3. 第一次试刷最该保证的是「能开机、能回退」，功能可以在确认开机无误之后再逐项加。

如果用户更想验证补齐效果，选 B 也完全可行，只是要在明确授权刷机时点名用哪一份，我会按指定文件重新核对新鲜度、回传、复算校验值再执行。**在用户明确说「刷机」之前，A 和 B 都不会执行。**
